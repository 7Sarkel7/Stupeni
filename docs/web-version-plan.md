# План веб-версии «Ступеней» (глубокий режим)

Статус: черновик плана, код не пишется. Автор плана — агент, решения — за владельцем (раздел 8).

## 0. Что и зачем

| | Мобильное приложение (как сейчас) | Веб (новое) |
|---|---|---|
| Режим | Duolingo/Sololearn: короткий урок + 2-минутная проверка | Глубокий: долгие вечера за компьютером |
| Содержание | Суть и квиз | Подробные объяснения, длинные практики, чтение официальных доков, проекты |
| Практика | В приложении | Локально в Android Studio, сдача через GitHub (ветка + push) на ревью |
| Прогресс | `SharedPreferences` | Отдельно, в браузере (`localStorage`). С телефоном не синхронизируется |
| Песочница кода | нет | **нет** (решение владельца) |

Что есть в репозитории сегодня (проверено): `content/catalog.json` — 9 треков (fundamentals, kotlin-android, cpp-esp32, backend, flutter, shipping, pgs, career, android-cis), у каждого урока `id`, `path` (md), `quiz` (`*.quiz.json`). Готовы (`ready`) треки 01–03 и `android-cis`. Flutter-приложение — `learner/`, тексты копируются в `learner/assets/content/` скриптом `tool/sync_content.sh`, в `pubspec.yaml` перечислены папки-ассеты. Уже есть `learner/web/` (шаблон Flutter), CI `build-apk.yml`. Есть домашки, лаборатории (`career/lab`), спеки капстоунов (`career/capstone/SPEC.md`, `android-cis/capstone/SPEC.md`) — это готовая основа для «длинных заданий».

## 1. Выбор технологии

### Вариант A. Тот же Flutter + web-таргет + слой «глубокого» контента
- Плюсы: один язык (Dart), уже есть код чтения каталога и прогресса; не нужен новый стек.
- Минусы:
  - Flutter Web рисует страницу сам (canvas): текст хуже выделяется и копируется, плохо ищется браузером (Ctrl+F), нет нормальных ссылок на раздел, тяжёлая первая загрузка (мегабайты), на слабом ноутбуке заметны тормоза. Для длинного чтения и копирования команд — как раз плохо.
  - Всё, что даёт «режим учебника» (оглавление справа, поиск, подсветка кода, вкладки, сворачиваемые подсказки, стиль Kotlin tour), надо писать руками. Это недели работы и вечная поддержка.
  - `flutter_markdown_plus` умеет базовый markdown; таблицы, блоки-подсказки и вкладки — самописные.
- Цена: высокая на старте и на поддержке; переиспользуется код, но не тот, что нужен вебу.

### Вариант B. Статический сайт-документация (генератор)
Кандидаты (все широко используются и поддерживаются): **Docusaurus** (Meta, React), **Astro Starlight**, **VitePress**. MkDocs Material не берём: его автор перевёл проект в режим поддержки.
- Плюсы: markdown — «родной» формат (наши уроки уже в md); поиск, оглавление справа, боковое меню, тёмная тема, подсветка Kotlin/bash, блоки-подсказки, вкладки, «Next step» внизу страницы — всё из коробки, это ровно стиль kotlinlang.org/docs. Лёгкая страница, нормальный текст, ссылки на разделы, быстрый старт. Хостинг на GitHub Pages бесплатный.
- Минусы: новый стек (Node.js, чуть-чуть React/MDX). Прогресс-галочки в браузере — маленький самописный скрипт (~100 строк).
- Цена: низкая на старте; поддержка — обновление зависимостей раз в пару месяцев (Dependabot).

### Рекомендация: **B, Docusaurus**
Причины: глубокий режим — это чтение + доки + сдача на ревью, а не интерактив; сайт-документация делает это лучше и в разы дешевле. Docusaurus выбран за самую большую аудиторию и документацию, нативный React для галочек прогресса, поддержку md/MDX, поиска и вкладок. Starlight — равноценная замена, если владельцу ближе Astro; решение не необратимое, так как контент — обычный markdown.

Flutter-приложение не меняется. Flutter web-таргет (`learner/web/`) в этом плане не используется.

## 2. Где хранится глубокий контент (без дублирования)

Принцип: **короткий урок остаётся единственным источником сути; глубокая глава — надстройка над ним, а не копия.**

```
content/
  catalog.json                 # мобильный каталог — НЕ меняется
  01-fundamentals/01-git.md    # короткий урок (мобайл) — НЕ меняется
  deep/                        # НОВОЕ, только для веба
    fundamentals/
      git/
        index.md               # глубокая глава (многостраничная: 01-…, 02-…)
        assignment.md
        research.md
    _shared/
      glossary.md              # словарь терминов (на него ссылаются главы)
      review-howto.md          # как сдавать на ревью (один раз, все ссылаются)
    deep.json                  # порядок глав и связь с id из catalog.json
site/                          # НОВОЕ: проект Docusaurus (docs.path = ../content/deep)
```

- Связь: во front matter главы `lesson: fund-git` (id из `catalog.json`). Сайт сам показывает «Короткая версия — в приложении» и подтягивает название/минуты из каталога. Текст короткого урока в главу не копируется.
- Мобильное приложение глубокий контент **не видит**: `pubspec.yaml` перечисляет папки-ассеты поштучно, `deep/` туда не входит, `sync_content.sh` её не копирует (проверить в PR 1 и закрепить проверкой в CI).
- Общие куски (глоссарий, инструкция по сдаче) лежат в `deep/_shared/` и вставляются через MDX-импорт, а не копируются.
- Ссылки на официальные доки — в одном файле `deep/links.json` (ключ → URL), чтобы CI проверял их на живость, а в главах писали `<Doc k="kotlin-collections"/>`. Это одна точка починки, если страница переехала.
- Проверка согласованности (скрипт в CI): каждая `lesson:` существует в каталоге; нет двух глав на один урок; у каждой главы есть обязательные разделы (см. п. 3).

## 3. Структура глубокой главы

Стиль — как Kotlin tour: короткие экраны, код с кнопкой копирования, «упражнение» в конце раздела, сворачиваемый ответ, «Следующий шаг» внизу.

Главная страница главы и разделы:

1. **Зачем это** — задача из жизни (1 абзац) и что вы сможете в конце.
2. **Слова простыми словами** — каждый термин объяснён до первого использования (в духе PEDAGOGY.md), ссылка в общий глоссарий.
3. **Разбор по шагам** — несколько подразделов; в каждом примере обязательный блок **до / действие / после** (команда или код, что изменилось). Бытовые аналогии. Раздел самодостаточен: нужные предпосылки пересказаны в 2–3 строках со ссылкой на «короткий урок».
4. **Типичные ошибки** — что видно на экране и что делать.
5. **Читаем официальные доки** (docs-research) — 3–5 вопросов, на которые в тексте главы ответа **нет**. Формат задания:
   - вопрос («Чем `List` отличается от `MutableList`? Что вернёт `listOf()` без аргументов?»);
   - ссылка на конкретную страницу (developer.android.com / kotlinlang.org / git-scm.com);
   - подсказка, какой раздел страницы искать;
   - формат ответа: 1–3 предложения + цитата/строка из доки, пишутся в `notes/<chapter>.md` в репозитории студента.
   Ответы проверяет ревьюер, «ключ» лежит в закрытом блоке для ревьюера (в `content/hints/`, как сейчас).
6. **Практика (assignment)** — длинное задание на 1–3 вечера в Android Studio. Единый шаблон `assignment.md`:
   - Цель и результат одним предложением.
   - Что подготовить (версии, ссылки на установку, кроме Android Studio ничего).
   - Задание по этапам (чекпойнты 1…N, у каждого — что запустить и что должно быть видно «после»).
   - Критерии приёмки (чек-лист да/нет, проверяемый по коду и скриншоту).
   - Что приложить в сдачу.
   - Рубрика ревью (3–4 пункта: работает, читается, коммиты осмысленные, доки прочитаны).
   - «Если застряли» — куда смотреть, прежде чем просить помощь.
7. **Проект (на несколько вечеров)** — в конце трека, не в каждой главе: этапы по вечерам (вечер 1 — каркас, вечер 2 — …), у каждого вечера своя сдача/ветка. Основа — уже написанные спеки капстоунов (`career/capstone/SPEC.md`, `android-cis/capstone/SPEC.md`).
8. **Итог и следующий шаг** — чек-лист «я умею…», ссылка на следующую главу, ссылка на мобильный квиз для закрепления.

### Поток сдачи на ревью (без доступа ко всему Android Studio у ревьюера)
1. Студент создаёт **свой** репозиторий (шаблон `stupeni-workbook` — отдельный репозиторий-шаблон, см. «Открытые вопросы») или форк.
2. Ветка на каждое задание: `assignment/<chapter>-<номер>` (например `assignment/kotlin-collections-1`).
3. Работает локально, коммиты маленькие и осмысленные (это отдельный пункт рубрики).
4. `git push` и **Pull Request в свой же `main`** (draft → ready) — PR и есть «сдача». Описание PR по шаблону `.github/pull_request_template.md` из репозитория-шаблона: что сделано, скриншот/лог запуска, ответы на docs-вопросы, на чём застрял.
5. Ревьюер (владелец, наставник или ИИ-агент) читает diff и оставляет комментарии построчно, ставит статус по рубрике. Студент исправляет новыми коммитами в ту же ветку.
6. Принято → студент вручную ставит галочку главы на сайте (локально в браузере) и делает merge.
Проверка кода без запуска у ревьюера: критерии приёмки сформулированы так, чтобы проверялись по diff + скриншоту + выводу тестов; где можно, в шаблоне лежит готовый unit-тест (как `career/lab`), CI репозитория-шаблона запускает `./gradlew test` и показывает зелёное/красное в PR.

Прогресс на сайте: `localStorage`, ключ вида `stupeni-web-v1`, галочки по разделам и главам, кнопка «экспорт/импорт JSON» (чтобы не потерять при чистке браузера). Никаких аккаунтов и серверов.

## 4. Какие главы углублять первыми (по текущему каталогу)

Порядок: сначала то, что нужно всем и что хорошо ложится на «читай доки + сделай руками», потом прикладное.

1. `fund-git` — Git (git-scm.com Pro Git, `git-scm.com/docs`); нужен для самой системы сдачи, поэтому первый. Задание: пройти весь поток «ветка → коммиты → push → PR» на своём репозитории.
2. `fund-http`, `fund-json` — HTTP и JSON (MDN можно как дополнение, но основа — доки OkHttp/kotlinx.serialization там, где доходит до кода).
3. `fund-debug` — отладка слоями (Logcat, debugger Android Studio — developer.android.com).
4. Kotlin-база под Android (в каталоге отдельного трека нет — `career-collections`, `career-models`, `career-algorithms`) — по образцу Kotlin tour (kotlinlang.org/docs/kotlin-tour-collections.html); здесь docs-research особенно полезен.
5. `and-coroutines`, `and-okhttp`, `and-state`, `and-display` — трек kotlin-android, первые уроки, затем Compose: `and-compose`, `and-remember`, `and-effects`, `and-navigation`, `and-vm-compose`, `and-lazy`, `and-m3`, `and-compose-test`.
6. Мини-проект 1 из `and-homework` / `and-compose-homework` (RemoteSkeleton) — на 2–3 вечера.
7. `android-cis` — flow, threads, Hilt, data (Room/DataStore), tests, CI, push, work; затем капстоун «Смена» как большой многовечерний проект.
8. `career` — резюме, система, capstone DeskNode (`career-capstone`).
9. Позже / по желанию: `cpp-esp32`, `backend`, `flutter`, `shipping`, `pgs` — вне фокуса Android, углублять только после п. 1–8.

## 5. Хостинг и CI

- Хостинг: **GitHub Pages**, деплой через GitHub Actions (`actions/configure-pages`, `actions/upload-pages-artifact`, `actions/deploy-pages`). В настройках репозитория: Pages → Source = «GitHub Actions».
- URL: `https://<owner>.github.io/Stupeni/`; в Docusaurus `baseUrl: '/Stupeni/'`, `url` — домен Pages.
- Workflow `.github/workflows/deploy-web.yml`:
  - триггеры: `push` в `main` при изменении `content/deep/**`, `site/**`, `content/catalog.json`; `pull_request` (только сборка и проверки, без деплоя); `workflow_dispatch`;
  - `permissions: contents: read, pages: write, id-token: write`; `concurrency` без отмены деплоя;
  - шаги: checkout → setup-node (LTS, кэш npm) → `npm ci` → скрипт проверки связей контента (п. 2) → проверка ссылок на доки (`links.json`, необязательная, не блокирует merge, лучше по расписанию раз в неделю) → `npm run build` (Docusaurus с `onBrokenLinks: 'throw'`) → upload-pages-artifact → deploy (только `main`);
  - отдельно от `build-apk.yml`: эти два пайплайна друг друга не запускают (разные `paths`).
- Dependabot для npm и actions раз в месяц.

## 7. Принципы качества (чек-лист для каждого PR с главой)
- Новичок поймёт: каждый термин объяснён простыми словами до первого употребления.
- Бытовой пример и блок «до / действие / после» в каждом примере.
- Глава самодостаточна (минимум пересказа предпосылок).
- Только широко используемые и поддерживаемые инструменты/библиотеки; номера версий не замораживаются в тексте, а берутся со страницы-источника (как в `PEDAGOGY.md`).
- Все ссылки на официальные доки идут через `links.json`.
- Нет кода-решения в репозитории (намёки в `hints/`, как сейчас).

## 8. Открытые вопросы к владельцу
1. Docusaurus или Astro Starlight? (рекомендация — Docusaurus; если нет предпочтения, берём его).
2. Репозиторий для сдач: отдельный публичный шаблон `stupeni-workbook` или ветки прямо в Stupeni? (рекомендация — отдельный, чтобы не засорять учебный репозиторий).
3. Кто ревьюер: вы сами, внешний наставник, ИИ-агент? Влияет на формат рубрики и описание PR.
4. Язык сайта — только русский? Официальные доки англоязычные: нужен ли в главах мини-словарь английских терминов (рекомендация — да).
5. Домен: достаточно `github.io` или нужен свой?
6. Нужна ли ссылка «Открыть в глубоком режиме» из мобильного приложения (это единственное изменение в `learner/`), или полностью раздельно?
7. Порядок п. 4 подходит? Что поднять выше (например, `android-cis` для скорого отклика на вакансии)?
8. Нужны ли «вечерние» таймеры/планировщик (сколько вечеров занимает проект), или достаточно указания «≈ N вечеров» в тексте?
9. Лицензия контента: оставляем как в репозитории или явно (например, CC BY) для публичного сайта?
