# CI на GitHub Actions

**Модуль:** A6. Найм Android, стек СНГ  
**Уровень:** J  
**Время:** около 35 минут  
**Лаборатория:** нет  
**Намёк:** [solutions/hint-ci.md](solutions/hint-ci.md)  
**Дальше:** [Самостоятельная: зелёный workflow](12-homework-ci.md)

## Цель

Собрать workflow (файл, в котором описано, когда и какие шаги GitHub запускает автоматически), который на каждом push (пуш — отправка ваших коммитов на сервер, например на GitHub) и pull request (просьба на GitHub проверить ваши изменения и добавить их в основную ветку) гоняет юнит-тесты `hire-scratch` тем же JDK, что и локальная сборка.

## Зачем это вам

Локально тесты зелёные, пока вы помните их запускать. CI красит ветку, когда вы забыли. На ревью (проверка вашего кода другим человеком до того, как изменения попадут в проект) это один из немногих артефактов (готовый результат сборки или проверки, который можно скачать, например APK), который нанимающий открывает без вашего ноутбука. В Ступенях уже есть workflow сборки APK (файл установки приложения для Android) приложения-учебника: [.github/workflows/build-apk.yml](../../.github/workflows/build-apk.yml). Он про Flutter и этот учебник. В `hire-scratch` его не копируют: другой проект, другая команда, другие версии действий.

Документация, с которой сверяют файл: [GitHub Actions](https://docs.github.com/en/actions), страницы Marketplace у `actions/checkout` и `actions/setup-java` на день коммита (сохранённый в Git снимок изменений с подписью).

## Теория

Workflow — файл в `.github/workflows`. Событие `push` и событие `pull_request` запускают его на ветках, где вы работаете. Одной машины Ubuntu хватает.

Шаги идут по порядку. Сначала checkout (чекаут — переключение рабочей папки на другую ветку или коммит), иначе на машине нет исходников. Затем JDK. Цифра JDK в workflow, в Android Studio и в README — одна и та же. Расхождение «локально 21, в CI 17» выглядит как случайный красный тест. Затем команда Gradle, которая гоняет юнит-тесты, не инструментальные. Если `gradlew` лежит в каталоге приложения, шаг выполняется оттуда, а не из пустого корня.

Права workflow держат узкими. Чтение репозитория достаточно для тестов. Секреты в YAML не вписывают и не печатают в лог (журнал, куда программа записывает, что делает). Keystore, bearer и сервисный JSON туда не кладут. `google-services.json`, если он появится в уроке про пуш, не является разрешением положить серверный ключ в git.

Версию действия пишут ту, которую Marketplace показывает сейчас. Число из статьи двухлетней давности может указывать на отозванный релиз (выпуск готовой версии приложения для пользователей). В этом уроке номера действий специально нет.

Красный шаг не отключают комментарием. Либо тест починен, либо код починен, либо тест был неверным и его переписали честно.

Кэш (быстрая копия уже полученных данных, чтобы не запрашивать их заново) Gradle ускоряет повторный прогон и не входит в планку J. Эмулятор в CI не входит в планку J: он дорогой и медленный. Тест кадра остаётся локальным, как в прошлой работе.

Бейдж в README — по желанию. Ссылка на последний зелёный прогон достаточна.

## Разбор на примере

Вечер CI у `hire-scratch`. Файл workflow называется понятно, не `main.yml`, если в репозитории потом будет второй workflow. Команда из README совпадает с командой в шаге. Вы пушите мелкий коммит, который ломает тест ViewModel, видите красный крест, чините, видите зелёный. Скриншот креста можно не хранить. Привычка смотреть на крест нужна.

Workflow Учебника «Ступени» в этот вечер только открывают глазами, чтобы узнать форму `on`, `jobs` и `steps`. Строки Flutter из него в Android-проект не переносят.

## Упражнения

На бумаге выпишите шаги своего будущего файла: событие, система, JDK, каталог, команда. Сверьте JDK с `compileOptions` или с тем, что показывает Android Studio. Намёк [solutions/hint-ci.md](solutions/hint-ci.md) не открывайте, пока файл сам не откажется собираться минут сорок.

### Самопроверка

- В списке шагов нет эмулятора.
- В списке шагов нет секрета.
- Команда совпадает с той, которой вы уже гоняете MockK-тест.

## Типичные ошибки

- Скопировать `build-apk.yml` Ступеней.
- Запустить `connectedAndroidTest` и ждать эмулятор, которого нет.
- Зафиксировать чужую версию `checkout` из блога.
- Зелёный workflow, который вызывает `assemble`, но не тесты.

## Чеклист

- [ ] Понятно, какой тест должен покраснеть при поломке ViewModel.
- [ ] JDK выбран и записан у себя, не выдуман из этого абзаца.
- [ ] Секреты в файл не планируются.
