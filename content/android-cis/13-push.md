## Цель

Показать уведомление из data-сообщения, не уронить процесс на мусорном payload (пейлоад — полезные данные внутри сообщения, без служебных заголовков) и выбрать один транспорт: FCM или RuStore Push.

## Зачем это вам

Телефоны в РФ и СНГ расходятся. На части есть Google Play services, и пуш приходит через FCM. На части Play services нет, и продуктовая команда смотрит на RuStore Push или на обёртку, которая умеет несколько транспортов. Junior (джун, junior — разработчик начального уровня), который подключает только один путь и честно пишет, какой путь не подключён, звучит сильнее, чем список SDK (набор инструментов для разработки под платформу) в резюме без канала уведомлений.

Страницы: [FCM на Android](https://firebase.google.com/docs/cloud-messaging/android/client), [каналы уведомлений](https://developer.android.com/develop/ui/views/notifications/channels), [разрешение на уведомления](https://developer.android.com/develop/ui/views/notifications/notification-permission), обзор RuStore без номера SDK: [пуш-уведомления](https://www.rustore.ru/help/sdk/push-notifications). Номер SDK берут с актуальной страницы Kotlin/Java в день проекта.

## Теория

С API (набор правил, по которым одна программа обращается к другой) 26 уведомление без канала не показывается. Канал создают до первого `notify`. Имя канала человек видит в настройках системы, поэтому оно на понятном языке. С API 33 разрешение `POST_NOTIFICATIONS` спрашивают в рантайме (время, когда программа уже запущена и работает, в отличие от сборки). Отказ человека не лечат повторным запросом в цикле.

Сообщение с готовым блоком notification система может показать сама, когда приложение в фоне, и не отдать данные в ваш код так, как вы ждёте. Data-сообщение приходит в сервис, и текст решаете вы. Для журнала это важно: в строке есть число неотправленных записей, его знает телефон, а не шаблон из консоли.

Разбор карты `Map<String, String>` — чистая функция, её и фиксирует лабораторная.

- Нет типа, пустой тип, чужой регистр, неизвестный тип — тихий `Ignore`. Процесс не падает.
- `type` равный `shift_reminder` — напоминание закрыть смену. Лишние ключи не мешают.
- `type` равный `sync_nudge` — просьба синхронизироваться. Ключ `pending` обязателен: `0` или целое без плюса, пробела и ведущего нуля. Иначе `Ignore`.

Показ уведомления — один класс. Его зовут и локальные часы, и сервис пуша. Сервис не открывает базу надолго и не вызывает Retrofit. Для `sync_nudge` он ставит уже описанную уникальную работу синхронизации. Тяжёлую работу в `onMessageReceived` система может оборвать.

Токен (секретная строка-пропуск, которая подтверждает, кто вы) устройства — адрес доставки. Его не пишут в info-лог релиза (выпуск готовой версии приложения для пользователей) и не коммитят (сохранённый в Git снимок изменений с подписью). Обновление токена обрабатывают, иначе сервер шлёт на старый адрес.

FCM требует проект Firebase и файл конфигурации клиента. Это не серверный ключ. Серверный ключ облачной отправки в репозиторий не кладут. Отладочное (отладка, дебаг — поиск причины ошибки: остановка программы, просмотр значений, логов) сообщение можно прислать из консоли Firebase на токен отладки.

RuStore Push — другой канал доставки, не «тот же Firebase под другим именем». Чтобы сообщение дошло, приложение заводят в консоли RuStore, сборка проходит модерацию, подпись сборки на устройстве совпадает с подписью в консоли, на устройстве есть дистрибьютор, чаще само приложение RuStore. Проектный идентификатор берут из консоли. Эти условия пишут в README, иначе кажется, что код «просто не работает». Обёртка Universal Push, которая везёт RuStore, FCM и HMS вместе, в планку J не входит.

В одной домашней работе подключают один транспорт. Второй описывают абзацем: что пришлось бы поменять в реализации `PushTokenSource`, не в разборе карты. Разбор карты от транспорта не зависит.

## Разбор на примере

Приходит карта `type=shift_reminder`. Сервис вызывает `parsePush`, получает напоминание, просит `ShiftNotifier` показать «Закройте смену». Приходит `pending=01`. Разбор возвращает `Ignore`, уведомления нет, исключения нет. Приходит `sync_nudge` с `pending=2`. Уведомление говорит, что есть неотправленные, и планировщик ставит одну синхронизацию. Повторный nudge не создаёт второго работника. Это правило добьёт урок WorkManager, здесь его только не ломают.

### Самопроверка

- `SHIFT_REMINDER` не считается напоминанием.
- Сервис пуша не содержит вызова API журнала.
- Намёк [solutions/hint-push.md](solutions/hint-push.md) закрыт.

## Типичные ошибки

- Показать пуш только логом (журнал, куда программа записывает, что делает) и забыть канал.
- Делать синхронизацию фото внутри сервиса.
- Подключить оба SDK и не суметь сказать, кто принёс токен.
- Закоммитить серверный ключ отправки.
