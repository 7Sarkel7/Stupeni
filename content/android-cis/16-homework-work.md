# Самостоятельная: уникальная синхронизация

**Модуль:** A8. Найм Android, стек СНГ  
**Уровень:** J  
**Время:** один вечер в `hire-scratch`  
**Лаборатория:** `WorkPolicyTest`  
**Намёк:** [solutions/hint-work.md](solutions/hint-work.md)  
**Дальше:** [Капстоун: журнал «Смена»](17-capstone.md)

## Цель

Поставить в `hire-scratch` одну уникальную работу, которая пишет время в DataStore, когда сеть есть, и не плодится от повторного нажатия.

## Зачем это вам

Журнал смены позовёт тот же приём для очереди фото. Если уникальное имя вы впервые увидите в капстоуне, вы смешаете его с Retrofit и Room. Этот вечер оставляет работника, которого видно в логе (журнал, куда программа записывает, что делает) и в настройках системы как одну задачу.

## Теория

Полноценный batch на сервер здесь не нужен. Работник читает DataStore, пишет туда миллисекунды запуска и возвращает успех. Ограничение сети включено. Кнопка и, если сервис пуша (отправка ваших коммитов на сервер, например на GitHub) уже есть, команда nudge ставят работу с одним именем.

Правило `shouldEnqueueSync` в приложении повторите своими словами и покройте тестом. Можно вызвать свою копию функции до постановки работы. Лабораторный файл курса остаётся с решением только у вас локально и в учебный репозиторий не уезжает.

## Разбор на примере

Первое нажатие при включённой сети ставит `scratch-sync`. Второе нажатие, пока работа не закончилась, не увеличивает число работ с этим именем. Авиарежим: функция или ограничение не дают работе притвориться успешной синхронизацией. После успеха в DataStore новое время, экран его показывает через уже знакомый `Flow`.

Напоминание о часе в эту работу не входит. Его ставят в капстоуне, отдельным именем.

## Упражнения

```bash
cd content/android-cis/lab
./gradlew test --tests dev.stupeni.hire.WorkPolicyTest
```

В `hire-scratch`:

- [ ] `CoroutineWorker` пишет время в DataStore и возвращает `success`.
- [ ] Запрос с `NetworkType.CONNECTED` и с запретом низкого заряда.
- [ ] Одно уникальное имя, повторный тап не создаёт вторую работу. Это видно логом имён или списком работ, который вы смотрели.
- [ ] Пустая «очередь» в вашем правиле — например флаг «нечего делать» — работу не ставит. Как вы кодируете «нечего делать», опишите в README одной фразой.
- [ ] Юнит-тест на правило постановки зелёный и входит в уже существующий workflow (файл, в котором описано, когда и какие шаги GitHub запускает автоматически).
- [ ] Сохранение заметки по-прежнему не переехало в работника.

### Рубрика

| Часть | 0 | 1 | 2 |
| --- | --- | --- | --- |
| Лаборатория | `WorkPolicyTest` красный | зелёный, пустую очередь путаете с ошибкой | зелёный, четыре условия вслух |
| Имя | новый запрос на каждый тап | имя есть, политику не проверяли | одно имя, второй тап не плодит работу, вы это видели |
| Сеть | работа пишет успех без сети и без ограничения | ограничение есть, низкий заряд забыт | сеть и низкий заряд заданы, правило им соответствует |
| CI (автоматическая сборка и проверка проекта на сервере при каждом изменении) | новый тест не в workflow | тест есть локально, workflow его не гоняет | workflow зелёный вместе с этим тестом |
| Честность | скопирован образец UploadWorker из документации без ограничений | намёк открыт сразу | свой работник и своё имя |

Ноль по любой строке — капстоун рано начинать с фона. Репозиторий `smena` можно завести пустым на M0, синхронизацию в нём не пишут, пока эта рубрика не без нулей.

## Типичные ошибки

- Назвать работу `sync` в `hire-scratch` и тем же именем потом незаметно скопировать класс в `smena`.
- Вернуть `retry` при выключенном интернете из самого `doWork`, хотя ограничение и так ждёт сеть, и получить плотный цикл.
- Забыть добавить тест в ту команду, которую вызывает Actions.
