# Откат и спасение

**Модуль:** 01. Фундамент  
**Время:** около 45 минут  
**Дальше:** [Ветки, слияние и конфликты](01-git-05-branches.md)

## Цель

Различать «убрать правку из индекса», «выбросить правку с диска», «передвинуть ветку» и «записать новый коммит, который отменяет старый». Вернуть коммит, который кажется потерянным, через reflog.

## Зачем это вам

На собеседовании и в первый месяц работы путают `reset` и `revert`. Первая команда переписывает, куда смотрит ветка. Вторая добавляет снимок. На общем `main` переписывание ломает коллегам уже скачанные коммиты. На своей вечерней ветке `reset` как раз спасает кривой эксперимент с таймаутом, если вы ещё не отправили его на сервер.

## Теория

Держите в голове три слоя из первого урока. Каждая команда отката трогает свой набор слоёв.

### restore: файл, не история

`git restore` меняет рабочее дерево или индекс. Коммиты он не двигает. Команда есть в Git 2.23 и новее. Старая форма `git checkout -- файл` делает то же с рабочим деревом; её ещё встретите в старых инструкциях.

| Команда | Индекс | Рабочее дерево | История |
| --- | --- | --- | --- |
| `git restore статус.txt` | как был | берётся из индекса | не трогается |
| `git restore --staged статус.txt` | как в `HEAD` | как было | не трогается |
| `git restore --source=HEAD --staged --worktree статус.txt` | как в `HEAD` | как в `HEAD` | не трогается |

Первая забирает с диска незакоммиченную правку. Если вы уже сделали `git add`, в индексе лежит отмеченная версия, и `git restore файл` вернёт к ней, а не к последнему коммиту. Чтобы и индекс, и диск совпали с коммитом, нужна третья строка таблицы.

`--source=HEAD~1 -- статус.txt` берёт файл из предыдущего снимка и кладёт в рабочее дерево. Это точечный откат одного файла, без движения ветки.

### reset: куда смотрит ветка

`git reset` двигает текущую ветку на указанный коммит. Режим решает, что станет с индексом и диском. По умолчанию режим `--mixed`.

Цель `HEAD~1` — родитель текущего коммита. `HEAD~2` — на два шага назад. Чужой SHA тоже годится.

| Режим | Ветка и HEAD | Индекс | Рабочее дерево |
| --- | --- | --- | --- |
| `--soft` | на указанный коммит | остаётся как у снимка, с которого ушли | без изменений |
| `--mixed` | на указанный коммит | приводится к указанному коммиту | без изменений |
| `--hard` | на указанный коммит | приводится к указанному коммиту | приводится к указанному коммиту |

```text
до soft/mixed/hard HEAD~1

    C1 ---- C2 ---- C3
                    ^
                   main, HEAD

после --soft HEAD~1

    C1 ---- C2 ---- C3
            ^         индекс всё ещё содержит дерево C3
           main

после --mixed HEAD~1

    C1 ---- C2 ---- C3
            ^
           main
    индекс = дерево C2
    на диске остались файлы как в C3 (их видно в git diff)

после --hard HEAD~1

    C1 ---- C2 ---- C3
            ^
           main
    индекс и диск = дерево C2
```

`C3` после этого не стирается сразу. На него не указывает ветка, но reflog помнит SHA. `--hard` выбрасывает и те правки, которые вы не коммитили, если они лежали в тех же файлах. Перед `--hard` смотрят `git status`. Если там есть нужное, сначала коммит или stash.

`git reset` на ветке, которую уже запушили, и следующий `push` разойдутся с сервером: вы переписали общую историю. Для отмены такого коммита у команды есть `revert`.

Старая путаница: `git reset файл` (без SHA, смешанный режим по пути) снимает файл с индекса, как `git restore --staged файл`. В новых уроках для файлов пишите `restore`, для движения ветки — `reset` с явным `--soft`, `--mixed` или `--hard`.

### revert: новый коммит против старого

`git revert SHA` смотрит diff указанного коммита и создаёт новый коммит с обратным diff. История растёт. Уже скачанные коллегами SHA остаются на месте.

```text
    C1 ---- C2 ---- C3 ---- R
                            ^
                           main
    R отменяет изменения C3, родители R указывают на C3
```

Так отменяют коммит, который уже на `origin/main`. Сообщение Git предложит сам, его стоит дописать причиной: что сломалось на столе.

Если в середине коммита нужна только часть, `git revert -n SHA` положит обратный diff в индекс и не закоммитит. Дальше вы правите и коммитите сами. Для первого месяца достаточно обычного `git revert` без `-n`.

Конфликт при revert решают как конфликт слияния: правят файл, `git add`, `git revert --continue`. Бросить попытку: `git revert --abort`.

### commit --amend

`git commit --amend` берёт индекс и сообщение и записывает новый коммит вместо текущего кончика. Родитель тот же, SHA другой.

Им правят последнее сообщение или добавляют файл, который забыли. Условия, при которых это дешёво:

- коммит ещё не на сервере, или на сервере он только ваш и никто от него не ответвился;
- вы готовы к тому, что старый SHA останется в reflog и пропадёт из ветки.

```text
$ git add status.txt
$ git commit --amend -m "feat: первая строка status станца" -m "timeout_ms — черновик для пульта."
```

`--amend` после push требует потом `--force-with-lease`. На `main`, который защищён, force всё равно отвергнут. Там забытый файл догоняют новым коммитом, а кривой уже общий снимок — через `revert`.

### reflog

Reflog — локальный журнал, куда двигались `HEAD` и ветки в этом клоне. На сервер он не уходит. По умолчанию записи живут около 90 дней.

```text
$ git reflog
a1b2c3d HEAD@{0}: commit (amend): feat: первая строка status станца
9f8e7d6 HEAD@{1}: commit: feat: первая строка status станца
0c11aa2 HEAD@{2}: reset: moving to HEAD~1
```

Вернуть ветку на снимок до ошибки, не затирая диск наугад:

```text
$ git switch -c rescue HEAD@{1}
```

`rescue` указывает на коммит, который был до amend или до reset. Потом его смотрят через `git log` и `git diff main` и решают, сливать или перенести отдельные файлы. `git reset --hard HEAD@{1}` делает то же движение на текущей ветке и сразу переписывает файлы: это уже осознанный шаг, когда вы прочитали, что лежит на `HEAD@{1}`.

Потерянная ветка тоже находится здесь: в reflog есть строка `checkout: moving from experiment/ping-retry to main`. SHA слева от неё — кончик брошенной ветки. `git branch experiment/ping-retry SHA` вешает имя обратно.

### Detached HEAD

`git switch --detach a1b2c3d` или `git checkout a1b2c3d` открывает снимок, не двигая ветку. `git status` пишет `HEAD detached at a1b2c3d`.

Новые коммиты в этом состоянии есть в объектах и в reflog, но ни одна ветка на них не указывает. Закроете ноутбук и переключитесь на `main` — коммиты станут «пропавшими», пока жив reflog.

Как оставить работу:

```text
$ git switch -c experiment/from-detached
```

Как просто вернуться, если коммитов в detached вы не делали:

```text
$ git switch main
```

## Разбор на примере

В песочнице три коммита. Последний — случайный `println`, уже закоммиченный, на сервер вы его не отправляли.

Посмотреть слои и убрать коммит, оставив правку на диске:

```text
$ git log --oneline
b7c6d5e (HEAD -> main) chore: println для отладки
e4f5a6b fix: повторять ping, пока SoftAP не ответит
a1b2c3d feat: первая строка status станца

$ git reset --mixed HEAD~1
$ git status -sb
## main
 M app/Client.kt
$ git log --oneline
e4f5a6b (HEAD -> main) fix: повторять ping, пока SoftAP не ответит
```

Ветка снова на коммите про ping. Строка с `println` осталась в файле как незакоммиченная правка. Её можно выбросить:

```text
$ git restore --source=HEAD --worktree --staged app/Client.kt
$ git status
On branch main
nothing to commit, working tree clean
```

Через минуту вы понимаете, что `println` всё-таки был нужен как напоминание. Reflog:

```text
$ git reflog
e4f5a6b HEAD@{0}: restore: ...
e4f5a6b HEAD@{1}: reset: moving to HEAD~1
b7c6d5e HEAD@{2}: commit: chore: println для отладки
$ git show b7c6d5e --stat
```

Снимок `b7c6d5e` на месте. Вернуть его отдельной веткой, не сдвигая `main`:

```text
$ git branch rescue/println b7c6d5e
$ git switch rescue/println
$ git log --oneline -1
b7c6d5e chore: println для отладки
```

Если этот коммит уже уехал на общий `main`, reset вам не помощник. На `main` для обычного коммита с одним родителем:

```text
$ git revert b7c6d5e
```

Появится новый коммит. `git log --oneline` покажет и старый `println`, и новый коммит, который его отменяет. Коллеги подтянут обычным `pull`.

У коммита слияния родителей два, и Git не знает, какую сторону считать «основной линией». Тогда пишут `git revert -m 1 SHA`: `-m 1` выбирает первого родителя, того, что был кончиком ветки, когда вы делали merge. Для коммита с одним родителем этот флаг не нужен и команда его не примет.

Сообщение последнего коммита, который ещё никуда не push, правят так:

```text
$ git commit --amend -m "fix: повторять ping, пока SoftAP не ответит"
$ git rev-parse HEAD
```

Новый хеш другой. Старый виден в `git reflog` как `HEAD@{1}`.

## Упражнения

1. В песочнице сделайте лишний коммит поверх текущего `main`. Выполните `git reset --soft HEAD~1`, затем `git status` и `git diff --staged`. Где теперь содержимое лишнего коммита? Повторите ситуацию на копии (ещё один коммит) для `--mixed` и запишите, чем статус отличается.
2. Зачем перед `git reset --hard` смотрят `git status`? Назовите команду, которая после случайного `--hard` покажет SHA, где ветка была минуту назад, и команду, которая повесит на этот SHA новое имя ветки, не трогая текущий `main`.
3. Коммит `fix: ping` уже на `origin/main`, им пользуются два человека. Какой командой вы отмените его поведение и почему `git reset --hard` на вашем ноутбуке их копии не починит.
4. Вы сделали `git switch --detach HEAD~1`, поправили файл и закоммитили. `git status` пишет `HEAD detached`. Что выполнить до переключения на `main`, чтобы коммит не остался только в reflog?

## Типичные ошибки

- `git reset --hard` при грязном статусе «чтобы статус стал зелёным».
- Amend уже общего коммита и force на `main`.
- `git revert` там, где коммит ещё никуда не уходил и проще снять его `reset --mixed`.
- Путать `git restore файл` после `git add`: диск вернётся к индексу, не к последнему хорошему смыслу, если в индекс уже попал мусор.
- Думать, что reflog есть на GitHub. Это журнал одного клона.
- Уходить из detached HEAD переключением ветки, не дав имя новым коммитам.
