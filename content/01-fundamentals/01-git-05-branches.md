# Ветки, слияние и конфликты

**Модуль:** 01. Фундамент  
**Время:** около 45 минут  
**Дальше:** [Rebase, интерактивный rebase, cherry-pick](01-git-06-rebase.md)

## Цель

Держать рабочий `main` отдельно от эксперимента. Сливать ветку fast-forward и слиянием с двумя родителями. Дочитывать конфликт до осмысленного файла, а не до случайного выбора «наших» или «их» строк.

## Зачем это вам

Пока опыт с BLE и TLS живёт прямо на `main`, следующий вечер начинается с неизвестной прошивки. На работе то же правило: в `main` попадает то, что уже можно собрать, опыт идёт веткой и возвращается через merge или rebase. Конфликт — не поломка Git. Это две правки одной строки, и собрать результат можете только вы, потому что вы знаете контракт `/v1/reading`.

## Теория

### Имя ветки

Ветка — файл-указатель в `.git/refs/heads/` (или запись в packed-refs) с SHA коммита. Создание ветки не копирует файлы.

```text
$ git branch
* main

$ git switch -c experiment/ping-retry
$ git branch
* experiment/ping-retry
  main
```

`git switch -c` создаёт ветку и переводит на неё `HEAD`. Без `-c` `git switch main` только переводит. Старая форма, её полно в инструкциях и в Android Studio: `git checkout -b experiment/ping-retry` и `git checkout main`. Для веток в новых командах предпочитайте `switch`: у `checkout` вторая работа — выписывать файлы, из-за этого им легко затереть правку.

Имя с косой чертой — просто имя. Полезный шаблон: `experiment/что-проверяем` для вечера с станцией и `feature/что-делаем` для задачи, которая поедет в pull request. Пробелы и русские буквы в имени лучше не использовать: скрипты и сервер их переживают не везде.

Список веток с кончиками:

```text
$ git branch -vv
* experiment/ping-retry a1b2c3d feat: первая строка status станции
  main                 a1b2c3d feat: первая строка status станции
```

Пока новых коммитов нет, оба имени смотрят на один SHA. Коммит сдвинет только ту ветку, которая сейчас в `HEAD`.

Переименовать текущую: `git branch -m feature/ping-retry`. Удалить локальную, которая уже влита и не нужна: `git branch -d feature/ping-retry`. Флаг `-d` откажется удалять неслитую ветку. `-D` удалит всё равно. Коммиты останутся в reflog, пока живёт запись.

Грязное рабочее дерево и смена ветки: Git разрешает switch, если файлы, которые отличаются между ветками, вы не трогали. Если трогали, будет отказ `would be overwritten by checkout`. Это не потеря данных. Куда деть правку — урок про stash. Короткий путь, если правка уже цельная: закоммитить её на текущей ветке и потом переключиться.

### Fast-forward

Если `main` — прямой предок ветки, слияние не создаёт новый снимок. Указатель `main` просто переезжает вперёд.

```text
до, вы на main:

    A ---- B                main, HEAD
            \
             C ---- D       feature/ping-retry

$ git merge feature/ping-retry
Updating B..D
Fast-forward

после:

    A ---- B ---- C ---- D  main, feature/ping-retry
                            HEAD
```

История остаётся прямой. Так бывает, когда в `main` никто не коммитил, пока вы работали.

`git merge --ff-only feature/ping-retry` сольёт только так и остановится, если нужен коммит слияния. Это страховка на скриптах: «двигай указатель, не создавай merge молча».

### Слияние с двумя родителями

Если `main` ушёл вперёд, общего «просто переезда» нет. Git собирает новый коммит с двумя родителями. Берутся три снимка: общий предок (база), ваш кончик (`ours`), входящая ветка (`theirs`).

```text
         main, до merge
          |
    A -- B -- E
          \
           C -- D     feature/fields

после git merge feature/fields, HEAD на main:

    A -- B -- E -- M   main
          \       /
           C ---- D    feature/fields
```

`M` — коммит слияния. Его дерево — результат смеси. `git show M` показывает, что вошло. `git log --oneline --graph` рисует развилку.

`git merge --no-ff feature/ping-retry` создаёт такой коммит даже при fast-forward. Команды так сохраняют в истории факт «вот тут влилась задача», даже если ветка была короткой. Другие команды как раз хотят прямую историю и просят rebase. Оба выбора — про договор, не про «правильный Git». Договор на работе важнее вкуса.

Пока слияние не закончено, `git status` пишет `All conflicts fixed but you are still merging` или список конфликтных файлов. Завершение — `git commit` без нового сообщения, Git подставит текст про merge. Отмена незавершённого слияния — `git merge --abort`: ветка вернётся туда, где была до команды.

### Что покажет diff ветки

Для ревью полезны две формы:

- `git diff main...feature/ping-retry` — три точки: что изменилось на feature с момента общего предка. Так обычно смотрит pull request.
- `git diff main..feature/ping-retry` — две точки: разница кончиков. Если `main` уехал вперёд, в этот diff попадут и чужие коммиты, с обратным знаком.

Три точки — «что я сделал в задаче». Две точки — «чем два кончика отличаются прямо сейчас».

### Конфликт

Конфликт возникает, когда обе стороны меняли одни и те же строки, или одна удалила файл, а другая его правила. Git помечает файл и останавливается.

```text
<<<<<<< HEAD
timeout_ms:1500
=======
timeout_ms:800
>>>>>>> feature/ping-retry
```

`<<<<<<<` — версия текущей ветки, на которой вы запустили merge (`ours`, сейчас это `HEAD`). `=======` разделяет. `>>>>>>>` — версия входящей ветки (`theirs`).

Маркеры нельзя оставлять в файле. Сборка иногда даже проходит, а в прошивку уезжает текст `<<<<<<<`. После правки файл выглядит как обычный исходник:

```text
fw:1.0.0
timeout_ms:800
```

Дальше:

```text
$ git add status.txt
$ git status
$ git commit
```

Если правильный ответ — целиком одна из сторон, есть короткие команды. Ими пользуются, когда прочитали diff и правда хотят одну сторону, а не «лишь бы прошло»:

```text
$ git checkout --ours -- status.txt
$ git checkout --theirs -- status.txt
```

Во время обычного merge `--ours` — ветка, на которой вы стоите, `--theirs` — то, что вливаете. В rebase смысл этих слов другой, это следующий урок. Пока вы в merge, не переносите привычку rebase.

`git merge --abort` возвращает состояние до попытки. Уже сделанный коммит слияния abort не откатывает: его отменяют `git revert -m 1 SHA`, если он уехал на сервер, или `reset`, если он ещё только ваш.

Конфликт удаления: одна сторона удалила `Client.kt`, другая меняла его. `git status` покажет `deleted by them` или `deleted by us`. Решение — либо вернуть файл (`git add`), либо подтвердить удаление (`git rm`). Оба варианта — осознанные.

## Разбор на примере

`main` отвечает за статус. Вы проверяете более короткий таймаут на своей ветке и не трогаете рабочую линию.

```text
$ cd ~/sandbox/git-course
$ git switch main
$ git switch -c feature/timeout
$ printf 'fw:1.0.0\ntimeout_ms:800\n' > status.txt
$ git add status.txt
$ git commit -m "feat: timeout ping 800 мс на время опыта"
```

Пока вы это делали, на `main` то же число `timeout_ms` уже поменяли и добавили поле board. В одной песочнице это можно сыграть так. Обе стороны должны расходиться в одной строке, иначе Git иногда сольёт соседние правки сам:

```text
$ git switch main
$ printf 'fw:1.0.0\ntimeout_ms:3000\nboard:esp32s3_dev\n' > status.txt
$ git add status.txt
$ git commit -m "feat: в status есть model платы"
$ git merge feature/timeout
Auto-merging status.txt
CONFLICT (content): Merge conflict in status.txt
Automatic merge failed; fix conflicts and then commit the result.
```

Общий предок держал `timeout_ms:1500`. `main` записал 3000 и строку `board`, ветка записала 800. Откройте файл. Оставьте таймаут опыта и поле board: станции нужны оба факта.

```text
fw:1.0.0
timeout_ms:800
board:esp32s3_dev
```

```text
$ git add status.txt
$ git commit -m "merge: timeout 800 мс и поле model"
$ git log --oneline --graph --decorate
*   m1m2m3m (HEAD -> main) merge: timeout 800 мс и поле model
|\
| * t1t2t3t (feature/timeout) feat: timeout ping 800 мс на время опыта
* | a9a9a9a feat: в status есть model платы
|/
* a1b2c3d feat: первая строка status станции
```

Если опыт мёртвый и сливать его не надо, ветку можно не мержить. Возврат к рабочему снимку: `git switch main`. Саму плату после экспериментальной прошивки ещё нужно прошить файлом с `main`: Git помнит исходник, не содержимое флеша.

Проверка, что именно уедет в ревью, до слияния:

```text
$ git diff main...feature/timeout
```

Три точки показывают коммиты задачи, без чужого `model`, если вы ещё не сливали.

## Упражнения

1. В песочнице заведите `feature/timeout` от чистого коммита, сделайте один коммит, вернитесь на `main` и выполните `git merge feature/timeout`. Это был fast-forward или коммит с двумя родителями? Как это видно в `git log --oneline --graph`.
2. Повторите конфликт из разбора: на `main` другое число `timeout_ms` и лишняя строка, на ветке третье число. Соберите файл так, чтобы остались и выбранный вами таймаут, и лишняя строка. Почему `git checkout --theirs` здесь был бы хуже ручной сборки.
3. Вы на `main` и вливаете `feature/fields`. В маркерах конфликта над `=======` чьё значение? Как называется сторона под чертой.
4. Коллега просит посмотреть «только мои коммиты относительно main». Какую из команд вы выполните и почему: `git diff main..feature` или `git diff main...feature`.

### Ориентир для самопроверки

Сначала запишите ответы своими словами. Короткий ключ — [01-git-05-branches.md](../hints/01-git-05-branches.md). В приложении нажмите на эту ссылку: откроется ключ, без отметки «изучил». Откройте его после своей попытки. Дословно в тетрадь ключ не переписывайте.

## Типичные ошибки

- Эксперимент сразу в `main`, потому что «ветка — это долго».
- Коммит с оставшимися маркерами `<<<<<<<`.
- `--theirs` или `--ours` без чтения обеих сторон.
- `git branch -D` на ветке, которую ещё не слили и чей SHA вы не записали. Reflog поможет не всегда, если ветку создавали в другом клоне и здесь на неё не переключались.
- Путать три точки и две в `git diff` и смотреть не тот набор коммитов перед ревью.
- Считать merge концом работы на плате. Прошивку на флеш Git не откатывает.
