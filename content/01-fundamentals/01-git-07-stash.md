# Stash: спрятать незакоммиченное

**Модуль:** 01. Фундамент  
**Время:** около 35 минут  
**Дальше:** [Удалённые репозитории, теги, релизы](01-git-08-remotes.md)

## Цель

Убрать незакоммиченные правки в стопку, переключить ветку или обновить её, вернуть правки обратно. Разобрать отказ `git pull` и отказ смены ветки, когда локальные изменения принадлежат другой задаче.

## Зачем это вам

Типичный вечер и типичный понедельник на работе выглядят одинаково. Вы уже правите парсер (код, который разбирает строку, например JSON, на понятные программе части; сам разбор называют парсингом) статуса на ветке задачи. В чат пишут: «обнови main, там новый контракт». `git pull` или `git switch` отвечают, что ваши локальные изменения будут затёрты, и ничего не делают. Это не поломка сети. Git отказывается выбросить несохранённую работу. Stash — полка для этой работы на десять минут, не замена коммиту (сохранённый в Git снимок изменений с подписью).

## Теория

Stash — особый коммит (на самом деле пара коммитов: индекс и рабочее дерево), на который не указывает ветка. Им заведует список `stash@{0}`, `stash@{1}` и дальше. Ноль — самая свежая запись. Записи локальные, на сервер сами не уходят.

### Положить

```text
$ git stash push -m "черновик полей status, ещё не коммит"
Saved working directory and index state On feature/status-fields: черновик полей status, ещё не коммит
```

Короткая форма `git stash -m "текст"` делает то же. Без сообщения Git подставит имя ветки и заголовок текущего коммита, через день вы не вспомните, какая полка ваша.

По умолчанию в stash уходят изменения отслеживаемых файлов. Новый файл, который ещё никогда не добавляли (`??` в статусе), останется на диске и снова помешает switch, если на другой ветке такого пути нет... он как раз не мешает switch, если файла нет на той ветке, но мешает, если вы хотели унести и его. Чтобы забрать и неотслеживаемые файлы:

```text
$ git stash push -u -m "черновик вместе с новым Client.kt"
```

`-u` равно `--include-untracked`. Файлы из `.gitignore` эта команда не трогает. Для них есть `-a` / `--all`. `-a` утащит и то, что вы специально игнорировали, включая локальные сборки. В первый месяц `-a` не используйте.

`git stash push -m "только парсер" -- app/StatusParser.kt` прячет один путь, остальное оставляет на месте.

После успешного push (пуш — отправка ваших коммитов на сервер, например на GitHub) рабочее дерево по отслеживаемым файлам чистое относительно `HEAD`. Правка жива в списке stash.

### Посмотреть

```text
$ git stash list
stash@{0}: On feature/status-fields: черновик полей status, ещё не коммит
stash@{1}: On main: WIP on main: a1b2c3d feat: первая строка status станции

$ git stash show -p stash@{0}
```

`show` без `-p` печатает только статистику файлов. `-p` печатает diff (дифф — список отличий между двумя версиями файла: что добавили, что убрали). Всегда читайте его перед `pop`: полок бывает несколько, легко вернуть чужой вечер.

### Вернуть

`git stash apply stash@{0}` кладёт правки на текущую ветку и оставляет запись в списке.

`git stash pop stash@{0}` делает то же и удаляет запись, если применение прошло без конфликта. Если файлы конфликтуют, запись остаётся в списке. Её удаляют вручную, когда конфликт разобран и вы уверены, что копия больше не нужна: `git stash drop stash@{0}`.

Без номера и `apply`, и `pop` берут `stash@{0}`.

Конфликтные маркеры те же, что при merge (мерж — слияние, то есть объединение изменений одной ветки Git с другой). После ручной сборки — `git add`. Отдельного `--continue` у stash нет: это уже обычные незакоммиченные правки.

Выбросить запись, не применяя: `git stash drop stash@{1}`. Очистить всю стопку: `git stash clear`. Вторая команда необратима на практике, хотя объекты ещё какое-то время можно вытащить из reflog (личный журнал Git, где записаны ваши перемещения по истории; с его помощью можно вернуть «потерянные» коммиты) коммитов stash. Не вызывайте `clear`, чтобы «навести красоту».

### Сценарий: pull не идёт из-за правок другой задачи

Вы на ветке `feature/status-fields`. В `StatusParser.kt` незакоммиченный разбор поля `model`. Эти правки — не для `main` и не готовы к коммиту. Коллега влил в `main` другой таймаут (предельное время ожидания ответа, после которого ожидание обрывают) и просит обновиться. Вы тянете текущую ветку или пытаетесь сначала перейти на `main`.

Обновление текущей ветки:

```text
$ git pull
error: Your local changes to the following files would be overwritten by merge:
	app/src/main/kotlin/dev/station/StatusParser.kt
Please commit your changes or stash them before you merge.
Aborting
Updating a1b2c3d..b2c3d4e
```

Смена ветки, если вы вспомнили, что черновик вообще от другой задачи, а обновить надо `main`:

```text
$ git switch main
error: Your local changes to the following files would be overwritten by checkout:
	app/src/main/kotlin/dev/station/StatusParser.kt
Please commit your changes or stash them before you switch branches.
Aborting
```

Оба отказа про одно: Git не затирает локальные байты файлом из другого снимка. Коммит был бы честным, если черновик уже цельный. Если нет — полка:

```text
$ git status -sb
$ git stash push -m "черновик полей status, ветка feature/status-fields"
$ git switch main
$ git pull
$ git switch feature/status-fields
$ git stash pop
```

Если цель была обновить ту же ветку, а не уходить на `main`:

```text
$ git stash push -m "черновик полей status перед pull"
$ git pull
$ git stash pop
```

`git pull` здесь подтянет чужие коммиты в чистом дереве. `pop` вернёт ваш черновик поверх. Если коллега трогал те же строки, `pop` остановится на маркерах. Соберите файл, `git add`, проверьте `git stash list`: запись на месте, потому что pop не дошёл до drop. Когда черновик снова только ваш и читается, `git stash drop` уберёт копию.

Чего эта полка не делает: не заменяет ветку. Если черновик про поля `model`, а вы случайно применили его на ветке про звук, `git diff` покажет чужую правку. Тогда `git restore` файла и новый `pop` уже на правильной ветке, пока запись не удалена. Поэтому до `drop` смотрят `git diff`.

Коммит против stash: если на задачу уже есть ветка и мысль цельная, лучше короткий коммит `wip`, чем третья безымянная полка. Stash хорош на минуты и часы. Через неделю `stash@{3}` без внятного `-m` — потерянная работа.

## Разбор на примере

Песочница без сервера. Смоделируйте чужой `main` второй веткой, чтобы отказ `switch` был настоящим.

```text
$ cd ~/sandbox/git-course
$ git switch main
$ printf 'fun parse(body: String) = body\n' > Parser.kt
$ git add Parser.kt
$ git commit -m "feat: заготовка парсера status"
$ git switch -c feature/status-fields
$ printf 'fun parse(body: String) = body.substringBefore(" ")\n' > Parser.kt
```

Не коммитьте. Это черновик другой задачи. На `main` тем временем «коллега» меняет тот же файл. Чтобы сыграть коллегу, спрячьте черновик, иначе switch не пустит:

```text
$ git stash push -m "черновик полей status"
$ git switch main
$ printf 'fun parse(body: String) = body.trim()\n' > Parser.kt
$ git add Parser.kt
$ git commit -m "fix: обрезать пробелы в теле status"
$ git switch feature/status-fields
$ git stash pop
```

Вы снова на своей ветке, черновик на месте, `main` впереди по этому файлу. Попытка влить свежий `main` в задачу, не убирая черновик:

```text
$ git merge main
error: Your local changes to the following files would be overwritten by merge:
	Parser.kt
Please commit your changes or stash them before you merge.
Aborting
```

Тот же текст, которым `git pull` останавливается, когда pull делает merge. Починка:

```text
$ git stash push -m "черновик полей status перед merge main"
$ git merge main
$ git stash pop
```

Дальше либо чистый diff вашего черновика поверх уже обновлённой ветки, либо маркеры. В маркерах оставьте смысл обоих: обрезку пробелов с `main` и `substringBefore`, если он всё ещё нужен задаче. Посмотрите список:

```text
$ git stash list
$ git stash show -p stash@{0}
```

Если pop прошёл чисто, верхней записи с этим сообщением уже нет. Если нет — дочитайте diff и только потом `git stash drop`.

## Упражнения

1. Воспроизведите отказ merge из разбора. Вставьте в тетрадь одну строку ошибки. Какими тремя командами вы обновляете ветку и возвращаете черновик.
2. Чем `git stash apply` отличается от `git stash pop`, если применение без конфликта и если с конфликтом.
3. Черновик — новый файл `Notes.kt`, его ещё не добавляли. Обычный `git stash push -m "заметки"` его не забрал, `git status` всё ещё показывает `??`. Какой флаг нужен и почему `-a` здесь опасен, если рядом лежит игнорируемый `build/`.
4. Вы спрятали правку с ветки про парсер и случайно сделали `pop` на ветке про звук. Запись уже удалилась из списка, потому что конфликтов не было. Как вернуть файл звуковой ветки к коммиту и есть ли ещё шанс достать спрятанный diff, если вы не делали `clear`.

## Типичные ошибки

- `git stash clear` в конце вечера «чтобы список не пугал».
- Pop не глядя, на какой вы ветке.
- Прятать в stash то, что уже пора коммитить на именной ветке.
- Думать, что stash заменяет push: на другом ноутбуке этой полки нет.
- `git pull` снова и снова при той же ошибке, без чтения строки `would be overwritten`.
- `-a` и случайно спрятанный каталог сборки или локальный ключ, который потом всплывёт в `stash show -p`.

## Чеклист

- [ ] Умею `git stash push -m` с фразой, по которой полку узнать.
- [ ] Перед pop смотрю `git stash show -p`.
- [ ] Знаю, что при конфликте pop оставляет запись в списке.
- [ ] Отказ pull из-за локальных правок чиню через stash, а не через `--hard`.
- [ ] Неотслеживаемый нужный файл забираю с `-u`, не с `-a`.
