# Снимок дня: status, add, commit, история

**Модуль:** 01. Фундамент  
**Время:** около 45 минут  
**Дальше:** [Откат и спасение](01-git-04-undo.md)

## Цель

Каждый день собирать понятный коммит: смотреть статус и diff, отмечать куски через `git add -p`, писать сообщение, по которому через неделю видно поведение. Читать историю, один коммит и автора строки. Не пускать в снимок сборки, секреты и машинный мусор.

## Зачем это вам

На ревью (проверка вашего кода другим человеком до того, как изменения попадут в проект) смотрят diff и сообщение, не вашу память. «фикс» (исправление ошибки; хотфикс — срочное исправление, которое выпускают без ожидания обычного релиза) через неделю не отличается от десяти других «фиксов». `git add .` рядом с `local.properties` и `.env` однажды увезёт путь к SDK (набор инструментов для разработки под платформу) и пароль в историю. Это ломает и вечер со станцией, и испытательный срок.

## Теория

### status

`git status` отвечает на четыре вопроса: какая ветка, следит ли она за remote (удалённая копия репозитория на сервере; origin — имя по умолчанию для основного такого адреса), что уже в индексе, что изменено на диске, какие файлы Git ещё не отслеживает.

Короткий вид удобен в скрипте и в привычке:

```text
$ git status -sb
## main
 M app/src/main/kotlin/dev/station/StationWifiClient.kt
?? local.properties
```

Пробел перед `M` в первой колонке значит: индекс чистый. `M` во второй колонке — правка в рабочем дереве. `??` — неотслеживаемый файл. Две колонки букв — формат `--short`. Первая колонка про индекс, вторая про рабочее дерево.

### diff

| Команда | Что сравнивает |
| --- | --- |
| `git diff` | рабочее дерево и индекс |
| `git diff --staged` | индекс и последний коммит (`HEAD`) |
| `git diff HEAD` | рабочее дерево и последний коммит, сразу оба слоя |
| `git diff HEAD~1 HEAD` | два соседних коммита |

Перед `git add` смотрите `git diff`. После `git add` смотрите `git diff --staged`: это ровно то, что запишет коммит. Пароль в этом выводе — стоп, из индекса его убирают до коммита (`git restore --staged` будет в следующем уроке).

### add и add -p

`git add путь` копирует текущее содержимое файла в индекс. Каталог добавляет всё внутри, чего нет в ignore.

`git add -p` показывает изменения кусками (hunk — один связный кусок изменений внутри файла) и спрашивает, какой кусок войдёт в снимок. Так в один коммит попадает правка ping, а отладочный (отладка, дебаг — поиск причины ошибки: остановка программы, просмотр значений, логов) `println` остаётся на диске.

```text
$ git add -p
diff --git a/StationWifiClient.kt b/StationWifiClient.kt
@@ -20,3 +20,7 @@
+        repeat(8) { attempt ->
+            if (ping()) return
+            delay(1_500)
+        }
(1/1) Stage this hunk [y,n,q,a,d,s,e,?]?
```

Ответы, которых хватает в первый месяц: `y` — взять кусок, `n` — оставить незакоммиченным, `s` — разбить кусок мельче, `q` — выйти и не трогать оставшиеся, `a` — взять этот и все следующие. `?` печатает подсказку.

`git add .` из корня репозитория отметит всё неотслеживаемое, что не попало под ignore. Это нормальная команда в чистом учебном каталоге и плохая привычка в проекте Android, пока вы не прочитали `git status`.

### Сообщение коммита

Сообщение отвечает на «что изменилось для поведения» и «зачем». Заголовок в повелительном наклонении, как подпись к патчу (небольшой набор правок, который можно применить к коду): «повторять ping», не «починил» и не «правки».

Тело отделяют пустой строкой. В теле — причина, ограничение, ссылка на контракт. Список файлов в заголовке не нужен: его и так показывает `git show`.

Два флага `-m` дают заголовок и тело без редактора:

```text
$ git commit -m "fix: ping станции уходит с UI-потока" -m "OkHttp в onClick держал экран, пока SoftAP молчал."
```

Без `-m` откроется `core.editor`. Пустой заголовок или строка из одних комментариев отменяют коммит.

### Conventional Commits

На многих работах заголовок начинают с типа. Это договорённость [Conventional Commits](https://www.conventionalcommits.org/), не закон Git. Её читают люди и иногда скрипты релиза (выпуск готовой версии приложения для пользователей).

```text
тип(область): что сделано
```

Область можно опустить. Типы, которые стоит узнавать с первого дня:

| Тип | Когда |
| --- | --- |
| `feat` | новое поведение для пользователя или для контракта |
| `fix` | исправление поведения |
| `docs` | только документация |
| `refactor` | структура кода без смены поведения |
| `test` | тесты |
| `chore` | рутина, которая не про поведение продукта |
| `build` | сборка, Gradle, зависимости |
| `ci` | GitHub Actions и другие проверки |

Примеры для станции:

```text
feat: пульт читает fw из тела /v1/reading
fix: повторять ping, пока SoftAP не ответит
build: поднять compileSdk по доке Android
ci: собирать APK при правках content
```

Один коммит — один смысл. Интерфейс пульта, прошивка и случайный чертёж в одном снимке через неделю не разбираются.

### log, show, blame

```text
$ git log --oneline --graph --all --decorate
* e4f5a6b (HEAD -> experiment/ping-retry) fix: повторять ping, пока SoftAP не ответит
* a1b2c3d (main) feat: первая строка status станции
```

`--oneline` — хеш (SHA, хеш — уникальный идентификатор коммита из букв и цифр) и заголовок. `--graph` — рёбра между родителями. `--all` — все ветки, не только текущая. `--decorate` — имена веток и тегов (постоянная метка на коммите, обычно с номером версии) на коммитах. Алиас (короткое имя, подставляемое вместо длинного) `lg` из прошлого урока — это эта строка.

`git show a1b2c3d` печатает сообщение и diff коммита. `git show HEAD:status.txt` печатает файл так, как он лежал в снимке, даже если на диске он уже другой.

`git blame -L 1,5 status.txt` для каждой строки показывает последний коммит, который её поставил. Это не приговор автору. Это вход: нашли SHA, открыли `git show`, прочитали зачем. Строка, переехавшая при форматировании, покажет коммит форматирования, а не исходную мысль. Тогда ищут глубже: `git log -S 'timeout_ms' -- status.txt` находит коммиты, где эта подстрока появилась или исчезла.

### .gitignore

Файл `.gitignore` в корне репозитория перечисляет шаблоны, которые `git status` не предлагает добавить. Он действует на неотслеживаемые пути. Уже закоммиченный файл ignore не прячет.

```text
# сборка Android и Gradle
.gradle/
build/
**/build/
local.properties
*.apk
*.aab
*.keystore

# секреты
.env
.env.*
!.env.example
*.jks

# прошивка и мусор стола
.pio/
*.bin
*.elf
serial-dump-*.log

# ОС
.DS_Store
Thumbs.db
```

Правила, которые путают в начале:

- `build/` без ведущего слэша игнорирует каталог с таким именем на любой глубине. Так пишут в шаблонах Android, рядом с `.gradle/`. Шаблон `/build/` закрыл бы только каталог в корне репозитория.
- `*.apk` — любое имя с этим суффиксом.
- `!` отменяет игнор для более узкого шаблона. `!.env.example` оставляет пример переменных, в котором значений нет.
- Строка с `#` — комментарий.
- Секрет, который уже в коммите, из истории этой строкой не исчезает.

Если файл уже отслеживается, его снимают с учёта, оставляя копию на диске:

```text
$ git rm --cached local.properties
```

Дальше коммит фиксирует удаление из снимка. Файл на диске остаётся, и ignore начинает его скрывать.

Глобальный exclude (`git config --global core.excludesfile ~/.gitignore_global`) годится для мусора редактора, который не хочет видеть ни один ваш репозиторий. Правила проекта всё равно кладут в `.gitignore` и коммитят: коллега про глобальный файл не знает.

Проверка, почему файл не виден или всё ещё виден:

```text
$ git check-ignore -v local.properties
.gitignore:5:local.properties	local.properties
```

## Разбор на примере

В `~/sandbox/git-course` уже есть коммит со `status.txt`. Вечер: вы учите пульт повторять ping и случайно положили рядом файл с паролем точки.

```text
$ printf 'SSID=METEO-A1B2\nPASS=super-secret\n' > .env
$ printf 'sdk.dir=/home/you/Android/Sdk\n' > local.properties
$ git status -sb
## main
?? .env
?? local.properties
```

Сначала ignore, потом код. Создайте `.gitignore` как в теории (хватит строк `.env`, `local.properties`, `build/`). Затем:

```text
$ git status -sb
## main
?? .gitignore
$ git check-ignore -v .env local.properties
.gitignore:1:.env	.env
.gitignore:2:local.properties	local.properties
$ git add .gitignore
$ git commit -m "chore: не коммитить .env и local.properties"
```

Теперь правка клиента. В файле две независимые мысли. Отметьте одну.

```text
$ mkdir -p app
$ printf 'fun ping(): Boolean = false\n' > app/Client.kt
$ git add app/Client.kt
$ git commit -m "feat: заготовка клиента ping"
```

Откройте файл и внесите два куска: цикл повторов и `println("debug")`. Через `git add -p` возьмите только цикл (`y` на нём, `n` на отладке). Проверьте индекс:

```text
$ git diff --staged
$ git commit -m "fix: повторять ping, пока SoftAP не ответит" -m "До 8 попыток с паузой. Отладочный вывод в коммит не входит."
$ git log --oneline --graph --all --decorate
$ git show --stat HEAD
$ git blame -L 1,8 app/Client.kt
```

В `git show` нет `.env`. В blame строка цикла указывает на коммит про SoftAP (плата сама раздаёт Wi-Fi, как маленький роутер). `println` всё ещё висит в `git diff` и в следующий снимок не входит.

## Упражнения

1. В песочнице доведите пример до коммита с `-p`. Вставьте в ответ: заголовок коммита, пуст ли `git diff --staged` после коммита, остался ли отладочный кусок в `git diff`.
2. Напишите сообщение (заголовок в стиле conventional commits и одно предложение тела): хендлер (обработчик: код, который принимает событие или запрос и реагирует на него) `POST /v1/publish` больше не читает журнал на карте внутри себя, а только запоминает путь и ставит флаг. Почему список файлов в заголовке не нужен.
3. Файл `secrets.env` уже был закоммичен вчера, сегодня вы добавили `*.env` в `.gitignore`. Покажется ли он в `git status` как изменённый, если поправить пароль внутри? Что сделать, чтобы новые правки пароля не предлагались к коммиту, и почему старый коммит от этого не станет безопасным.
4. `git log -S 'timeout_ms' --oneline -- status.txt`. Какой коммит команда обязана найти в вашей песочнице и чем этот поиск отличается от `git blame`.

## Типичные ошибки

- `git add .` при непустом списке `??`, не читая имена.
- Коммит с заголовком `фикс`, `правки`, `update files`.
- Один коммит на несвязанные правки, потому что «уже конец вечера».
- Вера, что `.gitignore` стирает файл из старых коммитов.
- `git rm` без `--cached` на `local.properties`: файл исчезнет и с диска, Android Studio потеряет путь к SDK.
- Читать `blame` как «этот человек виноват», не открывая `git show`.

## Чеклист

- [ ] Перед коммитом смотрю `git diff --staged`.
- [ ] Умею отметить один кусок через `git add -p`.
- [ ] Заголовок говорит о поведении, тип conventional commits узнаю.
- [ ] `git log --oneline --graph --all --decorate` читается без шпаргалки.
- [ ] В песочнице `.env` и `local.properties` не входят в `git show HEAD`.
