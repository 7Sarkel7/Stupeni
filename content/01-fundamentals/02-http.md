# HTTP без тумана

**Модуль:** 01. Фундамент  
**Время:** около 30 минут  
**Дальше:** [JSON и не-JSON](03-json.md)

## Цель

Читать обмен пульта и станца как три куска: стартовая строка, заголовки, тело. По коду ответа понимать, это успех, ошибка вашего запроса или плата честно говорит «карты нет». Проверять `GET /v1/reading` браузером или `curl` до того, как писать Kotlin.

## Зачем это вам

Пока ноутбук не открывает status, Android ни при чём. Пульт — ещё один клиент того же HTTP. Если не различать «нет TCP», «пришёл 400» и «пришёл 200 с текстом ошибки внутри», вы будете чинить кнопку, хотя сломан путь на карте.

В локальной сети станц говорит по обычному HTTP, порт 80, без TLS. Адрес точки доступа платы по умолчанию `192.168.10.1`. Это сознательное упрощение стола: сертификат на SoftAP только мешает первой проверке. Облако позже будет другим протоколом (`wss`), не «тем же HTTP, только из интернета».

## Теория

Запрос:

```http
POST /api/display HTTP/1.1
Host: 192.168.10.1
Content-Type: application/x-www-form-urlencoded

path=photos/sunset.gif
```

- **Метод** — что сделать. `GET` не меняет станц, им снимают статус и списки. `POST` просит действие: показать файл, остановить, принять заливку.
- **Путь** — какой ручкой пользоваться. Ведущий слэш обязателен: `/v1/reading`, не `api/status`. Опечатка без слэша — отдельный маршрут, которого пульт не вызывает.
- **Заголовки** — метаданные. Для формы важен `Content-Type`. Для заливки файла это будет `multipart/form-data`, не JSON.
- **Тело** — сами данные. У `GET /v1/reading` тела нет.

Ответ устроен так же: код, заголовки, тело.

| Код | Смысл на станце | Что делает пульт |
| --- | --- | --- |
| 200 | Действие принято или статус снят | Читать тело |
| 400 | Запрос плохой: пустой путь, нет файла | Показать тело как причину, не повторять вслепую |
| 503 | Плата жива, но зависимость нет (карта) | Сказать человеку «SD недоступна», не «станц выключен» |

Тело status в этой архитектуре — короткий текст, не веб-страница:

```text
OK fw:1.2.0 board:esp32s3_dev
```

Поля `fw:` и `model:` потом читает обновление прошивки. Пока достаточно глазами увидеть `OK`.

Хендлер на плате тонкий. Он разбирает аргументы, вызывает одно действие и отвечает. Он не крутит GIF и не ждёт минуту. Иначе `loop` не обслужит следующего клиента: HTTP на Arduino-`WebServer` живёт только пока `loop` вызывает `handleClient()`.

Один и тот же жест («стоп», «показать») могут принести HTTP из LAN и позже облако. Действие одно, транспорты разные. Если логика показа скопирована в два файла, вы почините кнопку и сломаете голос.

Проверка со стола, телефон ещё не нужен:

```bash
curl -sS -m 3 http://192.168.10.1/v1/reading
curl -sS -m 3 -X POST http://192.168.10.1/api/display \
  --data-urlencode "path=photos/sunset.gif"
```

`-m 3` — не висеть вечно, если плата не в этой сети. Пустой вывод и «connection refused» — это не HTTP-код. Кода нет, когда нет соединения.

## Разбор на примере

Показать ролик, который уже лежит на карте:

1. Пульт собирает `POST /api/display` с полем `path`.
2. Плата читает поле, проверяет, что путь не пустой и файл есть.
3. Если нет — `400` и короткая причина (`empty`, `missing`).
4. Если да — запоминает путь, ставит флаг «надо играть», отвечает `200` и `OK`.
5. Кадры рисует цикл прошивки, не этот запрос.

Пока шага 5 нет, экран чёрный при честном `200`. Это уже не «HTTP не работает». Status и display разведены: первый доказывает связь, второй доказывает контракт команды.

Заливка файла — тот же HTTP, другое тело. Туда едут байты, имя, тип и CRC. Ответ исторически текстовый, с префиксом `SAVED:OK:`, а не объект. Путать его с JSON — отдельный урок.

## Упражнения

1. `curl` к status повесился на 3 секундах и оборвался по таймауту. Назовите два разных объяснения, которые ещё не требуют открывать Android Studio.
2. Пульт послал `POST /api/display` с пустым `path` и получил `400` с телом `empty`. Что показать человеку и почему повтор той же команды не поможет?
3. Зачем ведущий слэш в `server.on("/v1/reading", ...)` и что увидит пульт, если зарегистрировать `"api/status"`?

### Ориентир для самопроверки

1. Телефон не в сети SoftAP, либо плата не слушает 80 (сервер не запущен, `handleClient` не крутится, не тот IP). Это отсутствие соединения, кода 200/400 ещё нет.
2. Человеку — текст причины. Повтор с тем же пустым путём снова даст 400. Чинить надо вызов, не «нажимать быстрее».
3. Путь в HTTP абсолютный от корня хоста и начинается с `/`. Без слэша маршрут другой, запрос пульта на `/v1/reading` в него не попадёт.

## Типичные ошибки

- Писать OkHttp, не открыв status в браузере.
- Считать любой ответ с телом успехом и игнорировать код 400/503.
- Класть тяжёлую работу (декод GIF, `delay` на секунды) в хендлер. Клиент ждёт, остальные запросы стоят.
- Думать, что локальный станц обязан говорить HTTPS. На SoftAP в этом проекте — `http://` и порт 80. Из-за этого на Android 9+ отдельно разрешают cleartext. Это тема модуля 02, но корни здесь.
- Делать два разных «стопа»: один для кнопки, другой для облака. Расходятся в первую же неделю.
