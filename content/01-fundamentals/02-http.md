# HTTP без тумана

**Модуль:** 01. Фундамент  
**Время:** около 30 минут  
**Дальше:** [JSON и не-JSON](03-json.md)

## Цель

Читать обмен пульта и станции как три куска: стартовая строка, заголовки, тело. По коду ответа понимать, это успех, ошибка вашего запроса или плата честно говорит «карты нет». Проверять `GET /v1/reading` браузером или `curl` до того, как писать Kotlin.

## Зачем это вам

Пока ноутбук не открывает status, Android ни при чём. Пульт — ещё один клиент того же HTTP. Если не различать «нет TCP», «пришёл 400» и «пришёл 200 с текстом ошибки внутри», вы будете чинить кнопку, хотя сломан путь на карте.

В локальной сети станция говорит по обычному HTTP, порт 80, без TLS. Адрес точки доступа в этом учебном проекте — `192.168.10.1`. Это сознательное упрощение стола: сертификат на SoftAP только мешает первой проверке. Облако позже будет другим протоколом (`wss`), не «тем же HTTP, только из интернета».

## Теория

Запрос:

```http
POST /v1/publish HTTP/1.1
Host: 192.168.10.1
Content-Type: application/x-www-form-urlencoded

path=logs/morning.csv
```

- **Метод** — что сделать. `GET` не меняет станция, им снимают статус и списки. `POST` просит действие: вывести журнал, остановить, принять заливку.
- **Путь** — какой ручкой пользоваться. Ведущий слэш обязателен: `/v1/reading`, не `v1/reading`. Опечатка без слэша — отдельный маршрут, которого пульт не вызывает.
- **Заголовки** — метаданные. Для формы важен `Content-Type`. Для заливки файла это будет `multipart/form-data`, не JSON.
- **Тело** — сами данные. У `GET /v1/reading` тела нет.

Ответ устроен так же: код, заголовки, тело.

| Код | Смысл на станции | Что делает пульт |
| --- | --- | --- |
| 200 | Действие принято или статус снят | Читать тело |
| 400 | Запрос плохой: пустой путь, нет файла | Показать тело как причину, не повторять вслепую |
| 503 | Плата жива, но зависимость нет (карта) | Сказать человеку «SD недоступна», не «станция выключена» |

Тело status в этой архитектуре — короткий текст, не веб-страница:

```text
OK fw:0.9.0 board:esp32s3_dev
```

Поля `fw:` и `board:` потом читает обновление прошивки. Пока достаточно глазами увидеть `OK`.

Хендлер на плате тонкий. Он разбирает аргументы, вызывает одно действие и отвечает. Он не разбирает журнал и не ждёт минуту. Иначе `loop` не обслужит следующего клиента: HTTP на Arduino-`WebServer` живёт только пока `loop` вызывает `handleClient()`.

Один и тот же жест («стоп», «показать») могут принести HTTP из LAN и позже облако. Действие одно, транспорты разные. Если логика показа скопирована в два файла, вы почините кнопку и сломаете голос.

Проверка со стола, телефон ещё не нужен:

```bash
curl -sS -m 3 http://192.168.10.1/v1/reading
curl -sS -m 3 -X POST http://192.168.10.1/v1/publish \
  --data-urlencode "path=logs/morning.csv"
```

`-m 3` — не висеть вечно, если плата не в этой сети. Пустой вывод и «connection refused» — это не HTTP-код. Кода нет, когда нет соединения.

## Разбор на примере

Показать журнал, который уже лежит на карте:

1. Пульт собирает `POST /v1/publish` с полем `path`.
2. Плата читает поле, проверяет, что путь не пустой и файл есть.
3. Если нет — `400` и короткая причина (`empty`, `missing`).
4. Если да — запоминает путь, ставит флаг «надо играть», отвечает `200` и `OK`.
5. Кадры рисует цикл прошивки, не этот запрос.

Пока шага 5 нет, экран чёрный при честном `200`. Это уже не «HTTP не работает». Status и display разведены: первый доказывает связь, второй доказывает контракт команды.

Заливка файла — тот же HTTP, другое тело. Туда едут байты, имя, тип и CRC. Ответ исторически текстовый, с префиксом `SAVED:OK:`, а не объект. Путать его с JSON — отдельный урок.

## Упражнения

1. `curl` к status повесился на 3 секундах и оборвался по таймауту. Назовите два разных объяснения, которые ещё не требуют открывать Android Studio.
2. Пульт послал `POST /v1/publish` с пустым `path` и получил `400` с телом `empty`. Что показать человеку и почему повтор той же команды не поможет?
3. Зачем ведущий слэш в `server.on("/v1/reading", ...)` и что увидит пульт, если зарегистрировать `"v1/reading"`?

### Ориентир для самопроверки

Сначала запишите ответы своими словами. Короткий ключ к этим вопросам — [02-http.md](../hints/02-http.md). Откройте его после своей попытки и отметьте расхождения. Дословно в тетрадь ключ не переписывайте. К самостоятельной работе модуля этот ключ не относится: там решения в репозитории нет.

## Типичные ошибки

- Писать OkHttp, не открыв status в браузере.
- Считать любой ответ с телом успехом и игнорировать код 400/503.
- Класть тяжёлую работу (разбор журнала, `delay` на секунды) в хендлер. Клиент ждёт, остальные запросы стоят.
- Думать, что локальная станция обязан говорить HTTPS. На SoftAP в этом проекте — `http://` и порт 80. Из-за этого на Android 9+ отдельно разрешают cleartext. Это тема модуля 02, но корни здесь.
- Делать два разных «стопа»: один для кнопки, другой для облака. Расходятся в первую же неделю.
