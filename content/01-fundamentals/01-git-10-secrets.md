# Ключи, секреты, большие файлы, IDE

**Модуль:** 01. Фундамент  
**Время:** около 40 минут  
**Дальше:** [Вопросы с собеседования](01-git-11-interview.md)

## Цель

Пушить по SSH или по токену, не оставляя секрет в репозитории и в URL. Знать порядок действий, если секрет уже попал в коммит. Коротко понимать Git LFS. Находить те же операции в Android Studio и в Cursor.

## Зачем это вам

`station_key`, пароль Wi-Fi, ключ подписи APK и личный токен GitHub в истории живут дольше задачи. Частный репозиторий копируют на второй ноутбук, в бэкап и в лог CI. На собеседовании и на работе «я потом добавлю в gitignore» не считается ответом: секрет сначала гасят у того, кто его выдал, и только потом чистят историю.

## Теория

### SSH-ключ

Пара ключей: закрытый остаётся на машине, открытый кладут на GitHub. Для новой машины:

```text
$ ssh-keygen -t ed25519 -C "you@example.com"
```

Путь по умолчанию `~/.ssh/id_ed25519`. Парольную фразу на ключ задайте: она не уходит на сервер, она запирает файл на диске. Пустой фразы хватает только на одноразовой учебной виртуалке, которую вы удалите вечером.

На GitHub: Settings → SSH and GPG keys → New SSH key. Вставляют содержимое `id_ed25519.pub`, одну строку. Файл без `.pub` не вставляют и не коммитят.

Проверка:

```text
$ ssh -T git@github.com
Hi <login>! You've successfully authenticated, but GitHub does not provide shell access.
```

Такой ответ — успех. Remote тогда вида `git@github.com:you/station.git`.

Чужой ноутбук, старый ключ, увольнение: ключ удаляют из настроек GitHub. Закрытый файл на потерянной машине с этого момента бесполезен только после удаления открытой половины на сервере. Поэтому удаление из GitHub — часть действий, не «когда-нибудь».

### Токен вместо пароля

По HTTPS GitHub не принимает пароль от аккаунта. Нужен personal access token. Для одного репозитория хватает fine-grained token: срок жизни, право Contents на чтение и запись, без лишних прав на все организации.

Токен показывают один раз. Его кладут в менеджер учётных данных системы (Git Credential Manager на Windows, связка ключей на macOS), не в файл проекта и не в URL.

Плохой remote, его так и оставлять нельзя:

```text
https://ghp_пример@github.com/you/station.git
```

Строка попадает в `.git/config`, в историю оболочки и в скриншот. Нормальный адрес без секрета:

```text
https://github.com/you/station.git
```

Если токен засветился, его revoke в GitHub: Settings → Developer settings → Personal access tokens. Старый токен после revoke мёртв. Новый заводят отдельно. «Поправить URL» без revoke оставляет рабочий ключ от аккаунта тому, кто успел скопировать строку.

### Что не коммитят

| Файл или значение | Где ему жить |
| --- | --- |
| `.env`, пароль Wi-Fi, `station_key` | менеджер секретов, NVS на плате, переменные CI |
| `local.properties` | только эта машина, путь к Android SDK |
| `*.keystore`, `*.jks`, `key.properties` | хранилище подписи вне git, бэкап не в репозитории |
| закрытый SSH-ключ, token, `google-services.json` с прод-ключами, если в нём секрет продакшена | машина или консоль провайдера |
| `build/`, `.gradle/`, APK, дамп Serial | сборка заново, не история |

Пример `.env.example` коммитят: имена переменных без значений. Настоящий `.env` в ignore.

Проверка перед каждым `git add` в проекте Android: в `git status` нет `local.properties` и нет `.env`. Шаблон ignore заводят в первый день, не после утечки.

### Если секрет уже в коммите

Порядок не меняется местами.

1. **Погасить секрет у источника.** Пароль сменить, токен отозвать, ключ API перевыпустить, `station_key` на плате и в облаке заменить. Пока старое значение работает, красивая история не помогает: его уже видел каждый клон.
2. **Убрать секрет из рабочего дерева** и из следующего коммита. Ignore, `git rm --cached`, новый коммит. Это лечит только кончик.
3. **Считать историю грязной.** Старый снимок всё ещё содержит строку. Её найдут `git log -S 'ИМЯ_ПЕРЕМЕННОЙ' --all` и любой, кто клонировал репозиторий раньше.
4. **Переписать историю согласованно**, если репозиторий общий. Инструмент для этого — [git-filter-repo](https://github.com/newren/git-filter-repo), не ручное ковыряние `.git/objects`. Все, кто клонировал, после переписывания делают свежий клон. Старые вилки и форки GitHub могут хранить коммит, пока его не вычистят по запросу в поддержку и пока не протухнут кэши. Secret scanning в настройках GitHub как раз орёт о найденных токенах: письмо от него читают, не помечают прочитанным.
5. **Повторить шаг 1**, если между утечкой и переписыванием прошло время. Ротация уже должна была случиться в шаге 1. Переписывание её не заменяет.

В учебной песочнице можно один раз прогнать механику на фальшивке `SECRET=example-not-a-real-token`. Настоящий токен, пароль точки станца и ключ подписи в этот эксперимент не кладут. На общем `main` команды filter-repo без договорённости с теми, кто клонировал, устраивает всем сломанные ветки: SHA меняются целиком.

Команда по форме, только для песочницы, где фальшивка уже в истории и секрет ненастоящий:

```text
$ git filter-repo --replace-text ../replacements.txt
```

В `replacements.txt` строка `example-not-a-real-token==>***REMOVED***`. После этого remote надо добавить заново: filter-repo его отцепляет специально, чтобы вы не запушили случайно. Дальше `--force-with-lease` имеет смысл только если вы понимаете, что переписали все SHA. В учебном голом репозитории из прошлого урока проще запушить в новый bare, чем спорить со старым.

`git revert` секрет из старых коммитов не вырезает. Новый коммит «удалил .env» оставляет `.env` в родителе.

### Большие файлы и Git LFS

Git охотно хранит текст. Ролик, дамп карты и жирный бинарник прошивки на каждом коммите раздувают клон: их байты остаются в истории, даже если файл потом удалили.

Git LFS подменяет в репозитории короткую ссылку-указатель, а байты кладёт в отдельное хранилище.

```text
$ git lfs install
$ git lfs track "*.gif"
```

`track` дописывает `.gitattributes`. Этот файл коммитят вместе с указателями. Без установленного LFS клон получит текстовые указатели вместо роликов.

На GitHub у LFS есть квота. Туда не кладут секреты: хранилище не становится сейфом от того, что файл большой. Исходники Kotlin и C++ через LFS не проводят. Для станца кандидат — демо-ролик, который иначе нельзя показать. Прошивку, которую собирают из исходников, в LFS не дублируют на каждом вечернем коммите: её воспроизводят сборкой, а выпускной файл крепят к релизу тега, если он вообще нужен людям.

### Android Studio

Окно Commit (иконка галочки или Tool Windows → Commit) показывает те же три слоя: список файлов, diff, сообщение. Галочка на файле — это `git add`. Кнопка Commit — `git commit`. Commit and Push — ещё и push.

Перед кнопкой прочитайте список. IDE рада предложить `local.properties`, `.idea` с машинными путями и сгенерированный APK, если ignore их не закрыл. Diff в окне — тот же `git diff`.

Git → Branches создаёт и переключает ветки. Annotate with Git Blame на поле редактора — `git blame`. Merge и rebase в меню вызывают те же команды; конфликт открывается в редакторе с тремя панелями, а в файле всё равно появляются маркеры, если смотреть его с диска.

Встроенный терминал Android Studio использует системный Git. Если `git status` в терминале и список в окне Commit расходятся, нажмите обновить список. Расхождение надолго значит, что IDE смотрит не в тот каталог или не видит `git` в `PATH`.

### Cursor

Боковая панель Source Control — статус, сообщение, кнопка коммита, список файлов. Ветка переключается в статусной строке. Это тот же Git, не отдельное хранилище.

Агент в чате может предложить команды и сам сделать коммит, если его об этом попросили. Перед тем как согласиться, вы читаете diff так же, как в терминале: нет ли `.env`, нет ли «фикс» вместо поведения, не смешаны ли две задачи. `git add .` из подсказки агента не становится безопасным от того, что его написала модель.

Pull request из Cursor ходит на GitHub через ваши же права. Описание PR после агента перечитывают: контракт `/v1/reading` и способ проверки должны быть вашими словами, если агент их выдумал.

Ни Android Studio, ни Cursor не заменяют `git log --oneline --graph --all` в вечер, когда история разъехалась. Окно красиво показывает удачный день. Отказ pull, rebase и reflog быстрее читаются в терминале, и это те же команды из уроков.

## Разбор на примере

Учебная утечка на фальшивке, в `~/sandbox/git-course`, не в Ступенях и не с настоящим токеном.

```text
$ printf 'SECRET=example-not-a-real-token\n' > .env
$ git add .env
$ git commit -m "chore: случайно добавил секрет"
$ git log -S 'example-not-a-real-token' --oneline --all
```

Вторая команда находит коммит. Значит, строка в истории есть.

Дальше по порядку, как с настоящим секретом, только гасить у провайдера нечего: значение и так мёртвое.

```text
$ git rm --cached .env
$ printf '.env\n' >> .gitignore
$ git add .gitignore
$ git commit -m "chore: убрать .env из снимка"
$ printf 'SECRET=example-not-a-real-token\n' > .env
$ git status -sb
```

Новый `.env` на диске не предлагается к коммиту. Старый коммит `git log -S` всё ещё находит. Для песочницы этого достаточно, чтобы увидеть дыру. Переписывание всей истории делайте здесь только если поставили `git-filter-repo` и готовы добавить remote заново. На репозитории, где есть второй человек, сначала письмо «я перепишу SHA», потом инструмент, потом свежие клоны.

Настоящий порядок, если вместо фальшивки в коммите оказался боевой токен: revoke в GitHub в ту же минуту, затем шаги с ignore, затем договорённость про историю. Минута revoke важнее вечера с filter-repo.

Проверка SSH, если ключ уже добавлен:

```text
$ ssh -T git@github.com
$ git remote -v
```

В URL нет `ghp_` и нет пароля. Есть либо `git@github.com:`, либо `https://github.com/` без учётных данных в строке.

## Упражнения

1. Где лежит открытый ключ, который можно вставить в GitHub, и где лежит закрытый, который туда не вставляют. Что даёт парольная фраза на ключ, если ноутбук украли до того, как вы удалили ключ в настройках GitHub.
2. Токен оказался в URL remote. Назовите два места, где его надо убить: на стороне GitHub и в своём клоне. Почему новый коммит «убрал URL» сам по себе токен не гасит.
3. В `git log -S` фальшивка находится, `.gitignore` уже содержит `.env`, кончик дерева чистый. Можно ли отдать этот репозиторий коллеге и сказать, что секрета нет? Что сказать вместо этого, если строка была настоящим паролем.
4. Чем байты файла в Git LFS отличаются от обычного blob для человека, который клонирует репозиторий без `git lfs`. Почему ключ подписи APK в LFS не кладут.

### Ориентир для самопроверки

Сначала запишите ответы своими словами. Короткий ключ — [01-git-10-secrets.md](../hints/01-git-10-secrets.md). В приложении нажмите на эту ссылку: откроется ключ, без отметки «изучил». Откройте его после своей попытки. Дословно в тетрадь ключ не переписывайте.

## Типичные ошибки

- Коммитить `.env`, потому что репозиторий частный.
- Вставлять на GitHub файл `id_ed25519` без `.pub`.
- Хранить токен в remote URL «чтобы не спрашивало пароль».
- Начинать с переписывания истории, пока старый токен ещё действует.
- `git revert` как способ «стереть секрет из всех снимков».
- Тащить в LFS каталог `build/` и ключи.
- Жать Commit в Android Studio, не просмотрев галочки на файлах.
- Принимать коммит агента в Cursor с сообщением `фикс` и лишним `.env`.
