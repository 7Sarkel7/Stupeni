# JSON и текст, который JSON не является

**Модуль:** 01. Фундамент  
**Время:** около 25 минут  
**Дальше:** [Отладка слоями](04-debug.md)

## Цель

Различать три формата станции: форма `key=value`, строка с префиксом `SAVED:OK:`, объект JSON. Собирать и читать объект команды облака. Не отдавать модели голосового помощника право выдумывать произвольный URL (адрес ресурса в интернете).

## Зачем это вам

В одном проекте легко решить, что «всё структурированное — это JSON». У станции это не так. Локальный публикация журнала — форма. Успех заливки — текст с префиксом. Команда из облака — JSON. Парсер (код, который разбирает строку, например JSON, на понятные программе части; сам разбор называют парсингом) не того формата даёт пустую ошибку, похожую на обрыв сети: исключение в `JSONObject`, хотя плата ответила честно.

## Теория

JSON — текст с жёсткой грамматикой. Объект в фигурных скобках, массив в квадратных, строки в двойных кавычках, числа и `true`/`false`/`null` без кавычек. Запятая после последнего элемента запрещена.

Команда, которую облако несёт на плату, выглядит так:

```json
{
  "command": "display",
  "request_id": "8f3a",
  "payload": {
    "path": "logs/morning.csv"
  }
}
```

`command` — имя из белого списка (`publish`, `idle`, `play_audio`, …). `payload` — аргументы именно этой команды. `request_id` нужен, чтобы подтверждение (`ack`) попало в тот запрос телефона, который ждёт, а не в соседний.

Это не то же самое, что локальный показ:

```text
path=logs/morning.csv
```

Здесь нет фигурных скобок. Заголовок `application/x-www-form-urlencoded`. На плате поле читают как аргумент формы (`server.arg("path")`), не как JSON.

И не то же самое, что ответ заливки:

```text
SAVED:OK:/logs/sample.csv:1840
```

Префикс, путь, размер. Режется строками. `JSONObject` на этой строке бросит исключение, хотя HTTP-код был 200. Успех заливки определяется префиксом и сверкой CRC (контрольная сумма, по которой проверяют, что данные не испортились), не ключом `"ok"`.

Голос добавляет ещё один объект, уже на телефоне и сервере, не на ESP:

```json
{
  "speak": "Показываю закат",
  "cue": "beep",
  "actions": [
    { "command": "display", "args": { "path": "logs/morning.csv" } }
  ]
}
```

Модель переводит фразу в уже существующие команды. Она не придумывает новую команду `format_sd`. Список разрешённых имён проверяют до того, как что-то уедет на плату. `cue` — имя короткого файла на карте (`cues/beep.wav`), не «синтезировать звук на микроконтроллере».

Практические правила чтения:

- Сначала посмотрите на первый непробельный символ. `{` или `[` — имеет смысл звать JSON-парсер. `DONE:` — режьте строку. `OK fw:` — статус текстом.
- Не ловите все исключения сети и парсинга одним пустым `catch`. Человеку нужны разные фразы: «станция не ответила» и «ответ не того формата».
- Числа и строки не взаимозаменяемы. `"factor": "2"` и `"factor": 2` для строгого парсера — разное. Договоритесь в одном месте и держитесь.
- Белый список команд важнее красивого промпта. Нет имени в списке — команда не едет на станцию, в журнал пишется отказ.

ESP32 в локальном API (набор правил, по которым одна программа обращается к другой) не обязан говорить JSON на каждом маршруте. Ретрофит и Gson живут на телефоне. Плата собирает строку и отдаёт её с честным `Content-Type`: `text/plain` или `application/json`, если тело и правда объект (например список файлов).

## Разбор на примере

Телефон залил маленький текстовый файл и получил:

```text
HTTP/1.1 200 OK
Content-Type: text/plain

SAVED:OK:/logs/note.csv:12
```

Разбор на Kotlin, без JSON:

```kotlin
fun parseUploadAck(body: String): String {
    require(body.startsWith("SAVED:OK:")) { "не ack заливки: $body" }
    val rest = body.removePrefix("SAVED:OK:")
    val path = rest.substringBeforeLast(':')
    return path
}
```

Тот же вечер, облако прислало на плату объект `publish`. Прошивка не строит второй декодер. Она достаёт `payload.path` и вызывает ту же функцию, что и `POST /v1/publish`. Формат транспорта другой, действие одно.

Если модель вернула `actions` с `command`, которого нет в списке, реле эту запись выбрасывает. В `speak` можно сказать, что команда не распознана. На SD ничего не форматируется.

## Упражнения

1. Даны три тела: `OK fw:0.9.0 board:esp32s3_dev`, `SAVED:OK:sample.csv:100`, `{"command":"idle","request_id":"1","payload":{}}`. Какой парсер к какому телу?
2. Почему поле `request_id` есть в облачной команде и не нужно в форме `POST /v1/publish` по LAN (локальная сеть в пределах дома или офиса)?
3. Модель прислала `{"command":"format_sd"}`. Что делает сервер, если такого имени нет в белом списке, даже если JSON синтаксически верный?

## Типичные ошибки

- Обернуть все ответы станции в `JSONObject`.
- Послать на `/v1/publish` сырой JSON и ждать, что `server.arg("path")` его поймёт. Поле формы и объект — разные тела.
- Доверять модели произвольную строку URL.
- Ловить `JSONException` и показывать «нет связи со станцией».
- Хранить в JSON пароль Wi-Fi «потому что так удобно логировать» (лог — журнал, куда программа записывает, что делает). В лог и в git секреты не пишут (урок 01).
