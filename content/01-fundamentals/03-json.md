# JSON и текст, который JSON не является

**Модуль:** 01. Фундамент  
**Время:** около 25 минут  
**Дальше:** [Отладка слоями](04-debug.md)

## Цель

Различать три формата станца: форма `key=value`, строка с префиксом `SAVED:OK:`, объект JSON. Собирать и читать объект команды облака. Не отдавать модели голосового помощника право выдумывать произвольный URL.

## Зачем это вам

В одном проекте легко решить, что «всё структурированное — это JSON». У станца это не так. Локальный показ файла — форма. Успех заливки — текст с префиксом. Команда из облака — JSON. Парсер не того формата даёт пустую ошибку, похожую на обрыв сети: исключение в `JSONObject`, хотя плата ответила честно.

## Теория

JSON — текст с жёсткой грамматикой. Объект в фигурных скобках, массив в квадратных, строки в двойных кавычках, числа и `true`/`false`/`null` без кавычек. Запятая после последнего элемента запрещена.

Команда, которую облако несёт на плату, выглядит так:

```json
{
  "command": "display",
  "request_id": "8f3a",
  "payload": {
    "path": "photos/sunset.gif"
  }
}
```

`command` — имя из белого списка (`display`, `stop`, `play_audio`, …). `payload` — аргументы именно этой команды. `request_id` нужен, чтобы подтверждение (`ack`) попало в тот запрос телефона, который ждёт, а не в соседний.

Это не то же самое, что локальный показ:

```text
path=photos/sunset.gif
```

Здесь нет фигурных скобок. Заголовок `application/x-www-form-urlencoded`. На плате поле читают как аргумент формы (`server.arg("path")`), не как JSON.

И не то же самое, что ответ заливки:

```text
SAVED:OK:/logs/clip.gif:842311
```

Префикс, путь, размер. Режется строками. `JSONObject` на этой строке бросит исключение, хотя HTTP-код был 200. Успех заливки определяется префиксом и сверкой CRC, не ключом `"ok"`.

Голос добавляет ещё один объект, уже на телефоне и сервере, не на ESP:

```json
{
  "speak": "Показываю закат",
  "person": "dance",
  "actions": [
    { "command": "display", "args": { "path": "photos/sunset.gif" } }
  ]
}
```

Модель переводит фразу в уже существующие команды. Она не придумывает новый маршрут `/api/format-sd`. Список разрешённых имён проверяют до того, как что-то уедет на плату. `person` — имя ролика из гардероба на карте (`person/dance.gif`), не «сгенерировать видео на микроконтроллере».

Практические правила чтения:

- Сначала посмотрите на первый непробельный символ. `{` или `[` — имеет смысл звать JSON-парсер. `DONE:` — режьте строку. `OK fw:` — статус текстом.
- Не ловите все исключения сети и парсинга одним пустым `catch`. Человеку нужны разные фразы: «станц не ответил» и «ответ не того формата».
- Числа и строки не взаимозаменяемы. `"factor": "2"` и `"factor": 2` для строгого парсера — разное. Договоритесь в одном месте и держитесь.
- Белый список команд важнее красивого промпта. Нет имени в списке — команда не едет на станц, в журнал пишется отказ.

ESP32 в локальном API не обязан говорить JSON на каждом маршруте. Ретрофит и Gson живут на телефоне. Плата собирает строку и отдаёт её с честным `Content-Type`: `text/plain` или `application/json`, если тело и правда объект (например список файлов).

## Разбор на примере

Телефон залил маленький текстовый файл и получил:

```text
HTTP/1.1 200 OK
Content-Type: text/plain

SAVED:OK:/logs/note.txt:12
```

Разбор на Kotlin, без JSON:

```kotlin
fun parseUploadAck(body: String): String {
    require(body.startsWith("SAVED:OK:")) { "не ack заливки: $body" }
    val rest = body.removePrefix("SAVED:OK:")
    val path = rest.substringBeforeLast(':')
    return path
}
```

Тот же вечер, облако прислало на плату объект `display`. Прошивка не строит второй декодер. Она достаёт `payload.path` и вызывает ту же функцию, что и `POST /api/display`. Формат транспорта другой, действие одно.

Если модель вернула `actions` с `command`, которого нет в списке, реле эту запись выбрасывает. В `speak` можно сказать, что команда не распознана. На SD ничего не форматируется.

## Упражнения

1. Даны три тела: `OK fw:1.2.0 board:esp32s3_dev`, `SAVED:OK:a.gif:100`, `{"command":"stop","request_id":"1","payload":{}}`. Какой парсер к какому телу?
2. Почему поле `request_id` есть в облачной команде и не нужно в форме `POST /api/display` по LAN?
3. Модель прислала `{"command":"format_sd"}`. Что делает сервер, если такого имени нет в белом списке, даже если JSON синтаксически верный?

### Ориентир для самопроверки

1. Статус — разбор префиксов `OK`, `fw:`, `model:`. Заливка — префикс `SAVED:OK:` и `substring`. Облако — JSON-парсер.
2. В LAN один запрос — один ответ HTTP, путать не с чем. Через облако ответов и команд несколько, подтверждение должно попасть в конкретное ожидание по идентификатору.
3. Команда не уходит на плату. Синтаксис JSON не равен разрешению. Человеку или полю `speak` — отказ, не тихий `eval`.

## Типичные ошибки

- Обернуть все ответы станца в `JSONObject`.
- Послать на `/api/display` сырой JSON и ждать, что `server.arg("path")` его поймёт. Поле формы и объект — разные тела.
- Доверять модели произвольную строку URL.
- Ловить `JSONException` и показывать «нет связи с станцом».
- Хранить в JSON пароль Wi-Fi «потому что так удобно логировать». В лог и в git секреты не пишут (урок 01).
