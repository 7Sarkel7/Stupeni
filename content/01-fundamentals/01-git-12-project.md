# Практика: командный вечер

**Модуль:** 01. Фундамент  
**Время:** около 90 минут  
**Дальше:** [HTTP без тумана](02-http.md)

## Цель

В отдельном репозитории пройти путь задачи так, будто вас двое. Завести ветки, получить и собрать конфликт, склеить черновики интерактивным rebase, открыть pull request, закрыть замечание новым коммитом и пометить выпуск тегом.

## Зачем это вам

По отдельности команды уже запускались. Вместе они путаются: rebase делают после чужого merge не той стороной, в PR правят amend-ом комментарий ревьюера, тег забывают отправить. Этот вечер — один сюжет. Готового репозитория в Ступенях нет: иначе вы прочитаете чужой граф и не соберёте свой.

Песочница живёт в `~/sandbox/team-station`. Не в каталоге Ступеней и не в клоне учебника. Личный PR в Ступени с этим заданием не открывают.

## Теория

Сюжет. Вы и «коллега» меняете `status.txt` станции. Коллега успевает влить в `main` поле `board` и другой таймаут. Вы на ветке `feature/timeout` набрали три черновых коммита про 800 мс. Дальше по порядку, которым это переживает команда, а не по алфавиту команд:

1. Свежий `main` коллеги уже на сервере.
2. Вы перекладываете свою ветку rebase-ом и в конфликте оставляете и 800 мс, и `board`.
3. Пока ветку на сервере не смотрели, склеиваете три коммита в один.
4. Пушите и открываете PR. В описании — поведение и проверка.
5. Замечание ревью закрываете новым коммитом, без amend.
6. Вливаете договорённым способом и ставите аннотированный тег `v0.1.0` на получившийся `main`.

Почему rebase раньше пуша. Интерактивная склейка меняет SHA. До первого push это никого не ломает. После ревью новый коммит как раз не склеивают молча: обсуждение ссылается на старые SHA.

Почему конфликт не лечится `--ours`. Во время rebase верхний блок — свежий `main` коллеги. Нижний — ваш патч. Станции нужны обе мысли. Слепой выбор одной стороны выкинет либо таймаут опыта, либо поле board.

Два способа завести сервер. Команды Git дальше одинаковые.

**GitHub.** Создайте пустой репозиторий без README, чтобы не спорить с первым коммитом. Адрес вида `git@github.com:<вы>/team-station.git` или HTTPS без токена в URL. PR, комментарий к строке и Release делаются здесь по-настоящему. Это основной путь, если аккаунт уже есть.

**Голый репозиторий на диске**, если сети или аккаунта вечером нет. Он заменяет сервер для веток, конфликта, rebase и тега. Страницу PR он не откроет: описание PR пишете в файл `pr.md` и честно помечаете, что GitHub не открывали. Механика команд при этом настоящая. В следующий вечер с сетью тот же сюжет можно повторить на GitHub, уже быстрее.

Второго человека играет второй клон. Коммиты коллеги вы делаете сами, другим каталогом. Смысл не в актёрстве, а в том, что объекты приходят с remote, а не правятся «на месте» в одном дереве без fetch.

## Разбор на примере

Подставьте свой адрес GitHub вместо пути bare, если идёте основным путём. Имя ветки и тексты файлов оставьте: по ним устроен конфликт.

### 1. Сервер и первый снимок

Голый репозиторий. Вторая команда переводит его головную ветку на `main`. Без неё голый репозиторий ждёт `master`: `git clone` не выпишет файлы, а push коллеги в `main` разойдётся с пустой историей.

```text
$ git init --bare ~/sandbox/team-remote.git
$ git --git-dir ~/sandbox/team-remote.git symbolic-ref HEAD refs/heads/main
$ mkdir -p ~/sandbox/team-station
$ cd ~/sandbox/team-station
$ git init -b main
$ git remote add origin ~/sandbox/team-remote.git
```

Или пустой репозиторий на GitHub:

```text
$ mkdir -p ~/sandbox/team-station
$ cd ~/sandbox/team-station
$ git init -b main
$ git remote add origin git@github.com:<вы>/team-station.git
```

Первый коммит, в нём ещё нет спора:

```text
$ printf 'fw:1.0.0\ntimeout_ms:1500\n' > status.txt
$ printf '# Учебная станция\n\nПесочница модуля Git. Это не репозиторий Ступеней.\n' > README.md
$ printf '.env\nlocal.properties\n' > .gitignore
$ git add status.txt README.md .gitignore
$ git commit -m "feat: первая строка status"
$ git push -u origin main
```

### 2. Коллега вливает model

```text
$ git clone ~/sandbox/team-remote.git ~/sandbox/team-colleague
```

На GitHub клонируйте тот же URL в `~/sandbox/team-colleague`.

```text
$ cd ~/sandbox/team-colleague
$ printf 'fw:1.0.0\ntimeout_ms:3000\nboard:esp32s3_dev\n' > status.txt
$ git add status.txt
$ git commit -m "feat: в status есть model платы"
$ git push origin HEAD:main
```

`HEAD:main` пишет текущий коммит в `main` на сервере, даже если вы забыли имя локальной ветки. На GitHub это обычный push в `main` учебного репозитория. В боевом защищённом `main` так уже не пушат, для сюжета коллега как раз тот, у кого право есть.

### 3. Ваша ветка с тремя черновиками

Вернитесь в первый клон. Не обновляйте его `main` до создания ветки: `feature/timeout` должна вырасти из старого снимка, иначе строка коллеги уже будет вашей базой и конфликта не получится.

```text
$ cd ~/sandbox/team-station
$ git switch -c feature/timeout
$ printf 'fw:1.0.0\ntimeout_ms:800\n' > status.txt
$ git add status.txt
$ git commit -m "wip"
$ printf '\nПауза.\n' >> README.md
$ git add README.md
$ git commit -m "wip2"
$ printf '\nПауза ping.\n' >> README.md
$ git add README.md
$ git commit -m "fix: timeout ping 800 мс"
$ git log --oneline main..HEAD
```

Три коммита. `status.txt` на ветке без строки `board`: коллегу вы ещё не забирали.

### 4. Rebase и конфликт

```text
$ git fetch origin
$ git rebase origin/main
```

Ожидаемый отказ применить первый коммит:

```text
CONFLICT (content): Merge conflict in status.txt
error: could not apply ... wip
```

Откройте `status.txt`. Верхний блок `<<<<<<< HEAD` — коллега, `timeout_ms:3000` и `board`. Нижний — ваш `800`. Соберите файл без маркеров:

```text
fw:1.0.0
timeout_ms:800
board:esp32s3_dev
```

```text
$ git add status.txt
$ git rebase --continue
```

Редактор может спросить сообщение коммита `wip`. Сохраните и закройте. Коммиты README должны лечь следом. Если rebase снова остановится, прочитайте `git status`, не вызывайте `--skip`, пока не поняли, какой коммит пропускаете. Бросить попытку и вернуться к трём исходным коммитам: `git rebase --abort`.

Проверка дерева:

```text
$ git diff origin/main...HEAD
```

В diff есть смена таймаута на 800 и нет строки `board` как удаления: модель пришла с базы и в вашем дереве остаётся. Файл на диске содержит обе строки.

### 5. Интерактивный rebase

Коммиты уже новые, их по-прежнему три поверх `origin/main`:

```text
$ git rebase -i origin/main
```

В списке сверху самый старый. Поставьте:

```text
pick <первый> wip
fixup <второй> wip2
squash <третий> fix: timeout ping 800 мс
```

Сохраните. На squash Git откроет все три сообщения подряд. Первую строку замените целиком: если оставить `wip`, в истории так и будет `wip`, даже когда тело уже длинное. Нужен один такой текст:

```text
feat: timeout ping 800 мс

Поле model со свежего main сохранено.
Пауза короче дефолтных 1500, это опыт ветки.
```

```text
$ git log --oneline --graph --decorate origin/main..HEAD
```

Одна строка коммита, не три. Если список редактора напугал и вы вышли пустым файлом, rebase отменился сам: повторите команду. Если склейка вышла кривой и на сервер вы ещё не пушили, `git reflog` покажет SHA до `rebase -i`, ветку можно вернуть `git reset --hard` на тот SHA.

### 6. Pull request

```text
$ git push -u origin feature/timeout
```

На GitHub откройте Draft pull request в `main`. Текст:

```text
feat: timeout ping 800 мс

Поведение: в status.txt таймаут опыта 800, поле model коллеги на месте.
Проверка: git diff origin/main...HEAD без маркеров конфликта, файл status.txt содержит обе строки.
Вне PR: прошивка на флеш, секреты, правки Ступеней.
```

Затем Ready for review. Без GitHub создайте в репозитории файл `pr.md` с тем же текстом и первой строкой `GitHub вечером не открывал`. Закоммитьте его отдельным коммитом на ветке и запушьте в свой bare. Это честная замена страницы, не настоящий PR.

### 7. Замечание ревью

Замечание, которое вы оставляете сами на строке README или записываете в `pr.md`: «не сказано, зачем 800, а не 3000 коллеги».

Не amend. Новый коммит:

```text
$ printf '\n800 мс — опыт ветки. 3000 коллеги в этот выпуск не берём.\n' >> README.md
$ git add README.md
$ git commit -m "docs: почему timeout 800, а не 3000"
$ git push
```

Обычный push, не force: склейка была до первого пуша, этот коммит к ней не относится. На GitHub закройте тред комментария. В графе ветки теперь два коммита поверх `main`: склейка и docs.

### 8. Вливание и тег

На GitHub влейте PR. Для этой задачи уместен squash, если описание PR уже хорошее, или merge commit, если хотите видеть оба коммита. Выберите один способ и в тетради запишите, какой граф ждёте.

Локальный `main` к этому моменту отстаёт от сервера на коммит коллеги. Сначала догоните его, потом смотрите граф. Иначе узел слияния сядет на старый снимок, а коммит с `model` окажется сбоку, хотя на сервере он уже был в `main`.

```text
$ git switch main
$ git pull --ff-only
$ git log --oneline --graph --decorate -8
```

Без GitHub сольёте сами в `~/sandbox/team-station` после того же `git pull --ff-only`. Один из способов, не оба.

Узел слияния, его хорошо видно на учебном графе:

```text
$ git merge --no-ff feature/timeout -m "merge: timeout 800 мс и поле model"
$ git push origin main
```

Squash без GitHub, одна фраза на `main`:

```text
$ git merge --squash feature/timeout
$ git commit -m "feat: timeout ping 800 мс" -m "Поле model сохранено. Заметка в README объясняет 800."
$ git push origin main
```

Запишите, какой выполнили. Если `--ff-only` отказал, на локальном `main` есть ваш лишний коммит. Не продолжайте merge, пока не поймёте, чей он: сюжет рассчитан на чистый fast-forward к коммиту коллеги.

Тег на коммите, который теперь кончик `main`:

```text
$ git tag -a v0.1.0 -m "Учебный выпуск: timeout 800 мс, в status есть model."
$ git push origin v0.1.0
$ git show v0.1.0 --stat
```

На GitHub из этого тега можно собрать Release с теми же двумя предложениями. В bare хватает тега: `git --git-dir ~/sandbox/team-remote.git show v0.1.0 --stat`.

Второй клон коллеги после `git fetch` и `git pull` видит тот же тег и тот же `status.txt`. Если не видит, тег не запушен или pull смотрел не в тот remote.

### Чем вечер отличается от работы

В боевом `main` коллега не пушит напрямую, если ветка защищена: у него тоже PR. Force вы здесь не использовали. Секрет в коммиты не клали, строка `.env` в ignore на месте. Флеш станции этот тег сам не прошивает.

## Упражнения

Сюжет выше и есть работа. Письменно ответьте после того, как команды прошли.

1. Вставьте вывод `git log --oneline --graph --decorate -8` с `main` и вывод `git show v0.1.0 --stat`. Одной фразой: fast-forward это был, merge-коммит или squash.
2. Почему в конфликте rebase вы не взяли `--ours` целиком. Какое число таймаута оказалось бы в файле.
3. Замечание ревью уже висело на запушенном коммите. Что сломается у обсуждения, если вместо `docs:` сделать amend и `--force-with-lease`.
4. Назовите файл, который вы проверили командой `git status` перед последним push, чтобы убедиться, что `.env` не попал в снимок. Если GitHub не открывали, где лежит текст, который заменяет описание PR.

### Ориентир для самопроверки

Сначала дойдите до тега своими командами. Короткий ключ к вопросам и к виду результата — [01-git-12-project.md](../hints/01-git-12-project.md). В приложении нажмите на эту ссылку: откроется ключ, без отметки «изучил». Откройте его после своей попытки. Это не скрипт, который проходит сюжет за вас, и не решение самостоятельной работы всего модуля про вечер станции.

### Рубрика

| Часть | 0 | 1 | 2 |
| --- | --- | --- | --- |
| Конфликт | маркеры остались или пропала `model` либо ваш таймаут | файл собран, в графе не видно, что был rebase | в `status.txt` и 800, и `board`, rebase был до склейки |
| История | три `wip` так и запушены | склейка есть, сообщения пустые | один осмысленный `feat` до ревью и отдельный `docs` после |
| PR | нет текста | текст есть, не сказано, как проверить | поведение, проверка, явная пометка, если вместо GitHub файл `pr.md` |
| Тег | нет тега | тег только локальный | аннотированный `v0.1.0` есть на remote, `git show` открывает сообщение |

Вечер сдан, когда нет нулей. Двойка по конфликту обязательна: без неё остальное можно случайно получить на одной ветке.

## Типичные ошибки

- Делать песочницу внутри Ступеней.
- Сначала pull `main` в свой каталог, потом ветку от уже нового коммита коллеги: конфликта не будет, сюжет развалится.
- `git rebase --skip` на первом конфликте: коммит с 800 исчезнет.
- Amend по замечанию ревью.
- `--force` «на всякий случай» при последнем push.
- Тег создать и не запушить.
- Пометить тегом старый коммит до вливания и считать, что выпущен `main`.

## Чеклист

- [ ] Каталог `~/sandbox/team-station` не лежит внутри Ступеней.
- [ ] Был конфликт в `status.txt`, маркеров в коммите нет.
- [ ] Интерактивный rebase склеил черновики до PR.
- [ ] Замечание закрыто коммитом `docs:`.
- [ ] `v0.1.0` аннотированный и виден на remote.
- [ ] В истории нет `.env` и нет настоящего токена.
