# Как Git помнит работу

**Модуль:** 01. Фундамент  
**Время:** около 40 минут  
**Дальше:** [Установка, настройка, init и clone](01-git-02-setup.md)

## Цель

Понять, что именно Git сохраняет, когда вы делаете коммит (сохранённый в Git снимок изменений с подписью). Уметь назвать три места, где лежит файл: рабочее дерево, индекс и история. По SHA и по `HEAD` сказать, на какой снимок вы сейчас смотрите.

## Зачем это вам

Пульт и прошивка станции ломаются по очереди. Вечером после смены вы не вспомните, какой таймаут (предельное время ожидания ответа, после которого ожидание обрывают) ещё отвечал на `/v1/reading`. Коммит — это подписанный снимок проекта, к которому можно вернуться. На работе от джуна (джун, junior — разработчик начального уровня) и мидла (мидл, middle — разработчик среднего уровня, который сам ведёт задачу до конца) ждут то же самое: не «я где-то правил», а «вот снимок, вот его хеш, вот ветка, на которую смотрит HEAD».

Git — программа на вашем компьютере. GitHub — сайт, где такие репозитории ещё и лежат удалённо. Пока вы не понимаете снимки, кнопки GitHub и окно Android Studio делают вид, что сохраняют «файлы», и прячут, что именно уедет в историю.

Справочник рядом с уроком, не вместо него: [Pro Git, глава про основы](https://git-scm.com/book/ru/v2/%D0%92%D0%B2%D0%B5%D0%B4%D0%B5%D0%BD%D0%B8%D0%B5-%D0%9E%D1%81%D0%BD%D0%BE%D0%B2%D1%8B-Git) и [git-scm.com/docs](https://git-scm.com/docs). Текст книги в урок не перенесён.

## Теория

Система контроля версий хранит историю проекта: что изменилось, кто это записал и как вернуться к старой версии. Git — распределённая система. Полная история лежит в каждом клоне (полная копия репозитория с историей на вашем компьютере), а не только на сервере. Поэтому `git log` работает в поезде без сети, а сервер нужен, когда историю надо отправить другим.

### Снимок, а не «папка с дельтами»

Коммит — снимок всего проекта в этот момент. У коммита есть дерево файлов. Если файл не менялся, новый коммит указывает на уже сохранённое содержимое, а не копирует байты второй раз. На диске Git потом ещё сжимает похожие объекты в pack-файлы. Для работы вам нужна модель снимка: «вот проект целиком на коммите `a1b2c3d`», а не «где-то лежит цепочка заплаток, которую надо проиграть с понедельника».

Внутри объектной базы три вида объектов, которые стоит узнавать:

| Объект | Что это |
| --- | --- |
| blob | Содержимое одного файла, без имени |
| tree | Папка: имена файлов и ссылки на blob и вложенные tree |
| commit | Снимок: ссылка на tree, родители, автор, дата, сообщение |

Имя файла живёт в дереве. Содержимое живёт в blob. Поэтому переименование без правки текста — дешёвая операция для Git: меняется дерево, blob тот же.

### Три места одного файла

```text
рабочее дерево              индекс                   история
файлы на диске              снимок «к коммиту»       коммиты в .git

status.txt                  status.txt               C2  parent: C1
timeout_ms:800   git add    timeout_ms:800  commit   tree: ...
(уже другая                 (ещё 1500, если          сообщение
 правка после add)           вы не добавляли)
```

1. **Рабочее дерево** — каталог проекта, как его видит редактор. Сюда вы пишете `timeout_ms:800`.
2. **Индекс** (его же называют staging area, область подготовки) — снимок, который попадёт в следующий коммит. Туда файл попадает командой `git add`. После `git add` вы можете снова править файл на диске: в индекс сама правка не переедет.
3. **Коммит** — записанный снимок плюс сообщение и ссылка на родительский коммит. Он лежит в каталоге `.git` и не меняется. Новый коммит — новый объект.

Пока вы не сделали `git add`, правка есть только на диске. Пока не сделали `git commit`, отмеченная правка есть в индексе и ещё не в истории.

### SHA

У каждого коммита есть идентификатор: хеш содержимого объекта. В обычном репозитории это SHA-1, 40 шестнадцатеричных символов. В командах хватает короткого префикса, обычно 7–12 символов, если он один такой в репозитории.

В хеш входят дерево файлов, список родителей, автор, коммитер, даты и сообщение. Поменяли сообщение или одну строку файла — это уже другой коммит с другим SHA. Старый объект при этом не «редактируется». Поэтому история Git похожа на цепочку, где каждое звено знает родителя, и подменить середину незаметно нельзя: дети ссылаются на точный SHA родителя.

Первый коммит в репозитории родителей не имеет. Обычный коммит имеет одного. Коммит слияния (мерж — слияние, то есть объединение изменений одной ветки Git с другой) имеет двух и больше: об этом отдельный урок про ветки.

### HEAD и ветка

`HEAD` — указатель «где я сейчас». В обычной работе он указывает на ветку, а ветка указывает на последний коммит этой линии.

```text
.git/HEAD
  ref: refs/heads/main

refs/heads/main
  a1b2c3d

    C1 ---- C2 ---- C3
                    ^
                   main
                   HEAD
```

Ветка — подвижное имя коммита, не отдельная копия папки. `main` и `experiment/ping-retry` могут указывать на один и тот же снимок, пока вы не сделаете новый коммит. После коммита вперёд двигается та ветка, на которую смотрит `HEAD`.

Иногда `HEAD` смотрит прямо на коммит, мимо ветки. Это detached HEAD: снимок открыт, но новой ветки под новые коммиты нет. Как из этого выбираться — в уроке про откат. Сейчас достаточно узнавать состояние по фразе `HEAD detached at`.

Проверить, куда смотрит указатель:

```text
$ git rev-parse --abbrev-ref HEAD
main

$ git rev-parse HEAD
a1b2c3d4e5f6789012345678901234567890abcd
```

Первая команда печатает имя ветки. В detached HEAD она печатает `HEAD`. Вторая всегда печатает полный хеш текущего коммита.

### Что лежит в `.git`

Каталог `.git` и есть репозиторий: объекты, ссылки веток (`refs/heads`), `HEAD`, настройки, журнал `logs`, по которому работает reflog (личный журнал Git, где записаны ваши перемещения по истории; с его помощью можно вернуть «потерянные» коммиты). Папка с исходниками без `.git` — просто файлы. Удалить `.git` значит удалить историю, даже если `status.txt` на месте.

Руками файлы в `.git/objects` не правят. Смотреть объект можно командой, которая его распакует:

```text
$ git cat-file -t HEAD
commit

$ git ls-tree --name-only HEAD
status.txt
```

`cat-file -t` говорит тип объекта. `cat-file -p` печатает содержимое. `ls-tree` показывает дерево снимка: какие файлы в него входили.

## Разбор на примере

Песочница для уроков Git — отдельный каталог, не репозиторий Ступеней. Вложенный `git init` внутри Ступеней смешает учебный мусор с учебником.

```text
$ mkdir -p ~/sandbox/git-course
$ cd ~/sandbox/git-course
$ git init -b main
Initialized empty Git repository in /home/you/sandbox/git-course/.git/

$ printf 'fw:1.0.0\ntimeout_ms:1500\n' > status.txt
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	status.txt

nothing added to commit but untracked files present
```

Файл есть в рабочем дереве. В индексе его нет, коммитов нет, `HEAD` указывать не на что.

```text
$ git add status.txt
$ git status
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   status.txt

$ git diff
$ git diff --staged
diff --git a/status.txt b/status.txt
new file mode 100644
index 0000000..c3d4e5f
--- /dev/null
+++ b/status.txt
@@ -0,0 +1,2 @@
+fw:1.0.0
+timeout_ms:1500
```

`git diff` без флага сравнивает рабочее дерево с индексом: после `git add` и без новой правки он пустой. `git diff --staged` сравнивает индекс с последним коммитом. Коммита ещё нет, поэтому видно весь новый файл. Это и есть содержимое будущего снимка.

```text
$ git commit -m "feat: первая строка status станции"
[main (root-commit) a1b2c3d] feat: первая строка status станции
 1 file changed, 2 insertions(+)
 create mode 100644 status.txt

$ git cat-file -p HEAD
tree 9f3a1c2e4b5d678901234567890123456789abcd
author Вы <you@example.com> 1763460000 +0300
committer Вы <you@example.com> 1763460000 +0300

feat: первая строка status станции

$ git status
On branch main
nothing to commit, working tree clean
```

У корневого коммита нет строки `parent`. Дерево, автор и сообщение вошли в объект. `HEAD` смотрит на `main`, `main` смотрит на `a1b2c3d`.

Поправьте таймаут и не добавляйте его:

```text
$ printf 'fw:1.0.0\ntimeout_ms:800\n' > status.txt
$ git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   status.txt

$ git rev-parse --short HEAD
a1b2c3d
```

Хеш текущего коммита тот же. Правка живёт в рабочем дереве. В следующий снимок она попадёт только после `git add` и нового `git commit`. У того коммита будет родитель `a1b2c3d` и другой SHA.

## Упражнения

Делайте в `~/sandbox/git-course`, не в каталоге Ступеней. Команды ниже предполагают, что разбор из урока вы уже прогнали.

1. Выполните `git cat-file -p HEAD` и `git ls-tree HEAD`. Выпишите SHA дерева и имена файлов. Есть ли у этого коммита родитель? Почему.
2. Снова измените `timeout_ms`, не делайте `git add`. Совпадает ли вывод `git rev-parse HEAD` с прошлым? В какой секции `git status` лежит правка?
3. Сделайте `git add status.txt`, затем ещё раз поменяйте число в файле, уже после add. Что покажут `git diff` и `git diff --staged`? В каком из двух мест какое число?
4. Объясните своими словами, почему второй коммит с тем же файлом получит новый SHA и будет ссылаться на первый. Что сломается в этой цепочке, если молча подменить байты первого объекта.

## Типичные ошибки

- Считать, что правка в редакторе уже «в гите». Она в истории только после коммита.
- Думать, что коммит хранит только diff (дифф — список отличий между двумя версиями файла: что добавили, что убрали). Diff Git умеет показать, сравнивая два снимка. Записывает он снимок.
- Путать ветку с копией каталога. Ветка — указатель на коммит.
- Путать `HEAD` и «последний коммит на сервере». `HEAD` — где вы в этом клоне.
- Удалять `.git`, чтобы «почистить историю», и терять все снимки.
- Инициализировать учебный репозиторий внутри Ступеней.

## Чеклист
