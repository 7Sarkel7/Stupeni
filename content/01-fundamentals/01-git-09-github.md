# GitHub: ветка, pull request, CI

**Модуль:** 01. Фундамент  
**Время:** около 50 минут  
**Дальше:** [Ключи, секреты, большие файлы, IDE](01-git-10-secrets.md)

## Цель

Провести задачу так, как её проводят в команде: ветка от свежего `main`, pull request, ревью, зелёная проверка, вливание договорённым способом. Отличить длинный git flow от коротких веток в trunk-based. Прочитать, что делает GitHub Actions в этом репозитории.

## Зачем это вам

Джуна нанимают не за знание слова «пулреквест», а за то, что он не пушит сырой эксперимент в `main`, отвечает на комментарий новым коммитом и не обходит красную сборку. Мидл ещё выбирает способ вливания и понимает, почему ветка живёт день, а не месяц. Станция тут ни при чём и при чём одновременно: прошивка и пульт — два репозитория или два каталога, и контракт между ними как раз обсуждают в описании PR, а не в чате, который пропадёт.

## Теория

### Форк или ветка в общем репозитории

Форк — ваша копия чужого репозитория на GitHub. Её заводят, когда в исходный репозиторий нельзя пушить: открытый проект, учебный репозиторий преподавателя, чужой продукт.

Дальше у вас два адреса:

| Имя | Куда смотрит |
| --- | --- |
| `origin` | ваш форк, туда вы пушите |
| `upstream` | исходный репозиторий, оттуда вы забираете свежий `main` |

```text
$ git remote add upstream https://github.com/org/station.git
$ git fetch upstream
$ git switch main
$ git merge upstream/main
```

Ветку задачи пушите в форк: `git push -u origin feature/timeout`. Pull request открывают из форка в `upstream`.

На работе в репозиторий команды обычно есть право записи. Форк не нужен. Вы пушите `feature/timeout` прямо в общий репозиторий и открываете PR внутри него. Оба пути заканчиваются одним и тем же объектом: запросом влить коммиты.

Ступени — учебник. Личную песочницу и файл вечера в этот репозиторий не присылают. Практическая работа модуля идёт в отдельном репозитории, который вы создаёте сами.

### Ветка задачи

Короткое имя про поведение: `feature/status-timeout`, `fix/ping-ui-thread`. От свежего `main`:

```text
$ git fetch origin
$ git switch main
$ git pull --ff-only
$ git switch -c feature/status-timeout
```

`--ff-only` на `main` не даст случайно завести коммит слияния, если вы отстали. Если команда отказала, у вас на `main` есть свой коммит. Его переносят на ветку задачи, а `main` возвращают к `origin/main` через `git reset --hard origin/main`, когда вы убедились, что свой коммит уже не только на `main`.

В ветке — коммиты одной задачи. Черновики склеивают rebase до первого пуша или осознанно после, с `--force-with-lease` и фразой в PR.

### Pull request

Pull request — страница, где видно коммиты, diff относительно базы, обсуждение и проверки. GitHub считает diff от общего предка, то есть те самые три точки.

Что писать в описании:

1. Какое поведение меняется. Для станции — контракт: `GET /v1/reading`, поле, таймаут.
2. Как проверить. Команда, экран, что должно мигнуть.
3. Чего в PR нет. Соседняя задача, секрет, переформатирование всего файла.

Черновик (Draft) говорят ревьюеру: смотреть можно, вливать рано. Кнопка Ready for review снимает черновик. Проверки на черновике чаще всего всё равно запускаются: красный крест на чужом `main` не появится, пока вы не влили, но на вашей ветке он уже виден.

Открыть PR можно в браузере: Compare & pull request после пуша. Из терминала, если стоит [GitHub CLI](https://cli.github.com/):

```text
$ gh pr create --draft --title "feat: timeout ping 800 мс" --body "Проверка: curl /v1/reading, в логе пульта не больше 8 попыток."
```

Дальше `gh pr ready`, когда черновик собран. Нет CLI — те же поля в браузере.

### Ревью

Комментарий к строке — вопрос или просьба. Ответ, который остаётся в истории, — новый коммит поверх, а не `--amend` коммита, на который уже ссылается обсуждение. Исключение: команда просит переписать историю ветки. Тогда rebase, `--force-with-lease` и фраза в PR «история переписана, старые SHA не смотрите».

Просьбу «поправь таймаут в README» закрывают коммитом `docs: почему timeout 800`. В интерфейсе отмечают тред решённым, когда правка на ветке, а не когда вы согласились в чате.

Approve — согласие влить. Request changes — вливать рано, есть конкретная правка. Оба статуса относятся к последнему просмотренному коммиту: новый push может снова попросить ревью, если так настроена защита ветки.

Своё ревью на собственном учебном PR GitHub позволяет оставить комментарием к строке. Это слабее чужого ревьюера и достаточно, чтобы прогнать жест «увидел замечание → запушил исправление».

### Проверки и GitHub Actions

GitHub Actions запускает команды на машине GitHub по файлу в `.github/workflows/`. Файл — сценарий: когда стартовать, на какой системе, какие шаги. Зелёная галочка на коммите — сценарий закончился с кодом 0. Красный крест — шаг вернул ошибку, лог шага и есть причина.

В Ступенях сценарий [`.github/workflows/build-apk.yml`](../../.github/workflows/build-apk.yml) называется Build learner APK. Он стартует на `push`, если изменились сам сценарий, `learner/`, `content/` или `tool/`, и ещё вручную через `workflow_dispatch`. Отдельного события `pull_request` в файле нет: галочка появляется потому, что push ветки — это push. На форке из чужого аккаунта такой push смотрит настройки репозитория-источника, не ждите ту же сборку молча.

Шаги по делу: взять код, поставить Java и Flutter, докачать NDK, выполнить `./tool/sync_content.sh`, `flutter test`, `flutter build apk --release`, положить `stupeni-learner.apk` в Artifacts. Секретов в сценарии нет, подпись debug-ключом зашита в репозитории специально: магазин этим APK не закрывают.

Как читать красный прогон:

1. Открыть упавший шаг, не кнопку Re-run.
2. Найти первую ошибку компилятора или теста, не последнюю строку «Process completed with exit code 1».
3. Повторить команду локально, если она про тесты или контент.
4. Новый коммит с починкой. Повторный push сам запустит сценарий на нужных путях.

Защита ветки (Settings → Branches → Branch protection, на части аккаунтов это Rulesets) умеет требовать, чтобы именованная проверка была зелёной. Пока она красная, кнопка вливания не нажимается. Обход галочки — не «скорость», а дырка, из-за которой `main` перестаёт собираться у всей команды.

Сценарий на работе устроен так же: событие, джоба, шаги `uses` (чужое действие) и `run` (команда оболочки). Секрет в шаге берут из `${{ secrets.ИМЯ }}`, значение задают в настройках репозитория, в файл его не вписывают и в `echo` не печатают. В логе GitHub маскирует известные секреты, это не повод проверить маску своим паролем.

### Как вливают

На странице PR кнопка предлагает один из способов. Его выбирает настройка репозитория, не каждый автор по настроению.

| Способ | Что появится на `main` |
| --- | --- |
| Merge commit | все коммиты ветки и узел слияния с двумя родителями |
| Squash | один новый коммит с diff всего PR, сообщение часто из заголовка PR |
| Rebase | коммиты ветки проиграны поверх свежего `main`, без узла слияния, SHA на `main` новые |

Squash удобен, когда в ветке десять `wip`, а в `main` нужна одна фраза. Плохо, если в ветке две независимые мысли: они склеятся навсегда. Rebase-кнопка даёт прямую историю и требует, чтобы конфликты вы уже починили у себя, иначе GitHub попросит обновить ветку. Merge commit честно хранит развилку и проще откатывается целиком через `git revert -m 1`.

После вливания локальный `main` отстаёт, пока вы не сделаете `git switch main` и `git pull`. Ветка задачи на сервере может удалиться сама, если стоит галочка. Локально: `git fetch --prune` убирает закладки удалённых веток, которых больше нет, затем `git branch -d feature/status-timeout`.

### Защищённый main

Защита, которую стоит узнавать в лицо:

- прямой push в `main` запрещён, только через PR;
- нужен один или два approve;
- нужные проверки зелёные;
- force и удаление ветки запрещены;
- иногда включено «linear history»: тогда кнопка merge-коммита недоступна, остаются squash или rebase.

Обход через `--force`, второй remote или правку на сайте — поломка договора. Если нет прав влить срочный hotfix, ищут человека с правом, а не дырку.

### Git flow и trunk-based

**Git flow** раскладывает работу по долгим веткам. `main` — только выпуски. `develop` — интеграция. От `develop` растут `feature/*`. Перед выпуском — `release/*`, после аварии на проде — `hotfix/*` обратно в `main` и в `develop`. Так живут продукты с длинной стабилизацией версии: прошивка, которую нельзя прошивать каждый вечер, коробочный релиз раз в квартал.

Цена — много веток, которые отстают друг от друга, и конфликты пачками в день слияния. Для приложения, которое выкладывают часто, эта схема тяжёлая.

**Trunk-based** держит одну главную линию, обычно `main`. Ветки задач живут часы или пару дней и вливаются обратно. Недоделанное поведение прячут флагом в коде, а не месячной веткой. PR при этом бывает: он короткий, его ревьюят в тот же день. «Мы на trunk» в вакансии Android чаще означает именно это, а не запрет веток.

Вопрос на собеседовании и в первый день: сколько живёт ветка и кто пишет в `main`. Ответ команды важнее схемы из статьи. Для станции на столе хватает короткой ветки от `main`: опыт не ломает последнюю прошивку, которая отвечала на status, а вливание одно, без `develop`.

## Разбор на примере

Задача: пульт повторяет ping. Репозиторий общий, форк не нужен.

```text
$ git fetch origin
$ git switch main
$ git pull --ff-only
$ git switch -c feature/ping-retry
```

Два коммита, второй по замечанию себе же: «в сообщении нет контракта». Склеивать их или нет — до пуша, интерактивным rebase. Затем:

```text
$ git push -u origin feature/ping-retry
```

В браузере откройте Draft PR. В тексте:

```text
feat: повторять ping, пока SoftAP не ответит

Контракт: GET /v1/reading, тело начинается с OK.
До 8 попыток, пауза 1.5 с, сеть не на UI-потоке.
Проверка: погасить точку, открыть пульт, экран не замирает, в логе попытки.
```

Сборка Actions на ветке зелёная, если вы трогали пути, которые есть в сценарии, или если в учебном репозитории станции свой сценарий. Красный тест — новый коммит, не снятие галочки.

Замечание ревью: «800 мс не объяснены». Не amend, а:

```text
$ git commit -am "docs: почему у ping пауза 1.5 с"
$ git push
```

`-a` у `git commit` добавляет изменения уже отслеживаемых файлов и сразу коммитит. Новые файлы он не возьмёт. После пуша страница PR сама покажет новый коммит. Тред можно закрыть.

Вливание по договору команды. Для такой задачи из одного смысла подходит squash: на `main` одна фраза. Если договор — merge commit, жмёте его и не спорите кнопкой. Потом:

```text
$ git switch main
$ git pull
$ git log --oneline -3
$ git fetch --prune
$ git branch -d feature/ping-retry
```

## Упражнения

1. Напишите описание PR из пяти-восьми строк для задачи «хендлер `/api/display` только запоминает путь, GIF крутит `loop`». Должны быть поведение, как проверить, чего в PR нет.
2. Ревьюер оставил комментарий на коммите, который уже на сервере. Почему следующий шаг — новый коммит, а не `git commit --amend`, если в чате не просили переписать историю.
3. В Ступенях упал шаг `flutter test` в Actions. Куда смотреть сначала и чем не является кнопка Re-run.
4. Команда выпускает прошивку раз в квартал и держит `develop`. Другая команда вливает Android-задачи в `main` в тот же день. Как называются эти два уклада и какой вопрос вы зададите, прежде чем выбрать себе схему для станции.

### Ориентир для самопроверки

Сначала запишите ответы своими словами. Короткий ключ — [01-git-09-github.md](../hints/01-git-09-github.md). В приложении нажмите на эту ссылку: откроется ключ, без отметки «изучил». Откройте его после своей попытки. Дословно в тетрадь ключ не переписывайте.

## Типичные ошибки

- PR с заголовком «фикс» и пустым телом.
- Влить свой же красный PR, потому что «тест мигает».
- Amend и force посреди ревью без фразы в обсуждении.
- Долгая ветка на месяц с половиной продукта, потом один конфликт на тысячу строк.
- Секрет в логе Actions, чтобы «посмотреть, подхватился ли».
- Путать форк (копия репозитория на сервере) и ветку (имя коммита).
- Нести личный лог вечера в PR Ступеней.
