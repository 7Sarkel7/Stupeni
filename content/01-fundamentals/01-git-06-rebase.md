# Rebase, интерактивный rebase, cherry-pick

**Модуль:** 01. Фундамент  
**Время:** около 45 минут  
**Дальше:** [Stash: спрятать незакоммиченное](01-git-07-stash.md)

## Цель

Переложить свои коммиты (сохранённый в Git снимок изменений с подписью) поверх свежего `main`. Склеить черновые коммиты и поправить их сообщения до того, как ветку увидят другие. Забрать один коммит с чужой ветки, не сливая её целиком.

## Зачем это вам

Merge (мерж — слияние, то есть объединение изменений одной ветки Git с другой) сохраняет развилку и честно показывает, что две линии жили параллельно. Rebase собирает прямую историю: ваши коммиты выглядят так, будто вы начали их уже от сегодняшнего `main`. На ревью (проверка вашего кода другим человеком до того, как изменения попадут в проект) такую ветку проще читать. Цена — у переписанных коммитов новые SHA (SHA, хеш — уникальный идентификатор коммита из букв и цифр). Если их уже забрали коллеги, вы подменяете им историю. Поэтому rebase — инструмент своей ветки до общей публикации и осторожный инструмент после, а не кнопка для `main`.

## Теория

### Что делает rebase

`git rebase main`, пока вы на `feature/timeout`, находит коммиты, которые есть на feature и которых нет на `main`, и заново применяет их патчи (небольшой набор правок, который можно применить к коду) поверх кончика `main`. Старые объекты остаются в reflog (личный журнал Git, где записаны ваши перемещения по истории; с его помощью можно вернуть «потерянные» коммиты). Ветка `feature/timeout` переезжает на новые SHA.

```text
до:

    A ---- B ---- E          main
           \
            C ---- D         feature/timeout

после git rebase main:

    A ---- B ---- E          main
                     \
                      C' -- D'    feature/timeout
```

`C'` — тот же diff (дифф — список отличий между двумя версиями файла: что добавили, что убрали) и то же сообщение, что у `C`, другой родитель и другой SHA. `main` этой командой не двигается. Чтобы `main` включил работу, после rebase делают merge (часто он уже fast-forward — простое слияние, при котором Git лишь передвигает указатель ветки вперёд) или pull request (просьба на GitHub проверить ваши изменения и добавить их в основную ветку).

Подтянуть свежий `main` и переложить ветку одной привычкой:

```text
$ git switch feature/timeout
$ git fetch origin
$ git rebase origin/main
```

`git pull --rebase` на отслеживаемой ветке делает fetch и rebase. Подробности pull (пулл — получение чужих коммитов с сервера и добавление их к вашей ветке) — в уроке про remote (удалённая копия репозитория на сервере; origin — имя по умолчанию для основного такого адреса).

Остановить и вернуть ветку к состоянию до команды: `git rebase --abort`. Продолжить после ручной починки: `git rebase --continue`. Пропустить коммит, который больше не нужен: `git rebase --skip` — только если вы поняли, что патч уже есть в базе и применять его второй раз вредно.

### Конфликт во время rebase

Конфликт здесь тот же маркер в файле. Меняется смысл слов ours и theirs.

Пока Git применяет ваш коммит поверх `main`, «текущая база» — это `main`. В маркере `<<<<<<< HEAD` лежит версия базы, не старой feature-ветки. Входящий кусок — ваш переносимый коммит.

```text
<<<<<<< HEAD
timeout_ms:3000
board:esp32s3_dev
=======
timeout_ms:800
>>>>>>> feat: timeout ping 800 мс
```

`--ours` во время rebase — сторона, на которую перекладываете (`main`). `--theirs` — коммит, который сейчас проигрывается (ваш). Это легко перепутать с merge. Надёжный путь — открыть файл и собрать смысл: таймаут (предельное время ожидания ответа, после которого ожидание обрывают) 800 из вашей задачи и `board` из свежего `main`.

```text
$ git add status.txt
$ git rebase --continue
```

Если редактор открыл сообщение коммита, сохраните его и закройте. Пока все коммиты не лягут, rebase не закончен. `git status` в этот момент пишет, какой шаг идёт.

### Интерактивный rebase

`git rebase -i main` открывает список коммитов, которые будут переиграны, от старого к новому. Слово в начале строки — приказ.

```text
pick c1d2e3f wip timeout
squash a9b8c7d wip ещё строка
fixup 111aaaa опечатка в комментарии
reword 222bbbb fix: timeout ping 800 мс
```

| Слово | Что будет с коммитом |
| --- | --- |
| `pick` | взять как есть |
| `reword` | взять diff, остановиться и дать поправить сообщение |
| `squash` | склеить с предыдущим коммитом в списке и открыть оба сообщения |
| `fixup` | склеить с предыдущим и выбросить это сообщение |
| `drop` | не переносить коммит |
| `edit` | остановиться после применения, можно поправить файлы и `git commit --amend`, затем `--continue` |

Порядок строк можно менять. На практикуме не переставляйте коммиты, которые зависят друг от друга по одним и тем же строкам: получите лишние конфликты.

Команда «склеить последние три коммита, база не нужна в списке»:

```text
$ git rebase -i HEAD~3
```

`HEAD~3` — база, её саму в списке нет. В списке три коммита поверх неё. Если между ними есть merge-коммит, интерактивный rebase без флага `--rebase-merges` остановится или развернёт историю плоско. Черновики склеивают до слияния с `main`, пока линия прямая.

После того как ветку запушили (пуш — отправка ваших коммитов на сервер, например на GitHub), переписанные SHA на сервере сами не заменятся. Обновление своей ветки — `git push --force-with-lease`. Почему не голый `--force`, разобрано в уроке про remote. Чужую ветку и `main` так не переписывают.

`git commit --fixup SHA` создаёт коммит с пометкой, какой коммит он чинит. Потом `git rebase -i --autosquash main` сам ставит `fixup` в нужное место списка. Удобно, когда ревьюер просит поправить уже существующий коммит вашей ветки. Делайте это, пока ветка ваша.

### Чего rebase не делает с общим main

Коммиты, которые уже на `origin/main` и от которых ответвились другие, не перекладывают. Вы меняете SHA, а у коллег в ветках родитель — старый SHA. Их следующая работа встанет на «пропавшего» родителя.

Свою feature-ветку, которую пока смотрите только вы, переписывать можно. Если открыт pull request и его уже забрали, в описании пишут «переписал историю, сделайте fetch и reset ветки на мою». Без этого предупреждения человек со старой копией вливает её обратно и возвращает вам дубликаты коммитов.

### cherry-pick

`git cherry-pick SHA` берёт diff одного коммита и применяет его на текущей ветке новым коммитом. Новый SHA, сообщение по умолчанию то же.

```text
$ git switch main
$ git cherry-pick e4f5a6b
```

Так на `main` переносят маленький hotfix (фикс — исправление ошибки; хотфикс — срочное исправление, которое выпускают без ожидания обычного релиза) с длинной feature-ветки, не дожидаясь всей задачи. Или тащат полезный коммит коллеги, не сливая его черновики.

Cherry-pick не связывает новый коммит со старым как родитель. В истории две похожие правки. Потом, когда целая ветка сольётся, Git часто поймёт, что патч уже есть, но конфликт всё ещё возможен, если контекст разъехался. В сообщении имеет смысл дописать, откуда взяли SHA.

Несколько коммитов по порядку: `git cherry-pick A^..B` или перечисление SHA от старого к новому. Прервать конфликтный cherry-pick: `git cherry-pick --abort`. Продолжить: `git add` и `git cherry-pick --continue`.

## Разбор на примере

На `feature/timeout` три мелких коммита: черновик, опечатка, нормальное сообщение. `main` уехал вперёд и поменял ту же строку таймаута.

Сначала посмотрите список, который будете склеивать. База — общий предок, пока вы ещё не rebase:

```text
$ git switch feature/timeout
$ git log --oneline main..HEAD
222bbbb fix: timeout ping 800 мс
111aaaa опечатка в комментарии
c1d2e3f wip timeout
```

`main..HEAD` — коммиты, достижимые с `HEAD` и не достижимые с `main`. Это и есть ваша работа.

Перенос на свежий `main` с конфликтом на первом же патче:

```text
$ git rebase main
Auto-merging status.txt
CONFLICT (content): Merge conflict in status.txt
error: could not apply c1d2e3f... wip timeout
```

В файле `HEAD` — свежий `main` (например `timeout_ms:3000` и строка `model`). Нижний блок — ваш черновик `800`. Соберите оба смысла, уберите маркеры.

```text
$ git add status.txt
$ git rebase --continue
```

Остальные коммиты, если они трогали только README, лягут сами. Если нет — тот же цикл: файл, `git add`, `--continue`.

Теперь склейка. Коммиты уже новые, их три поверх `main`:

```text
$ git rebase -i main
```

В редакторе:

```text
pick c1d2e3f wip timeout
fixup 111aaaa опечатка в комментарии
squash 222bbbb fix: timeout ping 800 мс
```

`fixup` выкинет сообщение опечатки. `squash` остановится и даст собрать одно сообщение. Итог, который стоит оставить:

```text
feat: timeout ping 800 мс

Поле model со свежего main сохранено.
Пауза короче, чем дефолтные 1500, опыт только на этой ветке.
```

Проверка:

```text
$ git log --oneline --graph --decorate main..HEAD
$ git diff main...HEAD
```

Один коммит, в diff нет маркеров конфликта, есть и `800`, и `board`.

Отдельно, если hotfix нужно на `main` сегодня, а остальная ветка сырая:

```text
$ git switch main
$ git cherry-pick <новый-SHA>
```

На учебном вечере cherry-pick можно тут же убрать своим `git reset --mixed HEAD~1`, раз вы его ещё не пушили. На работе такой коммит вместо reset отменяют `revert`, если он уже общий.

## Упражнения

1. Сделайте на ветке два коммита-черновика с плохими сообщениями `wip` и `wip2`. `git rebase -i HEAD~2`: первый `pick`, второй `fixup`. Какое сообщение осталось у единственного коммита и почему SHA другой, чем у исходного `wip`.
2. Во время rebase в файле конфликт. Напишите, какая сторона в верхнем блоке `<<<<<<< HEAD`, если вы выполняли `git rebase main`. Почему `git checkout --ours` может выбросить как раз вашу задачу.
3. Ветка уже открыта в pull request, коллега от неё не ответвлялся, вы склеили коммиты локально. Какой push обновит сервер и чем опасен вариант, который не смотрит, не появился ли на сервере чужой коммит. Полная команда force-with-lease будет в уроке про remote: здесь назовите требование своими словами.
4. На `main` нужен один коммит с ветки `feature/logs`, остальные коммиты той ветки сырые. Какая команда перенесёт только его. Чем новый коммит отличается от старого для `git log`.

Сначала запишите ответы своими словами. Короткий ключ — [01-git-06-rebase.md](../hints/01-git-06-rebase.md). В приложении нажмите на эту ссылку: откроется ключ, без отметки «изучил». Откройте его после своей попытки. Дословно в тетрадь ключ не переписывайте.

## Типичные ошибки

- Rebase общего `main`, потому что «так ровнее график».
- `--ours` в rebase в надежде оставить свою ветку.
- `git rebase --skip` на конфликте, который вы не поняли: коммит исчезнет из ветки.
- Интерактивный rebase уже опубликованной ветки без предупреждения в pull request.
- Cherry-pick всей пачки коммитов вместо merge, когда нужна вся ветка: теряется связь и легко забыть один SHA.
- Оставить маркеры конфликта и продолжить rebase.
