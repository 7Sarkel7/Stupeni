# Удалённые репозитории, теги, релизы

**Модуль:** 01. Фундамент  
**Время:** около 45 минут  
**Дальше:** [GitHub: ветка, pull request, CI](01-git-09-github.md)

## Цель

Понимать, что лежит на сервере, а что только у вас. Отличать fetch от pull. Отправлять ветку и запоминать, за какой удалённой веткой она следит. Обновлять свою ветку через rebase (ребейз — перенос ваших коммитов поверх другого, более свежего коммита, чтобы история выглядела прямой). Переписывать уже отправленную ветку так, чтобы не затереть чужой коммит (сохранённый в Git снимок изменений с подписью). Помечать снимок тегом и собирать из тега релиз.

## Зачем это вам

«Я запушил» и «я обновился» на работе означают конкретные команды. Fetch ничего не меняет в ваших файлах. Pull меняет. Force без lease затирает коммит коллеги, который вы ещё не видели. Тег `v1.2.0` — это ответ на вопрос «какой исходник сейчас на станции», когда прошивка на столе и прошивка в `main` уже разъехались.

## Теория

Remote (удалённая копия репозитория на сервере; origin — имя по умолчанию для основного такого адреса) — именованный адрес другого репозитория. У клона (полная копия репозитория с историей на вашем компьютере) адрес уже есть и зовётся `origin`.

```text
$ git remote -v
origin	git@github.com:you/station.git (fetch)
origin	git@github.com:you/station.git (push)
```

Две строки могут указывать на разные URL (адрес ресурса в интернете): забирать из одного места, отправлять в другое. Так устроен форк (ваша личная копия чужого репозитория на GitHub), об этом следующий урок. Добавить адрес: `git remote add origin git@github.com:you/station.git`. Переименовать: `git remote rename origin upstream`. Удалить: `git remote remove origin`. Само по себе `remove` не стирает коммиты, только адрес и ветки вида `origin/...`, которые Git хранит у вас как закладки.

### Ветки слежения

`origin/main` — не ветка на сервере прямо сейчас. Это закладка в вашем клоне: «когда я последний раз делал fetch, на сервере `main` был вот этот SHA» (SHA, хеш — уникальный идентификатор коммита из букв и цифр). Обновляется она от fetch, не от того, что коллега нажал кнопку.

Локальная `main` обычно следит за `origin/main`. Статус тогда пишет `ahead` и `behind`:

```text
$ git status -sb
## main...origin/main [behind 2]
```

`behind 2` — на закладке два коммита, которых нет у вас. `ahead 1` — у вас один коммит, которого нет на закладке. Числа про закладку. Если fetch был вчера, числа тоже вчерашние.

Посмотреть связь:

```text
$ git branch -vv
* feature/timeout a1b2c3d [origin/feature/timeout] feat: timeout ping 800 мс
```

Скобка — ветка, за которой следит локальная. Пустая скобка значит, что слежки нет: `git push` без аргументов не знает, куда слать, и попросит их.

Первый push с запоминанием:

```text
$ git push -u origin feature/timeout
```

`-u` равно `--set-upstream`. Следующие `git push`, `git pull` и `git status` на этой ветке используют `origin/feature/timeout`.

### fetch и pull

`git fetch origin` скачивает новые объекты и двигает закладки `origin/*`. Ваши ветки, индекс и файлы не трогает.

```text
до fetch

сервер main:     A -- B -- C -- D
локальный main:  A -- B -- C     HEAD
origin/main:     A -- B -- C

после fetch

локальный main:  A -- B -- C     HEAD
origin/main:     A -- B -- C -- D
```

Теперь можно прочитать чужое, не подмешивая к себе: `git log --oneline HEAD..origin/main` и `git diff HEAD...origin/main`.

`git pull` — это fetch плюс вливание закладки в текущую ветку. По умолчанию вливание делает merge (мерж — слияние, то есть объединение изменений одной ветки Git с другой), поэтому при расхождении появляется коммит слияния, а при грязном дереве (грязное дерево — в рабочем каталоге есть правки, которые вы ещё не сохранили коммитом) — отказ из урока про stash (стэш — временный «карман» Git для незакоммиченных правок).

```text
после pull (merge), если вы не расходились

локальный main:  A -- B -- C -- D     HEAD
origin/main:     A -- B -- C -- D
```

Если вы успели сделать свой коммит `E` поверх `C`, а на сервере появился `D`:

```text
после pull (merge)

                 E -- M     main, HEAD
                /    /
    A -- B -- C      D      origin/main до merge указывал на D
```

`git pull --rebase` вместо merge перекладывает ваши локальные коммиты поверх только что скачанных. История ветки остаётся прямой, SHA ваших коммитов меняются. Это уместно на своей feature-ветке. На общем `main`, куда коммитят несколько человек без договорённости, неожиданный rebase переписывает то, что вы уже могли кому-то отдать.

Личная настройка «pull всегда через rebase»:

```text
$ git config --global pull.rebase true
```

Ставьте её, только если согласны с этим для всех своих репозиториев. На работе смотрят договор команды. Узнать, что сделает pull без догадок: `git config --show-origin --get pull.rebase`. Если значения нет, pull сольёт merge.

`git fetch` перед трудным решением ничего не ломает. `git pull` на грязном дереве и на ветке, где вы не готовы к чужому merge, лучше не жать «ещё раз».

### push

`git push origin feature/timeout` отправляет коммиты, которых нет на сервере, и двигает одноимённую ветку на сервере, если это fast-forward (простое слияние, при котором Git лишь передвигает указатель ветки вперёд): серверный кончик — предок вашего. Если на сервере есть коммит, которого у вас нет, обычный push откажется. Сначала fetch и посмотрите, что это за коммит. Потом merge или rebase своей ветки и обычный push.

Удалить ветку на сервере, когда pull request (просьба на GitHub проверить ваши изменения и добавить их в основную ветку) уже влит и имя не нужно: `git push origin --delete feature/timeout`. Локальное имя удаляют отдельно `git branch -d`.

### force и force-with-lease

После rebase ваши SHA новые. Сервер помнит старые. Обычный push откажет, потому что это не fast-forward.

`git push --force` велит серверу передвинуть ветку на ваш SHA в любом случае. Если коллега успел положить на эту ветку коммит, которого вы не видели, `--force` его с кончика ветки снимет. Объект на сервере ещё поживёт в служебных ссылках, но в работе его уже нет.

`git push --force-with-lease` отправляет переписывание только если серверный кончик совпадает с вашей закладкой `origin/feature/timeout`. Чужой коммит, которого вы не фетчили, даст отказ. Тогда `git fetch`, смотрите `git log`, забираете чужое и только потом решаете, нужен ли новый lease.

```text
$ git fetch origin
$ git rebase origin/main
$ git push --force-with-lease
```

Lease сравнивает с закладкой. Если вы сделали fetch, увидели чужой коммит и всё равно хотите его выкинуть, lease уже не защитит: закладка обновилась, и вы осознанно заменяете кончик. Смысл флага — не затереть то, чего вы не видели.

Куда force не отправляют:

- `main` и любая ветка, от которой ответвляются другие;
- ветка коллеги;
- ситуация «push не прошёл, попробую force», без чтения отказа.

Защищённая ветка на GitHub отклонит force даже у того, кто ошибся. Это следующий урок.

### Теги

Тег — имя коммита, которое не едет вперёд с новыми коммитами. Ветка двигается, тег стоит.

Лёгкий тег — просто имя на SHA, как закладка без автора:

```text
$ git tag v1.2.0-light
```

Аннотированный тег — отдельный объект: автор, дата, сообщение. Им помечают выпуск.

```text
$ git tag -a v1.2.0 -m "Пульт и прошивка: status отвечает, timeout 1500."
$ git show v1.2.0
```

`git show` на аннотированном теге показывает и карточку тега, и коммит.

Теги сами не уходят с `git push`. Отдельно:

```text
$ git push origin v1.2.0
```

`git push origin --tags` отправит все локальные теги, включая случайные. На работе предпочитают явное имя одного тега.

Удалить локально: `git tag -d v1.2.0`. Удалить на сервере: `git push origin --delete v1.2.0`. Перевесить тег на другой коммит — редкая операция и путаница для тех, кто уже скачал старый тег. Проще выпустить `v1.2.1`.

По тегу открывают тот самый снимок, которым прошивали станцию:

```text
$ git switch --detach v1.2.0
```

Вы в detached HEAD (указатель Git на коммит, на котором вы сейчас стоите) на коммите релиза. Новые эксперименты — через `git switch -c`, не коммитом «в тег». Тег назад не двигается.

### Релиз на GitHub

Релиз — страница поверх тега: заголовок, заметки для человека, иногда приложенный файл (APK, прошивка). Тег без страницы всё равно указывает на коммит. Страница без тега на GitHub не живёт: релиз создаётся из тега.

Заметки пишут поведением: «/v1/reading отдаёт fw и board, ping повторяется 8 раз». Не списком SHA. Черновик релиза можно собрать и в интерфейсе GitHub (Releases → Draft a new release), выбрав уже запушенный тег. Команда `gh release create v1.2.0 --notes "..."`, если установлен GitHub CLI, делает то же из терминала.

В репозитории Ступеней APK (файл установки приложения для Android) собирает GitHub Actions и кладёт файл в Artifacts (артефакт — готовый результат сборки или проверки, который можно скачать, например APK) прогона, это не тег. Тег вы ставите на свой учебный или рабочий репозиторий, когда снимок и правда выпуск.

## Разбор на примере

Два каталога на одной машине заменяют сервер, пока нет GitHub. Голый репозиторий — адрес без рабочего дерева.

```text
$ git init --bare ~/sandbox/station-remote.git
$ cd ~/sandbox/git-course
$ git remote add origin ~/sandbox/station-remote.git
$ git push -u origin main
$ git remote -v
$ git status -sb
## main...origin/main
```

Второй клон — «коллега»:

```text
$ git clone ~/sandbox/station-remote.git ~/sandbox/station-colleague
$ cd ~/sandbox/station-colleague
$ git log --oneline
```

Коллега делает коммит и пушит. Вы у себя:

```text
$ git fetch origin
$ git status -sb
## main...origin/main [behind 1]
$ git log --oneline HEAD..origin/main
$ git pull --rebase
$ git status -sb
## main...origin/main
```

Fetch показал `behind`, файлы ещё не менял, пока вы не сделали pull. `--rebase` здесь fast-forward, если своих коммитов не было: перекладывать нечего, указатель просто догнал закладку.

Своя ветка и переписывание:

```text
$ git switch -c feature/timeout
$ printf 'fw:1.0.0\ntimeout_ms:800\n' > status.txt
$ git add status.txt
$ git commit -m "feat: timeout ping 800 мс"
$ git push -u origin feature/timeout
$ git commit --amend -m "feat: timeout ping 800 мс на время опыта"
$ git push
```

Второй push откажется: amend (дописывание или исправление последнего коммита вместо нового) сменил SHA, на сервере старый кончик. Посмотрите отказ. Затем:

```text
$ git fetch origin
$ git push --force-with-lease
```

Закладка совпала с тем, что вы сами запушили раньше, lease проходит. Если между amend и push коллега пушил в `feature/timeout`, lease остановит вас. Это и есть проверка.

Тег на коммите, которым вы довольны как учебной прошивкой:

```text
$ git switch main
$ git tag -a v0.1.0 -m "Учебный status: первая отметка песочницы."
$ git push origin v0.1.0
$ git show v0.1.0 --stat
```

Во втором клоне тег появится после `git fetch --tags` или обычного `git fetch` в современных версиях Git, которые забирают теги доступных коммитов. Проверка: `git tag` и `git show v0.1.0`.

## Упражнения

1. В своей песочнице выполните `git fetch`, не делая pull. Чем вывод `git status -sb` после чужого коммита отличается от состояния файлов. Какая команда как раз меняет файлы.
2. Объясните, что сравнит `--force-with-lease` перед тем, как передвинуть ветку на сервере. В каком случае голый `--force` снимет чужой коммит, а lease откажется.
3. Почему тег `v0.1.0` не заменяет ветку `main`. Что вы сделаете, чтобы открыть ровно тот снимок через месяц, когда `main` уйдёт вперёд на двадцать коммитов.
4. Аннотированный тег создан локально, `git push` без аргументов прошёл, коллега тега не видит. Какой команды не хватило.

### Ориентир для самопроверки

Сначала запишите ответы своими словами. Короткий ключ — [01-git-08-remotes.md](../hints/01-git-08-remotes.md). В приложении нажмите на эту ссылку: откроется ключ, без отметки «изучил». Откройте его после своей попытки. Дословно в тетрадь ключ не переписывайте.

## Типичные ошибки

- Путать `origin/main` с живым взглядом на сервер без fetch.
- `git pull` на грязной ветке и паника от отказа, хотя fetch ещё даже не нужен был повторно.
- `--force` на `main`, потому что push «просто не прошёл».
- Lease сразу после fetch, не читая, чей коммит приехал: защита уже пройдена, вы видели кончик.
- Лёгкий тег там, где нужен выпуск с автором и сообщением.
- `git push --tags` с мусорными локальными тегами `tmp` и `wip`.
- Коммит прямо в detached HEAD на теге релиза.
