# Поток, корутины и Result

**Модуль:** 02. Kotlin и Android  
**Время:** около 30 минут  
**Дальше:** [OkHttp и cleartext](02-okhttp.md)

## Цель

Увести запрос к станции с главного потока. Вернуть результат как `Result`, а не как бросок через весь экран. Показать успех и провал уже на UI-потоке (UI — пользовательский интерфейс: всё, что видит и нажимает человек).

## Зачем это вам

Кнопка «жив ли станция» — первый кусок пульта. Если вызвать сеть в `onClick`, экран стынет на время таймаута (предельное время ожидания ответа, после которого ожидание обрывают). На Android  с некоторой версии такой сокет ещё и роняет приложение `NetworkOnMainThreadException`. Для человека на диване это не «тонкость Kotlin», а пульт, который умер, пока плата молчала две секунды. Молчание SoftAP (плата сама раздаёт Wi-Fi, как маленький роутер) в первые секунды после питания — нормальный случай, не исключение.

Вы уже писали UI на Kotlin. Здесь одна новая дисциплина: главный поток рисует, IO ждёт плату.

## Теория

У процесса есть главный поток. Он разбирает нажатия и рисует кадры. Пока он в `execute()` у OkHttp, очередь кадров стоит. Корутина — способ описать ожидание так, чтобы поток в это время делал другую работу.

Экран нового пульта — Compose и Material 3, разметка XML (формат разметки с тегами в угловых скобках) для него не заводится. Подробный разбор кадра начинается с урока про composable. Здесь одна дисциплина потока, она от стека UI не зависит.

Практический минимум для экрана:

- Пока нет ViewModel, `lifecycleScope` привязан к Activity, которая держит `setContent`. Ушли с экрана — работа отменяется. Дальше тот же запрос переедет в `viewModelScope`. `GlobalScope` переживёт экран и может обновить уже снятый кадр.
- `Dispatchers.IO` — место для сокета.
- `Dispatchers.Main` — место для Toast и текста на кнопке.
- `runBlocking` на главном потоке — тот же затык, только выглядит как корутина. Им не оборачивают `onClick`.

Сигнатура ping:

```kotlin
fun ping(): Result<String> = runCatching {
    // сокет здесь. Вызовет IOException, если станции нет.
}
```

`runCatching` кладёт успех или исключение в `Result`. Экран не обязан знать про `IOException`. Он развивает оба конца:

```kotlin
lifecycleScope.launch(Dispatchers.IO) {
    val result = client.ping()
    withContext(Dispatchers.Main) {
        result.fold(
            onSuccess = { body -> toast(body) },
            onFailure = { e -> toast(e.message ?: "Нет связи со станцией") },
        )
    }
}
```

`fold` не бросает дальше. «Станция выключена» — обычная ветка, не краш.

Пока IP неизвестен, клиента нет. `lateinit` и обращение в `onCreate` до ввода адреса — способ уронить экран `UninitializedPropertyAccessException` раньше любой сети. Храните `StationWifiClient?` и создавайте его, когда человек или обнаружение в LAN (локальная сеть в пределах дома или офиса) дали хост.

Повтор ping на старте точки — цикл на IO, не на главном потоке:

```kotlin
fun pingWithWarmup(): Result<String> {
    var last: Result<String> = Result.failure(IllegalStateException("нет попыток"))
    repeat(8) {
        last = ping()
        if (last.isSuccess) return last
        Thread.sleep(1_500)
    }
    return last
}
```

`Thread.sleep` здесь терпим только потому, что вы уже на IO. На главном потоке те же полторы секунды — заморозка. Когда прогреете корутины глубже, сон заменится на `delay`, но смысл тот же: ждать плату не там, где рисуется интерфейс.

Ошибки, которые стоит различать в сообщении, а не глотать:

- нет сокета и таймаут — «станция не ответила»;
- HTTP 400/503 — в сообщение кладут тело ответа, это уже не «нет связи» (разбор кода будет в уроке OkHttp);
- исключение парсера (код, который разбирает строку, например JSON, на понятные программе части; сам разбор называют парсингом) — «не понял ответ».

Пустой `catch` прячет все три в работающую кнопку, которая ничего не сделала.

## Разбор на примере

Экран Compose: поле IP и кнопка Ping. Кнопку выключают сменой состояния, с которого рисуется `enabled`. По нажатию:

1. Прочитали IP, собрали клиент, если его ещё нет или хост сменился.
2. Запустили `lifecycleScope` на IO.
3. `ping()` внутри `runCatching` сходил на `/v1/reading`.
4. На главном потоке либо показали тело `OK fw:...`, либо фразу про связь.

Пока запрос идёт, кнопку выключают, иначе второй нажим плодит ещё сокеты и гонку (гонка — ошибка, при которой результат зависит от того, какой из параллельных процессов успеет раньше) Тостов. Это уже состояние экрана; подробно — урок 04 этого модуля. Здесь важно не блокировать отрисовку самого выключения кнопки: смену `enabled` делают на главном потоке до ухода на IO и после возврата.

Если вы ушли с экрана на середине таймаута, `lifecycleScope` отменяет корутину. Добивать Toast в уничтоженную Activity не нужно.

## Типичные ошибки

- Сеть и `Thread.sleep` в `onClick` или внутри `runOnUiThread`.
- `runBlocking(Dispatchers.Main)` вокруг ping.
- `GlobalScope` и обновление вьюхи без проверки, жив ли экран.
- `lateinit` клиент, который трогают до ввода IP.
- Показать человеку stack trace (стек вызовов — цепочка функций, по которой программа дошла до ошибки) вместо одной фразы. В лог (журнал, куда программа записывает, что делает) — исключение, на экран — что делать.

## Чеклист

- [ ] Ping выполняется на `Dispatchers.IO`.
- [ ] Текст на экране меняется на `Dispatchers.Main`.
- [ ] Провал сети — ветка `onFailure`, не падение Activity.
- [ ] Скоуп (область, внутри которой что-то живёт и действует; в корутинах это «хозяин» запущенных корутин) отменяется вместе с экраном.
- [ ] Клиент создаётся после того, как есть хост.
