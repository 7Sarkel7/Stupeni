# Поток, корутины и Result

**Модуль:** 02. Kotlin и Android  
**Время:** около 30 минут  
**Дальше:** [OkHttp и cleartext](02-okhttp.md)

## Цель

Увести запрос к станцу с главного потока. Вернуть результат как `Result`, а не как бросок через весь экран. Показать успех и провал уже на UI-потоке.

## Зачем это вам

Кнопка «жив ли станц» — первый кусок пульта. Если вызвать сеть в `onClick`, экран стынет на время таймаута. На Android  с некоторой версии такой сокет ещё и роняет приложение `NetworkOnMainThreadException`. Для человека на диване это не «тонкость Kotlin», а пульт, который умер, пока плата молчала две секунды. Молчание SoftAP в первые секунды после питания — нормальный случай, не исключение.

Вы уже писали UI на Kotlin. Здесь одна новая дисциплина: главный поток рисует, IO ждёт плату.

## Теория

У процесса есть главный поток. Он разбирает нажатия и рисует кадры. Пока он в `execute()` у OkHttp, очередь кадров стоит. Корутина — способ описать ожидание так, чтобы поток в это время делал другую работу.

Практический минимум для экрана:

- `lifecycleScope` привязан к экрану. Ушли с Activity — работа отменяется. `GlobalScope` переживёт экран и может трогать уже мёртвые вьюхи.
- `Dispatchers.IO` — место для сокета.
- `Dispatchers.Main` — место для Toast и текста на кнопке.
- `runBlocking` на главном потоке — тот же затык, только выглядит как корутина. Им не оборачивают `onClick`.

Сигнатура ping:

```kotlin
fun ping(): Result<String> = runCatching {
    // сокет здесь. Вызовет IOException, если станца нет.
}
```

`runCatching` кладёт успех или исключение в `Result`. Экран не обязан знать про `IOException`. Он развивает оба конца:

```kotlin
lifecycleScope.launch(Dispatchers.IO) {
    val result = client.ping()
    withContext(Dispatchers.Main) {
        result.fold(
            onSuccess = { body -> toast(body) },
            onFailure = { e -> toast(e.message ?: "Нет связи с станцом") },
        )
    }
}
```

`fold` не бросает дальше. «Станц выключен» — обычная ветка, не краш.

Пока IP неизвестен, клиента нет. `lateinit` и обращение в `onCreate` до ввода адреса — способ уронить экран `UninitializedPropertyAccessException` раньше любой сети. Храните `Esp32WifiClient?` и создавайте его, когда человек или обнаружение в LAN дали хост.

Повтор ping на старте точки — цикл на IO, не на главном потоке:

```kotlin
fun pingWithWarmup(): Result<String> {
    var last: Result<String> = Result.failure(IllegalStateException("нет попыток"))
    repeat(8) {
        last = ping()
        if (last.isSuccess) return last
        Thread.sleep(1_500)
    }
    return last
}
```

`Thread.sleep` здесь терпим только потому, что вы уже на IO. На главном потоке те же полторы секунды — заморозка. Когда прогреете корутины глубже, сон заменится на `delay`, но смысл тот же: ждать плату не там, где рисуется интерфейс.

Ошибки, которые стоит различать в сообщении, а не глотать:

- нет сокета и таймаут — «станц не ответил»;
- HTTP 400/503 — в сообщение кладут тело ответа, это уже не «нет связи» (разбор кода будет в уроке OkHttp);
- исключение парсера — «не понял ответ».

Пустой `catch` прячет все три в работающую кнопку, которая ничего не сделала.

## Разбор на примере

Экран с полем IP и кнопкой Ping. По нажатию:

1. Прочитали IP, собрали клиент, если его ещё нет или хост сменился.
2. Запустили `lifecycleScope` на IO.
3. `ping()` внутри `runCatching` сходил на `/v1/reading`.
4. На главном потоке либо показали тело `OK fw:...`, либо фразу про связь.

Пока запрос идёт, кнопку выключают, иначе второй нажим плодит ещё сокеты и гонку Тостов. Это уже состояние экрана; подробно — урок 04 этого модуля. Здесь важно не блокировать отрисовку самого выключения кнопки: смену `enabled` делают на главном потоке до ухода на IO и после возврата.

Если вы ушли с экрана на середине таймаута, `lifecycleScope` отменяет корутину. Добивать Toast в уничтоженную Activity не нужно.

## Упражнения

1. Почему `button.setOnClickListener { client.ping().getOrThrow() }` плох даже если `ping` уже возвращает `Result`?
2. Чем `lifecycleScope` отличается от `GlobalScope` в сценарии «открыл экран, нажал ping, сразу назад»?
3. Status отвечает не всегда с первой попытки после питания станца. Куда поставить паузу между попытками и куда нельзя?

## Типичные ошибки

- Сеть и `Thread.sleep` в `onClick` или внутри `runOnUiThread`.
- `runBlocking(Dispatchers.Main)` вокруг ping.
- `GlobalScope` и обновление вьюхи без проверки, жив ли экран.
- `lateinit` клиент, который трогают до ввода IP.
- Показать человеку stack trace вместо одной фразы. В лог — исключение, на экран — что делать.

## Чеклист

- [ ] Ping выполняется на `Dispatchers.IO`.
- [ ] Текст на экране меняется на `Dispatchers.Main`.
- [ ] Провал сети — ветка `onFailure`, не падение Activity.
- [ ] Скоуп отменяется вместе с экраном.
- [ ] Клиент создаётся после того, как есть хост.
