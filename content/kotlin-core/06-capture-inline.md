## Цель

Объяснить, что лямбда «помнит» переменные из места, где создана. Понять, чем это опасно (утечки, общее изменяемое состояние). Знать, зачем у стандартных функций слово `inline`, и не писать его без причины.

## Зачем это вам

Счётчик, который живёт между вызовами; колбэк, который держит `Activity`; цикл, где все лямбды вдруг видят одно и то же значение. Всё это — захват. Вопрос «что такое замыкание» задают на каждом собеседовании, а вопрос «зачем inline» следом за ним.

## Теория

**Замыкание.** Лямбда может читать и менять переменные внешней функции, даже когда эта функция уже вернулась.

```kotlin
fun makeCounter(): () -> Int {
    var count = 0
    return { count++ }
}

val a = makeCounter()
val b = makeCounter()
println(a()) // 0
println(a()) // 1
println(b()) // 0, у b свой count
```

Каждый вызов `makeCounter` создаёт свою переменную `count`, и лямбда, которую он вернул, держит именно её. В Java так нельзя (там только `final`), в Kotlin `var` захватывается: компилятор прячет её в специальный объект-«ящик».

**Что именно захвачено.** Не значение на момент создания, а **сама переменная**. Если вы потом измените её, лямбда увидит новое значение:

```kotlin
var name = "станц"
val say = { println(name) }
name = "лампа"
say() // лампа
```

Если нужен снимок, сделайте копию: `val snapshot = name` и используйте её.

**Захват в цикле.** `for (i in 0..2) actions += { println(i) }` в Kotlin безопасен: у каждого шага цикла своя `i`. А вот внешняя `var i = 0` с `while` разделяется всеми лямбдами, и они напечатают итоговое значение.

**Захват `this`.** Лямбда в методе класса может звать методы класса. Тем самым она держит ссылку на экземпляр. Для Android это главная ловушка: лямбда, спрятанная в синглтоне или в статическом поле, держит `Activity` и мешает собрать её сборщиком мусора после поворота экрана.

```kotlin
object Bus {
    var listener: (() -> Unit)? = null   // живёт всё время процесса
}

class ScreenActivity : ComponentActivity() {
    override fun onStart() {
        super.onStart()
        Bus.listener = { updateUi() }     // держит this
    }
    override fun onStop() {
        Bus.listener = null               // обязательно: отписка
        super.onStop()
    }
}
```

Правило: кто подписывает, тот отписывает. В Compose и корутинах этим занимаются `DisposableEffect` и `lifecycleScope`.

**Общее состояние и потоки.** Лямбда, которая меняет `var` из другого потока, создаёт гонку. Для счётчика между потоками берут `AtomicInteger` или `Mutex`. В Compose захваченное состояние переносят в `mutableStateOf`, иначе экран не узнает об изменении.

**Захват в Compose.** `remember { ... }` помнит значение между перерисовками. Лямбда, переданная в `Button(onClick = { count++ })`, захватывает `count` — но только если это `MutableState`, а не обычная `var`, UI не обновится. Об этом [урок про remember](../02-kotlin-android/07-remember.md).

## inline

Каждая лямбда — это объект: память и вызов через интерфейс. Для `list.filter { ... }` на тысячи элементов лишний объект на вызов не критичен, но внутри цикла по миллионам он заметен.

`inline fun` говорит компилятору: подставить тело функции и тело лямбды прямо в место вызова, без создания объекта.

```kotlin
inline fun measure(block: () -> Unit): Long {
    val start = System.nanoTime()
    block()
    return System.nanoTime() - start
}
```

Что это даёт:

- нет объекта лямбды и вызова через интерфейс;
- `return` из лямбды выходит из внешней функции (нелокальный `return`), поэтому в `forEach` это работает; поэтому же не работает в обычной (не inline) функции;
- работает `reified` для дженериков: `inline fun <reified T> parse(json: String)`. Это основная причина писать `inline` вручную.

Три слова-модификатора параметров. Для junior достаточно знать, что они существуют:

- `noinline` — этот параметр-лямбда не подставляется (нужно, если вы передаёте её дальше или храните в поле);
- `crossinline` — лямбду нельзя использовать для нелокального `return` (нужно, если вызываете её из другой лямбды или потока) — **M.**

Лямбду, которую вы **кладёте в поле** (`pendingAction`), inline сделать нельзя: ей нужен настоящий объект. Поэтому в [прошлом уроке](05-nullable-lambdas.md) параметр `onReady` лежит в обычной функции.

**Когда писать inline самому.** Почти никогда. Три случая: маленькая функция с лямбдой-параметром, которую зовут в горячем цикле; `reified`; своя функция в стиле `measure { }`. Просто «для скорости» — нет: JVM сама оптимизирует, а раздутый байткод вредит.

## Разбор на примере

Две реализации «выполнить N раз»:

```kotlin
fun repeatPlain(n: Int, action: (Int) -> Unit) { for (i in 0 until n) action(i) }
inline fun repeatInline(n: Int, action: (Int) -> Unit) { for (i in 0 until n) action(i) }
```

Для вызывающего код одинаков: `repeatPlain(3) { println(it) }`. Разница под капотом: у `repeatInline` на месте вызова оказывается обычный `for`. И ещё одна, видимая сразу:

```kotlin
fun first(): Int {
    repeatInline(5) { if (it == 2) return it }   // можно
    repeatPlain(5) { if (it == 2) return it }    // ошибка: return не из функции
    return -1
}
```

Стандартные `forEach`, `map`, `filter`, `let`, `run`, `also`, `apply` — все `inline`. Поэтому в них работает нелокальный `return`, а в `Thread { return }` нет.

- Называете три причины утечки `Activity` через лямбду: статическое поле, синглтон, непрерванный слушатель.

## Типичные ошибки

- Ждать, что лямбда запомнила значение, а не переменную.
- Лямбда в `object` или в `companion`, которая держит экран и никогда не отписывается.
- Разделяемая `var` без синхронизации в корутинах на разных диспетчерах.
- `inline` на функции без лямбда-параметров: компилятор предупредит, смысла нет.
- `inline` на большой функции: байткод копируется в каждый вызов.
