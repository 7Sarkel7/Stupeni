## Цель

Читать `(() -> Unit)?`, вызывать такую лямбду через `?.invoke()`, хранить действие в поле как отложенное и запускать его ровно один раз. Объяснить, почему `callback?.()` и `callback?.invoke()` — одно и то же, а `callback()` не скомпилируется.

## Зачем это вам

Callback, которого может не быть, встречается постоянно: слушатель, которого ещё не подписали; действие, которое выполнят после подключения; `onDismiss` у диалога по умолчанию. Для Bluetooth и Wi-Fi это основной паттерн: «хочу отправить команду, но сначала нужно подключиться». Здесь же самая частая причина путаницы: тип `(() -> Unit)?` выглядит страшно, хотя это просто `Int?`, где вместо `Int` лямбда.

## Теория

**Тип с вопросом.** `() -> Unit` — функция. `(() -> Unit)?` — «функция или `null`». Скобки вокруг типа функции обязательны: без них вопрос относился бы к результату.

```kotlin
val a: () -> Unit? = { null }     // функция, возвращающая Unit? — не то!
val b: (() -> Unit)? = null       // сама функция может быть null
```

**Нельзя вызвать напрямую.** Компилятор скажет, что значение может быть `null`:

```kotlin
var onReady: (() -> Unit)? = null
onReady()      // ошибка компиляции
```

**Безопасный вызов: `?.invoke()`.** Любая функция — объект с методом `invoke`. Вызов `f(x)` — сахар над `f.invoke(x)`. Поэтому к nullable-функции применим обычный `?.`:

```kotlin
onReady?.invoke()
```

Если `onReady == null`, ничего не происходит. Если нет, вызывается. Сокращённая запись `onReady?.()` корректна, но читается хуже; в командах чаще `?.invoke()`.

**Параметры и результат.**

```kotlin
var onResult: ((String) -> Unit)? = null
onResult?.invoke("готово")

val parser: ((String) -> Int)? = null
val value: Int = parser?.invoke("42") ?: 0   // результат — Int?, добавили Элвис
```

**Умное приведение.** Для локальной `val` или параметра работает проверка:

```kotlin
fun notify(callback: (() -> Unit)?) {
    if (callback != null) callback()   // здесь уже () -> Unit
}
```

Для **изменяемого поля класса** `var` умное приведение не сработает: в другом потоке поле могли обнулить между проверкой и вызовом. Копия решает вопрос: `val action = pendingAction; if (action != null) action()` или `?.invoke()` напрямую.

**Параметр по умолчанию `null`.** Обработчик необязателен:

```kotlin
fun showDialog(text: String, onDismiss: (() -> Unit)? = null) { ... }
showDialog("Готово")
showDialog("Готово") { println("закрыли") }  // хвостовая лямбда работает и для nullable
```

## Паттерн: отложенное действие

Задача. Пользователь нажал «Показать файл». Соединения с станцом ещё нет. Нужно: подключиться, и **когда** подключимся, выполнить нажатое. Запоминаем действие в переменной и вызываем после события.

```kotlin
class LampLink(private val transport: Transport) {
    private var pendingAction: (() -> Unit)? = null
    private var connected = false

    fun runWhenReady(onReady: () -> Unit) {
        if (connected) {
            onReady()
        } else {
            pendingAction = onReady
            transport.connect()
        }
    }

    fun onConnected() {          // вызывает транспорт, когда соединение готово
        connected = true
        pendingAction?.invoke()
        pendingAction = null
    }
}
```

Чем это работает:

1. `pendingAction = onReady` — лямбда не вызывается, а кладётся в поле. Это значение, как строка.
2. `connect()` запускает асинхронную работу и сразу возвращает управление.
3. Позже система зовёт `onConnected()`. Там `pendingAction?.invoke()` вызывает отложенное.
4. `pendingAction = null` — очистка. Без неё при следующем подключении сработает старое действие второй раз. Это самый частый баг паттерна.

Те же шаги в сжатом виде из задачи: `pendingAction = onReady; connect(); ... pendingAction?.invoke(); pendingAction = null`.

**Что обязательно решить в паттерне:**

- Что если действие попросили, пока подключение уже идёт? Либо заменить (последний выигрывает), либо ставить в очередь. Нужен флаг `connecting`, иначе вы позовёте `connect()` дважды.
- Что если соединение оборвалось? Обычно отложенное действие сбрасывают: через минуту оно будет неактуальным.
- Порядок: сначала взять действие в локальную переменную и обнулить поле, потом вызвать. Если лямбда сама вызовет `runWhenReady`, поле уже свободно:

```kotlin
fun onConnected() {
    connected = true
    val action = pendingAction
    pendingAction = null
    action?.invoke()
}
```

- Какой поток вызывает `onConnected`. В Android колбэки BLE и сокета приходят не с главного потока, а лямбда может трогать UI. Тогда переключение потока делает вызывающий, или поле защищают. В этом курсе главный поток и корутины разобраны в [уроке про корутины](../02-kotlin-android/01-coroutines.md) и [Job, scope](13-job-scope.md).
- Утечка: лямбда в поле держит всё, что захватила, включая `Activity`. Подробнее в [следующем уроке](06-capture-inline.md).

## Разбор на примере

Тест на паттерн пишут без железа: транспорт — подделка.

```kotlin
class FakeTransport : Transport {
    var connectCalls = 0
    override fun connect() { connectCalls++ }
}

val transport = FakeTransport()
val link = LampLink(transport)
val log = mutableListOf<String>()

link.runWhenReady { log += "показать" }
check(transport.connectCalls == 1 && log.isEmpty())  // подключились, действие ждёт
link.onConnected()
check(log == listOf("показать"))                      // выполнено
link.onConnected()
check(log == listOf("показать"))                      // второй раз не выполнено
```

Эту проверку вы запускаете в [работе](07-homework-lambdas.md), там `PendingLink` с флагом `connecting` и сбросом при разрыве.

## Упражнения

1. Допишите тип. Что здесь `null`-able: `val f: (Int) -> String?`, `val g: ((Int) -> String)?`, `val h: (Int?) -> String`?
2. Перепишите `if (cb != null) cb(x)` в одну строку с `?.invoke`.
3. Напишите `fun notifyIfPresent(callback: ((String) -> Unit)?, message: String): Boolean`: возвращает `true`, если вызвали. Реализуйте её в `Lambdas.kt` и запустите `nullableCallbackIsSafe`.
4. Напишите класс `Debounced`, который хранит `var last: (() -> Unit)?`. Метод `schedule(action)` заменяет `last`, метод `flush()` вызывает его один раз и обнуляет. Проверьте руками.
5. Почему `pendingAction = null` ставят после вызова, а не вместо? Что произойдёт, если вызвать `pendingAction?.invoke()`, а лямбда внутри вызовет `runWhenReady` снова? (Поле перезапишется, а потом обнулится: новое действие потеряно. Поэтому порядок «взять, обнулить, вызвать».)
6. Устно: чем пара «`callback?.invoke()`» отличается от «`callback!!.invoke()`» в сценарии, когда колбэка нет?

### Самопроверка

- Отличаете `() -> Unit?` и `(() -> Unit)?` и можете объяснить на примере.
- Объясняете паттерн отложенного действия по четырём шагам.
- Назовёте три решения, которые паттерн заставляет принять: повторный запрос, обрыв, порядок обнуления.

## Типичные ошибки

- Не обнулить поле после вызова: действие срабатывает при каждом подключении.
- Вызвать `connect()` на каждый запрос, пока подключение ещё идёт.
- Проверить `if (pendingAction != null) pendingAction()` для `var`-поля: не компилируется (или гонка).
- Хранить в поле лямбду, захватившую `Activity`, и забыть сбросить на `onDestroy`.
- Обернуть лямбду в `try/catch` с пустым телом: ошибка внутри отложенного действия пропадёт молча.
- `!!` вместо `?.invoke()`.
