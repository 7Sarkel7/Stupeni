# Намёк. 01-git-12-project

Откройте после своей попытки. Здесь вид результата и ответы на вопросы вечера, не скрипт, который выполняет шаги за вас.

1. Перед слиянием (мерж — слияние, то есть объединение изменений одной ветки Git с другой) локальный `main` догоняют `git pull --ff-only`, чтобы коммит (сохранённый в Git снимок изменений с подписью) коллеги с `model` был на первой линии, а не сбоку. После `merge --no-ff` на графе узел слияния, под ним коммит `docs` и осмысленный `feat` (не три `wip`). После squash (склеивание нескольких коммитов в один) на `main` один новый коммит с общим diff (дифф — список отличий между двумя версиями файла: что добавили, что убрали). Тег (постоянная метка на коммите, обычно с номером версии) `v0.1.0` стоит на выпуске, `git show v0.1.0` печатает сообщение про timeout (таймаут — предельное время ожидания ответа, после которого ожидание обрывают) 800 и model. Точный `--stat` зависит от способа вливания: смотрите свой вывод.
2. `--ours` во время rebase (ребейз — перенос ваших коммитов поверх другого, более свежего коммита, чтобы история выглядела прямой) — это `origin/main`, таймаут 3000 и model. Ваши 800 лежат в нижнем блоке. Целиком `--ours` оставит 3000.
3. Amend (дописывание или исправление последнего коммита вместо нового) заменит SHA (SHA, хеш — уникальный идентификатор коммита из букв и цифр), на который ссылается комментарий. Force-with-lease обновит ветку, только если чужого коммита сверху не было, и всё равно оторвёт обсуждение от старого патча (небольшой набор правок, который можно применить к коду). Новый коммит `docs:` оставляет и замечание, и ответ.
4. Перед последним push (пуш — отправка ваших коммитов на сервер, например на GitHub) `git status` не должен показывать `.env` как файл к коммиту. Если GitHub не открывали, описание лежит в `pr.md` и прямо говорит, что страницы PR (pull request — просьба на GitHub проверить ваши изменения и добавить их в основную ветку) не было.
