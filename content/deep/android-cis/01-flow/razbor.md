# Разбор по шагам

Каждый пример показан в трёх частях: **до** (что есть), **действие** (что делаем), **после** (что получилось).

## Шаг 1. Холодный Flow ничего не делает, пока его не соберут

Бытовая картинка: вы написали рецепт, но не поставили кастрюлю на плиту. Рецепт есть, борщ — нет.

**До.** Описали поток из двух статусов:

```kotlin
val statuses = flow {
    println("старт")
    emit("жду")
    emit("готово")
}
```

На экране консоли пока пусто: слово «старт» не напечатано. Код внутри `flow { }` ещё не запускался.

**Действие.** Собираем поток дважды:

```kotlin
statuses.collect { println(it) }
statuses.collect { println(it) }
```

**После.** В консоли:

```text
старт
жду
готово
старт
жду
готово
```

Видно главное: слово «старт» напечатано **дважды**. Каждый сборщик запускает тело `flow { }` с самого начала. Поэтому поток называют холодным: он «остыл» и не работает, пока кто-то не пришёл.

:::tip Где это важно
Если `flow { }` внутри читает таблицу базы, то два сборщика — это два чтения. Иногда это нужно, иногда нет. Поэтому надо знать, где сборщик один.
:::

## Шаг 2. Операторы описывают конвейер, но тоже ничего не запускают

`map`, `filter` и им подобные **добавляют шаги** в конвейер:

```kotlin
val loud = statuses.map { it.uppercase() }
```

**До.** `statuses` умеет отдавать «жду» и «готово».
**Действие.** Вызвали `map`. Никто не собирает.
**После.** Ничего не напечатано и не выполнено. Получился новый холодный поток `loud`, который сработает только на `collect`.

## Шаг 3. StateFlow: у него всегда есть текущее значение

Бытовая картинка: табло на вокзале. Вы подошли, а оно уже что-то показывает. Вы не ждёте следующего объявления.

```kotlin
val state = MutableStateFlow("ещё нет")
```

**До.** `state.value` равно `"ещё нет"`. Подписчика нет.

**Действие.** Подписываемся (внутри корутины) и два раза подряд записываем одно и то же:

```kotlin
state.collect { println("получил: $it") }   // в отдельной корутине
state.value = "жду"
state.value = "жду"
```

**После.** Подписчик напечатает:

```text
получил: ещё нет
получил: жду
```

Два нюанса:

1. Подписчик **сразу** получил текущее значение (`ещё нет`), ждать не пришлось.
2. Вторая запись `"жду"` ничего не напечатала: `StateFlow` сравнивает новое значение со старым через `equals` и повтор не отправляет. Поэтому экран не дёргается зря.

## Шаг 4. Кто хозяин: ViewModel и viewModelScope

Данные экрана живут во `ViewModel`. У неё есть свой скоуп: `viewModelScope`. Когда `ViewModel` уничтожена, всё, что запущено в этом скоупе, **отменяется само**.

Схема (это иллюстрация на другом примере, не решение задания из практики):

```kotlin
class TeaViewModel : ViewModel() {

    // Внутри можно менять
    private val _seconds = MutableStateFlow(0)

    // Наружу отдаём только чтение
    val seconds: StateFlow<Int> = _seconds

    init {
        viewModelScope.launch {
            while (true) {
                delay(1_000)
                _seconds.value = _seconds.value + 1
            }
        }
    }
}
```

**До.** Экран открыт, `seconds` равно 0.
**Действие.** Каждую секунду корутина прибавляет единицу.
**После.** `seconds` растёт: 1, 2, 3… Пользователь закрыл экран, `ViewModel` уничтожена, цикл остановился сам.

Почему наружу отдают `StateFlow`, а не `MutableStateFlow`: чтобы экран не мог по ошибке сам записать значение. Меняет данные только `ViewModel`.

## Шаг 5. Подключаем к экрану Compose

```kotlin
@Composable
fun TeaRoute(viewModel: TeaViewModel = viewModel()) {
    val seconds by viewModel.seconds.collectAsStateWithLifecycle()
    Text("Прошло секунд: $seconds")
}
```

**До.** Экран пустой.
**Действие.** `collectAsStateWithLifecycle` подписывается на `StateFlow`.
**После.** Текст обновляется с каждым новым значением. Когда экран свернули и его не видно, подписка приостанавливается, а когда вернулись, возобновляется. Это экономит батарею.

:::danger Типичные ошибки
- **`collect` прямо в теле composable.** Compose перерисовывает функцию много раз; подписки будут плодиться. Подписываются один раз, через `collectAsStateWithLifecycle`.
- **`GlobalScope.launch`.** Эта работа переживёт экран и продолжит гонять данные в никуда. В этом треке `GlobalScope` не используют.
- **Пустой `catch (e: Exception)` вокруг корутин.** Он проглатывает отмену (`CancellationException`), и корутина «не умирает». Отмену пробрасывают дальше.
- **Собрать один холодный поток из двух мест.** Тело запустится дважды, значения задвоятся (шаг 1).
:::

## Для любопытных: SharedFlow

`StateFlow` хранит снимок. Для **событий без текущего значения** (показать тост один раз, перейти назад) берут `SharedFlow`. Если положить в него снимок списка, после поворота экрана придётся хранить список отдельно.
