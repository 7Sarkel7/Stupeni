## Теория

### Wi-Fi и сеть

**Состояние сети.** `ConnectivityManager.registerDefaultNetworkCallback` сообщает, когда сеть появилась и пропала. `NetworkCapabilities` говорит, что это Wi-Fi или мобильная сеть и есть ли доступ в интернет.

```kotlin
val cm = context.getSystemService(ConnectivityManager::class.java)
val callback = object : ConnectivityManager.NetworkCallback() {
    override fun onAvailable(network: Network) { online.value = true }
    override fun onLost(network: Network) { online.value = false }
}
cm.registerDefaultNetworkCallback(callback)
// отписка обязательна: cm.unregisterNetworkCallback(callback)
```

Колбэк превращают в `callbackFlow` и отдают в `StateFlow`. Подписка живёт, пока подписан сборщик ([урок про Flow](../android-cis/01-flow.md)); `awaitClose { cm.unregisterNetworkCallback(callback) }`.

**Плата в режиме точки доступа (SoftAP — плата сама раздаёт Wi-Fi, как маленький роутер).** Телефон подключён к Wi-Fi платы, где нет интернета. Android может считать сеть «без интернета» и направлять трафик по мобильной сети. Чтобы запросы к плате шли через Wi-Fi, сеть запрашивают и привязывают:

```kotlin
val request = NetworkRequest.Builder()
    .addTransportType(NetworkCapabilities.TRANSPORT_WIFI)
    .build()
cm.requestNetwork(request, object : ConnectivityManager.NetworkCallback() {
    override fun onAvailable(network: Network) {
        // OkHttpClient.Builder().socketFactory(network.socketFactory)
    }
})
```

Подключение к конкретной сети из приложения на новых Android делают через `WifiNetworkSpecifier` и системный диалог (нужны Android 10+, разрешения `CHANGE_NETWORK_STATE`, на Android 13+ ещё `NEARBY_WIFI_DEVICES`); обычно проще попросить пользователя подключиться в настройках и проверить, что сеть та самая.

**Открытый HTTP.** Плата отвечает по `http://`, а Android с API 28 по умолчанию запрещает cleartext (передача данных по HTTP без шифрования). Для локальной лампы это разрешают точечно через `network_security_config` для нужного адреса, а не `usesCleartextTraffic="true"` на всё приложение. Подробности — [урок про OkHttp](../02-kotlin-android/02-okhttp.md).

**Поиск по имени (mDNS/NSD).** Вместо ввода IP: `NsdManager.discoverServices("_http._tcp", NsdManager.PROTOCOL_DNS_SD, listener)`. Найденный сервис нужно «разрешить» (`resolveService` или `registerServiceInfoCallback` на новых API), чтобы получить адрес и порт. Плата со своей стороны объявляет сервис (mDNS на ESP32). Ограничения: часть роутеров глушит multicast, гостевая сеть изолирует клиентов; всегда оставляйте ручной ввод IP.

### BLE

**Роли.** Телефон — *central* (ищет и подключается), плата — *peripheral* (рекламирует себя и ждёт). Данные лежат в **GATT**: *сервис* (группа) → *характеристика* (значение с правами чтения, записи, уведомления), у каждого UUID (длинный практически уникальный идентификатор).

**Шаги.**

1. Разрешения ([урок 03](03-permissions.md)): на API 31+ `BLUETOOTH_SCAN` и `BLUETOOTH_CONNECT`. Bluetooth должен быть включён.
2. **Скан** через `BluetoothLeScanner.startScan(filters, settings, callback)`. Фильтр по UUID сервиса или имени обязателен: без него придут все устройства вокруг, и батарея пострадает. Скан останавливают по первому подходящему результату и по таймауту (предельное время ожидания ответа, после которого ожидание обрывают).
3. **Подключение** `device.connectGatt(context, autoConnect = false, callback)`. Результат приходит в `onConnectionStateChange`. Объект `BluetoothGatt` обязательно закрывают `close()`, иначе исчерпается лимит соединений.
4. **Поиск сервисов** `gatt.discoverServices()` → `onServicesDiscovered`.
5. **Запись и чтение** характеристики: `writeCharacteristic`, `readCharacteristic`. Результат в `onCharacteristicWrite/Read`.
6. **Уведомления:** `setCharacteristicNotification` плюс запись в дескриптор `0x2902` (CCCD). Новые значения в `onCharacteristicChanged`.

**Правила, которые ломают новичков (M.):**

- **Одна операция за раз.** Нельзя отправить две записи подряд: вторая потеряется или упадёт. Нужна очередь: следующая операция стартует в колбэке завершения предыдущей. Это тот самый паттерн (типовой проверенный приём решения задачи) отложенного действия, но с очередью.
- Колбэки приходят **не с главного потока**. Работу с UI (пользовательский интерфейс: всё, что видит и нажимает человек) переключайте.
- Ошибка `status = 133` — «общая ошибка стека»; лечат закрытием `gatt`, паузой и повтором.
- Размер данных ограничен MTU (`requestMtu`); большой файл режут на куски.
- Поведение зависит от производителя телефона. Тестируйте минимум на двух.
- Если нужно «подключиться, потом отправить» — не вызывайте `write` сразу после `connectGatt`: ждите `onServicesDiscovered`.

Готовые обёртки (например, Nordic Android-BLE-Library и Kotlin-BLE-Library) берут на себя очередь и повторы. Для учебной задачи полезно один раз сделать руками, в работе — брать проверенное.

**Обёртка в корутины.** `suspend fun connect(): Result<Unit>` через `suspendCancellableCoroutine` или `CompletableDeferred`, завершаемые в колбэке. Тогда код отправки читается сверху вниз: `connect(); discover(); write(cmd)`. Отмена корутины закрывает `gatt` ([урок 13](../kotlin-core/13-job-scope.md)).

### Что говорить честно

Если вы запускали только локальный HTTP, в резюме это и пишете. BLE «читал документацию» и «подключил характеристику, отправил байт и увидел светодиод» — две разные строки.

## Разбор на примере

Кнопка «Включить» при выключенном соединении с лампой.

- Состояние: `Disconnected`, `Connecting`, `Ready`.
- Нажатие: если `Ready` — отправить; иначе запомнить действие, запустить подключение (один раз, пока идёт), по `onServicesDiscovered` выполнить запомненное и очистить поле. Это та самая логика, которую вы пишете в [работе по лямбдам](../kotlin-core/07-homework-lambdas.md).
- Обрыв: состояние `Disconnected`, запомненное действие сбрасывается, экран говорит «потеряли связь».
- На выходе с экрана: `gatt.close()`.

## Упражнения

Нужна плата с BLE или второй телефон с приложением nRF Connect.

1. Включите `nRF Connect` и найдите вашу плату. Выпишите UUID сервиса и характеристик.
2. Напишите скан по UUID сервиса с таймаутом 10 секунд и остановкой по первому результату.
3. Подключитесь, найдите сервисы, прочитайте одну характеристику и выведите в лог (журнал, куда программа записывает, что делает).
4. Отправьте одну команду. Затем отправьте две подряд и посмотрите на последствия; сделайте очередь.
5. Для Wi-Fi: подпишитесь на `NetworkCallback` и покажите баннер «нет сети». Отключите Wi-Fi и проверьте.
6. Через `NsdManager` найдите сервис `_http._tcp` в домашней сети (или mDNS на плате) и выведите адрес.
7. Устно: чем BLE central отличается от peripheral? Почему скан без фильтра плох? Что такое CCCD?

## Типичные ошибки

- Скан без фильтра и без остановки.
- Не закрывать `BluetoothGatt`.
- Вызвать `write` сразу после `connectGatt`.
- Несколько операций одновременно.
- Работа с UI из колбэка BLE.
- `usesCleartextTraffic="true"` на всё приложение ради одной лампы.
- Нет ручного ввода IP при поиске по имени.
- Не отписаться от `NetworkCallback`.
